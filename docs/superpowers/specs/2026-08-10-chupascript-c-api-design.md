# ChupaScript: публичный C API

Дата: 2026-08-10
Статус: скелет зафиксирован; форма `Value` и модель ошибок открыты

## 1. Область документа

Документ фиксирует границу между рантаймом ChupaScript и хостом: время жизни
сущностей, формат входных данных, соглашения заголовка и набор функций.

Заголовок один — `core/include/chupascript/chupascript.h`. Он рассчитан на
прямое чтение из Swift и на обёртку для Kotlin, поэтому C-совместим целиком и не
содержит ни одного типа C++.

Грамматика и семантика языка определены в `docs/grammar.md` и
`docs/semantics.md`; этот документ их не повторяет.

## 2. Как API используется

Схема, под которую он спроектирован:

1. Контроллер экрана получает JSON: макет вьюх и данные.
2. Создаёт **один контекст** на экран.
3. Загружает данные — один вызов.
4. Разбирает макет, создаёт вьюхи. Для каждой вьюхи заводится структура `Props`,
   в полях которой лежат скомпилированные выражения.
5. Отрисовка вычисляет выражения; действия пользователя выполняют скрипты.
6. Экран закрыт — контекст уничтожен, вместе с ним всё остальное.

## 3. Владение и время жизни

**Владеющая сущность одна — `ChupaContext`.** Хост её создаёт и уничтожает;
больше в API нет ничего, что требует освобождения.

**Всё, что породил контекст, — невладеющие хендлы:** `ChupaExpression *`,
`ChupaScript *`, значения. Они живут до смерти контекста; использование после —
неопределённое поведение.

Следствия:

- Функция уничтожения в API ровно одна. Двойное освобождение невыразимо.
- Swift-структура `Props` остаётся структурой: поля-`OpaquePointer` копируются
  побитово, `deinit` не нужен, счётчики ссылок не появляются.
- Одинаковые исходники вправе вернуть **один и тот же** указатель. Дедупликация
  возможна именно потому, что владения нет: будь у выражения своё уничтожение,
  разделяемое дерево пришлось бы считать ссылками. API её уже допускает, и
  введение дедупликации не потребует изменений в заголовке.

Выигрыш от дедупликации не косметический: лента из 60 ячеек по 8 props — это
480 вызовов компиляции и 8 уникальных выражений.

**Память — одна арена на контекст.** В ней лежит всё: скопированный текст
исходников, разобранные данные, деревья разбора, значения. Поштучного
освобождения нет вовсе; вся память возвращается при уничтожении контекста.

**Потоки — без внутренней синхронизации.** Один контекст одновременно использует
не более одного потока; последовательное использование из разных потоков
допустимо. Разные контексты независимы: глобального изменяемого состояния в
библиотеке нет, поэтому два экрана могут готовиться параллельно.

## 4. Фазы контекста

```
создан  →  данные поставлены  →  компиляция и вычисление
```

`chupa_context_set_data` вызывается **ровно один раз** и **до первой
компиляции**. Нарушение порядка сообщается тем же каналом, что и прочие
неудачи (§8): повторный `set_data` возвращает `false`, компиляция без данных —
`NULL`.

Из порядка следует, что компилятор видит состав корневых имён. Поэтому
обращение к несуществующему корню — **ошибка компиляции**: `usre.name`
отвергается при разборе макета, а не при первом показе экрана.

Глубже первого сегмента проверять нечего: `user.prfoile.avatar` даёт `null` по
правилам чтения у `null` (`docs/semantics.md` §6.3) и ошибкой не является ни на
каком этапе.

## 5. Формат данных

Данные приходят объектом JSON; его ключи становятся корневыми именами.

```json
{"user": {"name": "Вася"}, "state": {"count": 0}}
```

JSON выбран потому, что бэкенд отдаёт именно его, а его модель значений
совпадает с нашей один в один: `null`, `true`/`false`, число, строка, объект,
массив — ровно шесть типов из `docs/semantics.md` §2.1, без лишнего. Бинарный
формат парсится быстрее, но требует разобрать JSON и переупаковать, то есть
разбор случается дважды.

Профиль:

| Вопрос | Решение | Обоснование |
|---|---|---|
| Верхний уровень | объект | Его ключи — корневые имена |
| Числа | принимается всё, что допускает JSON, включая экспоненту; всё становится `double` | `from_chars` с `general`. Ограничение на числовые литералы в языке к данным отношения не имеет |
| Escape-последовательности | полный набор JSON, включая `\uXXXX` и суррогатные пары → UTF-8 | `json.dumps` по умолчанию экранирует всю кириллицу в `\u`; отказ сломал бы типичный бэкенд |
| Строки без escape-последовательностей | срез буфера, без аллокации | Текст и так копируется в арену один раз |
| Строки с escape-последовательностями | раскодируются в арену | |
| Дубликаты ключей | последний выигрывает | Бэкенд их отсутствия не гарантирует |
| Глубина вложенности | предел 64 | Рекурсивный спуск на `[[[[…` роняет стек; две строки кода снимают класс падений |
| Комментарии, висячие запятые, `NaN`, `Infinity` | не принимаются | Ни один бэкенд их не шлёт; каждое — ветка в парсере |
| Представление объекта | массив пар, отсортированный по ключу; поиск двоичный | Порядок ключей в языке не определён (§2.1), значит сортировать вправе. Для 3–20 ключей быстрее хеш-таблицы и не аллоцирует ничего сверх массива |

**Ограничение, о котором нужно знать заранее.** Число в языке — `double`.
Идентификатор вида `"id": 9007199254740993` приедет искажённым. Лекарство одно:
такие поля бэкенд должен слать строками. Это свойство модели значений, а не
парсера, но проявляется оно здесь.

Пагинация в эту схему не входит: новая прогрузка ленты — новый контекст.

## 6. Соглашения заголовка

| Решение | Обоснование |
|---|---|
| Префикс `chupa_` у функций, `Chupa` у типов | В C нет пространств имён; `cs_` слишком ходовой, `chupascript_` длинный |
| C99; заголовок собирается и как C, и как C++ | Нужны `stdbool.h` и `stdint.h` |
| Заголовок самодостаточен | Включает `<stddef.h>`, `<stdint.h>`, `<stdbool.h>`; требующий предварительных включений заголовок ломает чужие сборки |
| Непрозрачные типы — неполные структуры | `typedef struct ChupaContext ChupaContext;` вместо `void *`: C ловит перепутанные аргументы |
| Строки на входе — `const char *` + `size_t` | Не полагаемся на NUL: Swift отдаёт `withUTF8` указателем с длиной, без копий. `size_t` Swift показывает как `Int` |
| Строки на выходе — указатель + длина, UTF-8, без NUL, во владении контекста | `count` строки в языке считает байты; строка может содержать любой байт |
| `bool` из `<stdbool.h>` | Swift видит `Bool`, а не `Int32` |
| Аннотации nullability | Swift превращает `_Nullable` в опционал, `_Nonnull` — в обычный тип; без них всё приезжает опционалом |
| Макрос `CHUPA_API` | На Android библиотека собирается с `-fvisibility=hidden` |
| Windows не закладывается | `__declspec` добавляется четырьмя строками, когда понадобится; сейчас это мёртвый код |
| Функции про сам контекст — `chupa_context_*`, операции — без этой части | Контекст принимают все функции без исключения, поэтому в именах операций эта часть несёт ноль информации |

Преамбула:

```c
#ifndef CHUPASCRIPT_H
#define CHUPASCRIPT_H

#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

#if defined(__clang__)
#  define CHUPA_NONNULL_BEGIN _Pragma("clang assume_nonnull begin")
#  define CHUPA_NONNULL_END   _Pragma("clang assume_nonnull end")
#  define CHUPA_NULLABLE      _Nullable
#else
#  define CHUPA_NONNULL_BEGIN
#  define CHUPA_NONNULL_END
#  define CHUPA_NULLABLE
#endif

#define CHUPA_API __attribute__((visibility("default")))

#ifdef __cplusplus
extern "C" {
#endif

CHUPA_NONNULL_BEGIN

typedef struct ChupaContext    ChupaContext;
typedef struct ChupaExpression ChupaExpression;
typedef struct ChupaScript     ChupaScript;
```

**Ограничение импортёра Swift.** Все три непрозрачных типа Swift покажет одним и
тем же `OpaquePointer` — различать их он не умеет. Обёртка на Swift обязана
завернуть их в собственные типы, иначе `chupa_eval(ctx, script)` соберётся. В C
такая перепутка не собирается.

## 7. Функции

```c
/* Версия библиотеки как "major.minor.patch". Никогда не NULL. */
CHUPA_API const char *chupa_version(void);

/* ─── Контекст ─────────────────────────────────────────────────────── */

/* Создаёт пустой контекст. NULL — не хватило памяти. */
CHUPA_API ChupaContext *CHUPA_NULLABLE chupa_context_create(void);

/* Уничтожает контекст и всё, что он породил: данные, скомпилированные
 * выражения и скрипты, значения. NULL допустим и ничего не делает. */
CHUPA_API void chupa_context_destroy(ChupaContext *CHUPA_NULLABLE ctx);

/* Загружает данные: объект JSON, ключи которого становятся корневыми
 * именами. Вызывается ровно один раз и до первой компиляции.
 * При неудаче контекст остаётся без данных. */
CHUPA_API bool chupa_context_set_data(ChupaContext *ctx,
                                      const char *json, size_t len);

/* Описание последней неудачи на этом контексте. Действительно до
 * следующего вызова любой функции с этим контекстом. */
CHUPA_API const char *CHUPA_NULLABLE
chupa_context_error(const ChupaContext *ctx, size_t *CHUPA_NULLABLE len);

/* ─── Компиляция ───────────────────────────────────────────────────── */

/* Компилируют исходник. Текст копируется — буфер вызывающего больше не
 * нужен. Результат принадлежит контексту и живёт до его смерти;
 * уничтожать его отдельно нельзя и нечем. Одинаковые исходники могут
 * вернуть один и тот же указатель. NULL — ошибка компиляции. */
CHUPA_API ChupaExpression *CHUPA_NULLABLE
chupa_compile_expression(ChupaContext *ctx, const char *source, size_t len);

CHUPA_API ChupaScript *CHUPA_NULLABLE
chupa_compile_script(ChupaContext *ctx, const char *source, size_t len);

/* ─── Исполнение ───────────────────────────────────────────────────── */

/* Выполняет скрипт: мутирует данные контекста, значения не возвращает.
 * false — ошибка выполнения, часть изменений могла быть применена. */
CHUPA_API bool chupa_run(ChupaContext *ctx, ChupaScript *script);
```

**Копирование исходника закрывает вопрос о времени жизни буфера.** Требование
`docs/grammar.md` §7 — чтобы буфер пережил скомпилированную программу — снято:
контекст копирует текст в арену, строковые литералы становятся срезами этой
копии, хост освобождает свой буфер сразу. Цена — одна копия текста на экран.

**Ошибка в `chupa_run` оставляет данные изменёнными частично.** Скрипт —
последовательность стейтментов; ошибка прерывает её посередине, откатывать
нечего, поскольку арена не хранит предыдущих состояний. Обработчик, упавший на
третьем присваивании из пяти, оставит первые два применёнными. Это цена принятой
модели памяти, а не недосмотр.

## 8. Модель ошибок: зафиксирован канал, не содержание

Четыре функции сообщают о неудаче: `set_data`, обе компиляции, `run`. Обойтись
без канала нельзя — иначе синтаксическую ошибку в макете нечем заметить.

Зафиксирован **канал**: провал возвращается признаком (`false` или `NULL`),
подробность лежит в контексте и читается через `chupa_context_error`. Так
устроены sqlite и большинство C-библиотек.

**Содержание** — позиции в исходнике, коды ошибок, список диагностик вместо
одной — остаётся открытым. Выбор канала расширяем без слома: к контексту
добавляются новые аксессоры, сигнатуры функций из §7 не меняются.

## 9. Принятые решения и обоснования

| Решение | Обоснование |
|---|---|
| Один контекст на экран, время жизни задаёт хост | Совпадает с временем жизни контроллера, вьюх и `Props` |
| Ничто из порождённого не переживает контекст | Убирает подсчёт ссылок и сборщик мусора целиком: освобождение одно, вместе с ареной |
| Скомпилированное принадлежит контексту | Кэш между экранами в этой схеме не возникает — `Props` умирают вместе с контроллером. Взамен появляется дедупликация внутри экрана |
| Единственная функция уничтожения | Двойное освобождение невыразимо; `Props` остаётся структурой без `deinit` |
| Данные ставятся один раз, до компиляции | Компилятор видит состав корней и ловит опечатку в корневом имени при разборе макета |
| Формат данных — JSON | Бэкенд отдаёт его; модель значений совпадает; бинарный формат означал бы двойной разбор |
| Ключи объекта отсортированы | Порядок в языке не определён; двоичный поиск по массиву быстрее хеш-таблицы на типичных 3–20 ключах |
| Исходник копируется в арену | Снимает с хоста обязательство хранить буфер; одна копия текста на экран |
| Канал ошибок — признак плюс аксессор | Расширяется без изменения сигнатур |
| Без внутренней синхронизации | Один экран — один поток; контексты независимы, глобального состояния нет |
| `Value` — тег-юнион, без NaN-boxing | Решение пользователя: используем то, что уже есть в `core/src/value.hpp` |

## 10. Открытые вопросы

1. **Форма `Value` на границе** — структура по значению или непрозрачный хендл с
   аксессорами. Блокируется выбором обвязки Kotlin: Kotlin/Native cinterop
   читает заголовок сам, JNI не видит его вовсе и пропускает через границу
   только примитивы и хендлы. Блокирует `chupa_eval` и все аксессоры к
   значениям.
2. **Содержание диагностики** — позиции, коды, одна ошибка или список (§8).
3. **Корневые ключи, не являющиеся идентификаторами.** `{"user-name": …}` в
   программу не попадёт: обратиться к корню можно только голым идентификатором.
   Ошибка загрузки данных или молча недоступное поле?
4. **Глава 10 `docs/semantics.md`** всё ещё говорит «не написана». Решения этого
   документа её закрывают и должны быть туда перенесены.
5. **`core/src/value.hpp`**: `Value::Kind::Map` расходится с типом `Object` из
   `docs/semantics.md` §2.1; `strictEqual` и `looseEqual` ссылаются на `===` и
   `==`, тогда как равенство в языке одно.
