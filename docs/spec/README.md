# Спецификация ChupaLang

Нормативное описание языка. Всё остальное — производное от него.

```
docs/spec/              источник правды
    │
    └──▶ docs/ChupaScript.md    книга: объясняет то, что здесь определено
```

При расхождении книги или реализации со спецификацией исправляются они, а не
спецификация.

## Принцип: самодостаточность с опорой на ECMA-262

Спецификация **самодостаточна**. Чтобы реализовать язык или написать тест,
достаточно этого документа: все значения, преобразования, операторы, конструкции
и встроенные методы определены здесь, а не ссылкой наружу.

Из ECMA-262 берутся структура изложения, термины и формулировки алгоритмов,
проверенные тремя десятилетиями реализаций. Оттуда же берётся эталон поведения:
ChupaLang — подмножество JavaScript по форме без изъятий и, за вычетом
приложения C, по поведению. Если текст спецификации расходится с ECMA-262 и это
расхождение не записано в приложении C — это дефект спецификации, а не
особенность языка.

Нормативная формулировка — **правило эталона**, раздел 1.2.

Нормативная ссылка: **ECMA-262, издание 16 (ES2025)**, https://tc39.es/ecma262/
Привязка неподвижна. При выходе нового издания сверяется список изменений и
подтверждается, что подмножества они не касаются; до этого действует ES2025.

## Принцип: закрытый минимальный набор

Язык не наследует библиотеку JavaScript целиком. Встроенные средства — **закрытый
список**, в который входит только то, что действительно нужно для BDUI: разметка
экрана, отбор и преобразование данных пришедшего JSON, формирование строк.

Всё, что не перечислено в разделе 9, в языке отсутствует, даже если существует в
JavaScript. Список расширяется только явным решением; критерии расширения — в
`09-library.md`, раздел 9.8.

Это сужение законно: программа на ChupaLang остаётся корректной программой на
JavaScript.

## Принцип: проза задаёт правило, тест закрепляет значение

Всякое нормативное утверждение — абзац со стабильным идентификатором. Утверждение
задаёт правило: что вычисляется, в каком порядке, что происходит при отказе.

Точное значение закрепляет **нормативный корпус тестов**: пара «вход —
наблюдаемое поведение» на каждый идентификатор. Прозой значение фиксируется
хуже, чем примером. Что `[NaN].includes(NaN)` истинно, а `[NaN].indexOf(NaN)`
даёт −1; что `Object.keys({ b: 1, 2: 2, a: 3, 1: 4 })` даёт
`["1", "2", "b", "a"]`; что `String(1e21)` — это `"1e+21"`, а
`String(0.1 + 0.2)` — `"0.30000000000000004"`. Каждое из этих утверждений в виде
теста однозначно, а в виде абзаца — повод для спора о том, что имелось в виду.

У всякого `CS-RT-` и `CS-LIB-` должен быть хотя бы один тест; тест называется
идентификатором правила; примеры из документа должны входить в корпус как его
подмножество.

Тест поэтому не производен от спецификации, а входит в неё. Корпус исполняется
и интерпретатором, и V8: совпадение результатов есть практическая проверка
CS-CONF-0010.

## Принцип: только язык

Спецификация определяет язык и ничего сверх него. Всё, что относится к
исполнению — как единица исполнения попадает в движок, что требуется от
реализации, каким преобразованием обеспечивается поведение на Web, — вынесено в
`docs/impl/` и частью спецификации не является.

Проверить границу можно так: утверждение принадлежит спецификации, если верно
для всякой единицы исполнения ChupaLang независимо от того, кто её исполняет.

## Разделы

Номер раздела принадлежит теме, а не файлу, который её задаёт: до фазы 2 раздел
может быть распределён по нескольким артефактам, после — задаётся одним,
названным по своему номеру. Ссылаться на утверждение следует по идентификатору,
а не по номеру раздела: идентификатор не меняется никогда (раздел 2).

| № | Артефакт | Содержание | Статус |
|---|---|---|---|
| 0 | `README.md` | структура, принципы, статусы | готов |
| 1 | `01-scope.md` | область применения, инвариант, термины | готов |
| 2 | `02-notation.md` | нотация, конвенции, термины | готов |
| 3 | `03-lexical.md` | исходный текст, токены, литералы | ведётся |
| 4 | `04-values.md` | типы, значения, преобразования | готов |
| 5 | `05-names.md` | области, связывание, граф вызовов | готов |
| 6 | `06-expressions.md` | выражения | план |
| 7 | `07-statements.md` | `Statement` и объявления | план |
| 8 | `08-functions.md` | функции | план |
| 9 | `09-library.md` | встроенные средства | готов |
| 10 | `10-errors.md` | классификация ошибок | план |
| 11 | `11-tests.md` | устройство корпуса | план |
| A | `A-grammar.md` | сводка грамматики (справочное) | план |
| B | `B-narrowings.md` | сужения относительно JavaScript (справочное) | готов |
| C | `C-divergences.md` | расхождения с ECMA-262 | готов |
| D | `D-inherited.md` | наследуемое поведение (справочное) | ведётся |

Нормативны также `grammar/lexical.txt`, `grammar/syntax.txt`, `rules.json` и
`builtins.json` — до фазы 2, которая переносит продукции в разделы 3, 6, 7, 8,
распределяет правила по их разделам, переносит библиотеку в раздел 9 и собирает
из продукций приложение A; после этого все четыре файла удаляются.

Не входит в спецификацию: `docs/impl/` — профили, требования к реализации,
механизм воспроизведения на Web.

Приложение C — единственное место, где описаны расхождения с ECMA-262. Запись
приложения C содержит поведение по ECMA-262, поведение по настоящей
спецификации и причину отказа от совпадения; механизм, обеспечивающий это
поведение на Web, — предмет `docs/impl/`. Приложение D расхождений не содержит
вовсе: там поведение, которое язык наследует в точности и хотел бы изменить, но
не изменяет.

Приложение C должно оставаться коротким: всякая запись в нём требует
преобразования исходного текста на Web и ослабляет CS-CONF-0010.

Раздел получает статус «готов» только после явного решения по каждому его пункту.
