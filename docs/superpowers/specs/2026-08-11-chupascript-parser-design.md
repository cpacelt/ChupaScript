# ChupaScript: парсер и дерево разбора

Дата: 2026-08-11
Статус: спроектировано, не реализовано

## 1. Область документа

Слой превращает поток токенов лексера в дерево разбора и отвергает тексты, не
соответствующие синтаксической грамматике `docs/grammar.md` §5, включая ранние
ошибки парсера §5.5.

**В слой не входят статические проверки §6.1 и §6.2.** Обе требуют знать, что
возвращает билтин, то есть таблицу из `docs/semantics.md` §8. Парсер без неё
обходится: `count(arr);` и `push(arr, 1);` синтаксически идентичны и разбираются
одинаково. Проверки пишутся вместе с таблицей — `docs/backlog.md` B11. §6.3
отдельной проверкой не является по построению, §6.4 — поведение интерпретатора.

Граница выходит ровной: слой заканчивается ровно там, где начинается знание о
билтинах.

## 2. Что и где живёт

| Файл | Ответственность |
|---|---|

`Ast` и `Parser` разделены потому, что решения о хранении (B6–B10) меняют
`ast.cpp` и не должны трогать `parser.cpp`.

## 3. Черновик, спрятанный за швом

Хранение дерева выбрано умышленно тупым. Это допустимо ровно постольку,
поскольку оно ни для кого не видно:

- парсер создаёт узлы **только** через строитель `Ast` и получает непрозрачный
  `NodeId`;
- всё остальное — тесты в том числе — читает узлы **только** через аксессоры
  `Ast`.

Если тест напишет `nodes[i].textOffset`, шов перестанет существовать и первое же
решение о хранении сломает сотню тестов. Это главное ограничение слоя, и
нарушение его — дефект, а не стилистика.

Отложенные решения перечислены в `docs/backlog.md` B6–B10 (B12 с тех пор снята);
в коде
комментарием `// TODO(B<N>)` помечены только те два места, где решение
действительно предстоит принять при переезде — B7 (`nodes_` в `ast.hpp`) и B10
(`children_` в `ast.hpp`, `scratch_` в `parser.cpp`). B6, B8 и B9 —
свойства текущей раскладки и контракта, а не конкретной строки кода, поэтому
привязать их к месту в файле нечем.

## 4. Форма дерева

### 4.1 Виды узлов

Шестнадцать видов — прямая транскрипция `docs/grammar.md` §5.

| Вид | Дети | Своё поле |
|---|---|---|
| `Program` | стейтменты | — |
| `Assign` | цель, значение | `op` — один из `=` `+=` `-=` `*=` `/=` |
| `CallStatement` | вызов | — |
| `Conditional` | условие, ветвь-да, ветвь-нет | — |
| `Binary` | левый, правый | `op` |
| `Unary` | операнд | `op` — `!` либо `-` |
| `Index` | база, индекс | — |
| `Member` | база | имя поля |
| `Call` | аргументы | имя функции |
| `Identifier` | — | имя |
| `Number` | — | значение |
| `String` | — | срез литерала, признак экранирования |
| `Boolean` | — | значение |
| `Null` | — | — |
| `Array` | элементы | — |
| `Object` | чередование: ключ, значение, ключ, значение | — |

`EmptyStatement` узла не порождает: `;` в потоке стейтментов просто съедается.

Отдельных видов под `||`, `&&`, `??`, сравнения и арифметику нет — всё это
`Binary`, различаемый по `op`. Приоритет в дереве уже выражен формой, а не видом
узла.

Ключи объектного литерала — узлы `String`, а не отдельное поле: §5.5 требует,
чтобы ключом был строковый литерал, и узел `String` ровно это и есть.

### 4.2 Узел

Раскладка узла — приватный вложенный тип `Ast`, а не самостоятельная структура в
пространстве имён. Это и есть шов из §3, доведённый до принуждения языком:
«тест написал `nodes[i].textOffset`» не компилируется, а не порицается в ревью.
Наружу выходят только `NodeKind`, `NodeId` и `kNoNode` — то, без чего нельзя
пользоваться аксессорами.

```cpp
class Ast {
    // ...
   private:
    struct Node {
        NodeKind kind;
        TokenKind op;                      // Binary, Unary, Assign; иначе End
        std::uint32_t offset;              // смещение в исходнике для диагностики
        std::uint32_t childStart, childCount;   // диапазон в боковом пуле
        std::uint32_t textOffset, textLength;   // имя либо содержимое литерала
        double number;                     // Number
        bool boolean;                      // Boolean
        bool hasEscape;                    // String
    };
};
```

Поля не пересекаются, узел заведомо толстый — это и есть отложенное решение об
упаковке (B6). Смещение есть у каждого узла: без него сообщение об ошибке
интерпретатора не сможет указать на место в исходнике.

### 4.3 Один механизм детей

У всех видов узлов дети лежат одинаково — диапазон `{childStart, childCount}` в
одном боковом векторе `NodeId`. Бинарный узел это двое детей, тернарный трое,
вызов — аргументы, объектный литерал — `2n` чередующихся.

Однородность выбрана вместо экономии: альтернатива — отдельные поля `a`, `b`,
`c` для арности до трёх плюс диапазон для остальных — даёт два механизма и,
значит, два способа читать дерево. Тесты и интерпретатор ходили бы то так, то
эдак, а решение B10 пришлось бы принимать дважды.

Цена — одна косвенность на доступ к операнду. Она замерена бенчмарками и
отложена как B10.

### 4.4 Интерфейс `Ast`

```cpp
using NodeId = std::uint32_t;
inline constexpr NodeId kNoNode = 0;   // индекс 0 занят узлом-пустышкой
```

Строитель — единственный способ создать узел:

```cpp
NodeId number(const Token &t);
NodeId string(const Token &t);
NodeId boolean(const Token &t);
NodeId null(const Token &t);
NodeId identifier(const Token &t);
NodeId member(NodeId base, const Token &name);
NodeId index(NodeId base, NodeId subscript, std::uint32_t offset);
NodeId unary(TokenKind op, NodeId operand, std::uint32_t offset);
NodeId binary(TokenKind op, NodeId lhs, NodeId rhs, std::uint32_t offset);
NodeId conditional(NodeId cond, NodeId whenTrue, NodeId whenFalse,
                   std::uint32_t offset);
NodeId call(const Token &name, const NodeId *args, std::uint32_t count);
NodeId array(const NodeId *items, std::uint32_t count, std::uint32_t offset);
NodeId object(const NodeId *pairs, std::uint32_t count, std::uint32_t offset);
NodeId assign(TokenKind op, NodeId target, NodeId value, std::uint32_t offset);
NodeId callStatement(NodeId call, std::uint32_t offset);
NodeId program(const NodeId *statements, std::uint32_t count);
```

Аксессоры — единственный способ прочитать узел:

```cpp
NodeKind      kind(NodeId n)  const noexcept;
TokenKind     op(NodeId n)    const noexcept;
std::uint32_t offset(NodeId n) const noexcept;

std::uint32_t childCount(NodeId n) const noexcept;
NodeId        child(NodeId n, std::uint32_t i) const noexcept;

double           numberValue(NodeId n) const noexcept;
bool             boolValue(NodeId n)   const noexcept;
std::string_view text(NodeId n, std::string_view source) const noexcept;  // имя либо содержимое литерала
bool             hasEscape(NodeId n)   const noexcept;

NodeId root() const noexcept;   // kNoNode, если разбор не удался
```

`text` для `String` отдаёт содержимое **без кавычек** и без раскодирования
экранирования: сырые байты литерала плюс отдельный признак `hasEscape` — тот же
контракт, что у `Token` в лексере. Раскодирование отложено (B9).

`Ast` указателя на исходник не хранит: узлы держат смещения, а байты приходят
`text` параметром. Поэтому требования «буфер исходника обязан пережить `Ast`»
нет — B12 в бэклоге стоит в статусе «снято». Обязанность у вызывающего одна:
передать в `text` тот же текст, над которым дерево построено; в отладочной
сборке несовпадение ловится утверждением по длине (`Ast::sourceLength()`).

*Исходно этот документ описывал обратное — `Ast` держал `src_`, и правило
«пережить дерево» было настоящим. Указатель снят рефакторингом ядра
(`docs/superpowers/specs/2026-08-15-chupascript-core-entities-design.md`, Р3).*

Строитель принимает `const Token &` там, где узлу нужны и смещение, и текст, и
явное `offset` там, где смещение узла — это позиция оператора, а не токена
операнда. `binary` получает смещение оператора, `index`, `array` и `object` —
открывающей скобки: именно на них указывает сообщение об ошибке.

`count` везде — длина переданного массива `NodeId`. У `object` это `2n`, а не
число пар: дети хранятся чередованием, и строитель копирует их как есть.

## 5. Парсер

### 5.1 Поверхность

```cpp
bool parseExpression(const char *source, std::uint32_t length,
                     Ast &ast, Diagnostic &diag);

bool parseProgram(const char *source, std::uint32_t length,
                  Ast &ast, Diagnostic &diag);
```

Не `noexcept`: обе функции зовут `ast.reset(length)`, а `reset` аллоцирует
(`std::vector::clear`/`push_back`). Правило проекта — `noexcept` только там, где
нет аллокаций.

Две функции — два стартовых символа §5.1. Класс парсера живёт в `.cpp` и наружу
не видён: у него нет состояния, интересного вызывающему.

Обе после разбора требуют `TokenKind::End`; остаток текста — ошибка §5.5.
`parseExpression` не принимает `;`: стейтментов в этом режиме не существует, и
завершающая точка с запятой останется лишним токеном перед концом текста.

### 5.2 Рекурсивный спуск, транскрибирующий §5.3

Правило за правилом, в том же порядке и с теми же именами:

```
Ternary → LogicalOr → LogicalAnd → Comparison → NilCoalesce
        → Additive → Multiplicative → Unary → Postfix → Primary
```

Precedence climbing не используется. Приоритеты уже записаны цепочкой правил в
`docs/grammar.md` §5.3, и построчное совпадение кода с текстом спеки ценнее
сэкономленных кадров стека: расхождение кода и грамматики — самый дорогой вид
ошибки в этом слое, а десять маленьких функций делают его видимым при чтении.

Ассоциативность падает из формы правила и не требует отдельной логики:

| Правило | Форма | Ассоциативность |
|---|---|---|
| `LogicalOr`, `LogicalAnd`, `Additive`, `Multiplicative` | цикл `( op X )*` | левая |
| `NilCoalesce`, `Ternary` | рекурсия в себя справа | правая |
| `Comparison` | `?`, а не `*` | нет — второе сравнение подряд не разбирается |

Неассоциативность сравнений (§5.4) получена не бесплатно: `comparison()` сама
проверяет, что после разобранного сравнения следующий токен — не ещё один
оператор сравнения, и в этом случае отказывает выделенным сообщением `chained
comparison is not allowed`, а не общим «текст после стартового символа». Общее
сообщение не назвало бы причину — что именно в `a < b < c` запрещено, — а
цепочка сравнений достаточно частая опечатка, чтобы диагностика того стоила.

### 5.3 Единственная неоднозначная точка

Стейтмент начинается с `Identifier` и в случае присваивания, и в случае вызова.
Различить их по первому токену нельзя; по второму — тоже (`a.b = 1` и `a.b(1);`
расходятся только в конце цепочки).

Решение: разобрать `Identifier` с постфиксной цепочкой обычным правилом
`Postfix`, затем посмотреть на следующий токен.

| Следующий токен | Требование к разобранному | Результат |
|---|---|---|
| `AssignOp` | цепочка из `.` и `[]`, в основании `Identifier`; вызовов внутри нет | `Assign` |
| `;` | корень цепочки — `Call` | `CallStatement` |
| иное | — | ошибка §5.5 |

`LeftHandSide` в §5.2 вызовов не допускает, поэтому `f(a).b = 1` отвергается
первой строкой таблицы, а `f(a).b;` — второй: корень здесь `Member`, а не
`Call`.

Это единственное место, где парсер смотрит вперёд дальше одного токена, и
lookahead здесь не нужен вовсе: решение принимается **после** разбора, по уже
построенному поддереву.

## 6. Ошибки

Тот же `Diagnostic` и то же поведение, что у лексера: `ErrorCode::Syntax`,
смещение в байтах, сообщение. После первой ошибки разбор прекращается,
`ast.root()` возвращает `kNoNode`.

Восстановления после ошибки и множественных ошибок нет. Читатель диагностики —
разработчик макета, а макет либо компилируется, либо экран не открывается;
списка ошибок здесь никто не ждёт. Восстановление — это отдельный набор эвристик
и вдвое больший объём тестов ради вывода, которого никто не увидит.

Ошибки лексера проходят насквозь: парсер их не переписывает и не оборачивает.

## 7. Тестирование

Тесты сгруппированы по правилам грамматики. Каждое утверждение ходит через
аксессоры `Ast` — прямой доступ к `Node` в тестах запрещён (§3).

| Набор | Что проверяет |
|---|---|
| `ParserPrimary` | каждая альтернатива `Primary`, включая пустые `[]` и `{}` |
| `ParserPostfix` | цепочки `.`, `[]`, вызов; смешанные `a.b[0].c` |
| `ParserPrecedence` | все примеры §5.4 и Приложения B.2, форма дерева поэлементно |
| `ParserAssociativity` | левая у `+`, правая у `??` и `? :` |
| `ParserStatement` | обе продукции, пустой стейтмент, пустая программа |
| `ParserEarlyErrors` | каждая строка таблицы §5.5, с кодом и точным смещением |
| `ParserModes` | что разбирается в одном режиме и отвергается в другом |

Форма дерева проверяется целиком, а не «корень — `Binary`»: тест на `a + b * c`
обязан спуститься до обоих листьев. Утверждение только о корне пропускает ровно
ту ошибку, ради которой писался тест.

Негативные тесты утверждают `diag.code` **и** `diag.offset`, а не только факт
отказа: смещение — единственное, что делает диагностику полезной, и единственное,
что легко сломать незаметно.

## 8. Производительность

Бенчмарки по подмножествам грамматики, как у лексера: цепочка `Postfix`,
арифметика с приоритетами, литералы-агрегаты, реалистичное выражение props,
реалистичный обработчик. База пишется в `benchmarks/baseline.json` и сверяется
`tools/bench-compare.py`.

Черновик заведомо расточителен, и это осознанно: база нужна затем, чтобы у
каждого решения из B6–B10 была цифра до и после, а не догадка.

## 9. Принятые решения

| Решение | Обоснование |
|---|---|
| Хранение спрятано за строителем и аксессорами | Пять решений о хранении можно принимать по одному, не трогая парсер и тесты |
| `NodeId` — индекс, а не указатель | Переезд в арену (B7) не меняет ни одного типа в интерфейсе; индекс вдвое компактнее |
| Один механизм детей для всех видов узлов | Два механизма означали бы два способа читать дерево и два места для каждой будущей правки |
| Рекурсивный спуск по правилам §5.3, не precedence climbing | Построчное совпадение с грамматикой; расхождение кода и спеки — самая дорогая ошибка слоя |
| `Binary` с полем `op` вместо вида узла на оператор | Приоритет выражен формой дерева; отдельные виды дали бы 14 почти одинаковых веток |
| `Boolean` с полем-значением, а не два вида узла | Один вид на альтернативу `Primary` в грамматике; у интерпретатора одна ветка на вид |
| Ключ объектного литерала — узел `String` | §5.5 требует строковый литерал; узел `String` ровно это и означает |
| Различение стейтментов после разбора, а не по lookahead | Решение принимается по построенному поддереву, поэтому произвольная длина цепочки ничего не стоит |
| Нет восстановления после ошибки | Читатель — разработчик макета; макет либо компилируется, либо нет |
| Смещение у каждого узла | Сообщения интерпретатора обязаны указывать на место в исходнике |
| §6.1 и §6.2 не входят в слой | Требуют таблицы билтинов; без неё обе формы разбираются одинаково |
| Неассоциативность сравнений — выделенная диагностика, а не общая ошибка «текст после выражения» | Сообщение обязано называть причину отказа |
