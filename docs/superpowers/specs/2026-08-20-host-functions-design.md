# ChupaScript: функции хоста — ревизия

Дата: 2026-08-20
Статус: дизайн на согласовании, реализации нет

## 1. Область документа

Как хост объявляет собственные функции и как программа на ChupaScript их зовёт:
состав заголовка, порядок использования, что происходит на компиляции и на
вычислении, что сторожится, а что остаётся контрактом.

Грамматика вызова не меняется (`docs/grammar.md` §5.3): синтаксис
`имя(аргументы)` тот же, новых форм в языке не появляется. Меняется только то,
откуда берётся смысл имени: сегодня — исключительно из таблицы билтинов
(`core/src/builtin.cpp`), после этой работы — из неё либо из таблицы,
наполненной хостом.

**Отменяет** `docs/superpowers/specs/2026-08-14-host-functions-design.md`.
Тот документ проектировался против модели памяти, которой больше нет:
переработка от 19–20 августа
(`2026-08-19-memory-model-redesign-design.md`) сделала значение
самодостаточным и убрала пулы, а вместе с ними — половину его обоснований.
Раздел 2 перечисляет расхождения поимённо, чтобы отмена не выглядела
переписыванием по вкусу.

Семантика языка не меняется: `docs/semantics.md` §3.2 (выражения не имеют
побочных эффектов) остаётся в силе дословно, и раздел 6 объясняет, каким
устройством это удерживается.

## 2. Что изменилось с 14 августа

### 2.1 Обоснования, потерявшие предмет

| решение спеки 14.08 | на чём стояло | что с ним стало |
|---|---|---|
| `ChupaScalar` вместо `ChupaValue` на границе | «значение адресует пул индексом и живёт до следующего вычисления» | значение самодостаточно, 16 байт, считает ссылки; правила времени жизни у него те же, что у всякого результата `chupa_eval` |
| агрегат в аргументе отвергается до вызова | то же | чтение агрегата не требует контекста вовсе (`chupa_array_count` и прочие не берут `ChupaContext *`) — приём агрегата бесплатен |
| §8 «Дисциплина пулов» целиком | переезд `text_` при росте | пула `text_` не существует; всякая строка — коробка, владеющая своими байтами |
| `HostFunction::name` как `std::string`, «а не срез пула `text_`» | то же | довод исчез, решение остаётся верным по другой причине: имя переживает регистрацию |
| страж «травит контекст», потому что сеттеры возвращают `void` | сигнатуры сеттеров | сеттеры возвращают `bool` (переработка C API, задачи 6–7) — достаточно честного отказа |
| бокс обвязки держит буфер под возвращаемую строку | движок копировал `out->s` после возврата | хост делает значение прямо в колбэке через `chupa_make_string`; копии после возврата нет |

### 2.2 Что из спеки 14.08 сохраняется как было

`chupa_fail` с немедленным копированием байт сообщения; отказ регистрации при
`deterministic` без `pure`; два новых столбца в `BuiltinInfo`; единая функция
резолва `resolveCallee` на `check` и `eval`; запрет регистрации после первой
компиляции; отдельный модуль `core/src/host.*`.

### 2.3 Что добавляется

Вариадичность; `release` для `user_data`; код ошибки `CHUPA_ERR_HOST`;
агрегаты в аргументах; закрытый контекст вместо выборочных стражей.

## 3. Зачем

Хост-функция закрывает три сценария, ни один из которых сегодня не выражается:

1. **Действия.** Тап отправляет аналитику, открывает экран, показывает алерт.
   Скрипт умеет менять данные, но не умеет попросить хост что-то сделать.
2. **Чистые функции в props.** Локализация, формат даты и валюты — правила,
   живущие на стороне платформы; переносить их в язык бессмысленно.
3. **Запросы состояния хоста.** `isFeatureEnabled('x')`, `screenWidth()` —
   данные, которые не приходят с бэкенда.

Первый сценарий даёт `Void`-функции, второй и третий — возвращающие значение.
Механизм регистрации у всех трёх один.

## 4. Что пересекает границу

**Внутрь — любое значение языка**, включая `Array` и `Object`. Аргументы
приходят как `const ChupaValue *`, читаются теми же функциями, что и результат
`chupa_eval`, и живут **на время вызова**: они заимствованы (правило 1
заголовка). Хост, которому значение нужно дольше, зовёт `chupa_value_retain`.

**Наружу — только скаляр**: `Null`, `Boolean`, `Number`, `String`. Возврат
агрегата отложен (раздел 13): он потребовал бы строителя массивов и объектов в
C API и доступа к таблице ключей контекста, то есть заметно большей поверхности,
чем всё остальное в этом документе вместе взятое.

Скаляр хост собирает четырьмя функциями (раздел 5). Из них выделяет память
только строка длиннее пятнадцати байт; ссылка создателя уходит в список
отложенного освобождения контекста и живёт до границы операции — ровно как у
значения, созданного самим движком.

Вернуть можно и аргумент как есть, не копируя: его удерживает ссылка, созданная
вычислением подвыражения, и она лежит в том же списке. Отдельного удержания это
не требует.

## 5. Заголовок

Добавляется к `core/include/chupascript/chupascript.h`.

```c
/* ─── Функции хоста ────────────────────────────────────────────────────── */

typedef enum ChupaFunctionFlags {
    CHUPA_FN_NONE          = 0,
    CHUPA_FN_RETURNS_VALUE = 1u << 0,  /* без него — Void (docs/semantics.md 2.2) */
    CHUPA_FN_PURE          = 1u << 1,  /* без него — вызов только в скрипте */
    CHUPA_FN_DETERMINISTIC = 1u << 2,  /* задел под кэш props; сегодня не читается */
} ChupaFunctionFlags;

/* Без верхней границы числа аргументов — как у format. */
#define CHUPA_VARIADIC 255

/* args заимствованы и действительны только на время вызова — правило 2
 * заголовка. Пережить вызов может лишь то, что хост удержал через
 * chupa_value_retain.
 *
 * out == NULL, если функция объявлена без CHUPA_FN_RETURNS_VALUE.
 *
 * ctx закрыт: изнутри вызова на нём разрешены только chupa_make_string,
 * chupa_fail и чтение ошибки. Всё прочее отказывает с CHUPA_ERR_USAGE.
 *
 * Возврат false — отказ; перед ним коллбэк вправе позвать chupa_fail и задать
 * код с сообщением. Смещение подставляет движок — узел вызова. */
typedef bool (*ChupaHostFunction)(ChupaContext *ctx,
                                  const ChupaValue *args, size_t argc,
                                  ChupaValue *CHUPA_NULLABLE out,
                                  void *CHUPA_NULLABLE user_data);

typedef struct ChupaFunction {
    const char *name;
    size_t      name_len;
    uint8_t     min_args;
    uint8_t     max_args;   /* CHUPA_VARIADIC — без верхней границы */
    uint32_t    flags;      /* ChupaFunctionFlags */
    ChupaHostFunction call;
    void       *CHUPA_NULLABLE user_data;
    /* Зовётся ровно один раз на каждую зарегистрированную функцию из
     * chupa_context_destroy. NULL — освобождать нечего. Реестр только
     * пополняется, поэтому другого момента не существует. */
    void      (*CHUPA_NULLABLE release)(void *CHUPA_NULLABLE user_data);
} ChupaFunction;

/* Обязана быть вызвана ДО первой компиляции на этом контексте. */
CHUPA_API CHUPA_MUST_USE bool
chupa_register(ChupaContext *ctx, const ChupaFunction *fn);

/* Задаёт причину отказа. Байты сообщения копируются немедленно, поэтому буфер
 * вызывающего дальше не нужен. Зовётся только изнутри коллбэка. */
CHUPA_API void chupa_fail(ChupaContext *ctx, ChupaErrorCode code,
                          const char *msg, size_t len);

/* ─── Создание значений ────────────────────────────────────────────────── */
/* Нужны колбэку, чтобы собрать результат. Первые три памяти не выделяют
 * вовсе; строка до пятнадцати байт тоже ложится внутрь значения. */

CHUPA_API void chupa_make_null  (ChupaValue *out);
CHUPA_API void chupa_make_bool  (ChupaValue *out, bool value);
CHUPA_API void chupa_make_number(ChupaValue *out, double value);

/* Байты обязаны быть корректным UTF-8 — то же обязательство хоста, что у
 * chupa_context_set_string. false — не хватило памяти. */
CHUPA_API CHUPA_MUST_USE bool
chupa_make_string(ChupaContext *ctx, const char *bytes, size_t len,
                  ChupaValue *out);
```

К `ChupaErrorCode` добавляется `CHUPA_ERR_HOST`. Отдельный код, а не
переиспользованный: хосту, разбирающему падение, важно отличить «моя
собственная функция отказала» от «движок нашёл несовпадение типов», и по
существующим кодам это неразличимо.

### 5.1 Почему дескриптор, а не имя с коллбэком

Регистрация — прежде всего объявление сигнатуры; коллбэк к нему приложен.

`core/src/check.cpp` сегодня выдаёт три диагностики — `unknown function`,
`wrong number of arguments`, `call result is not used` — и берёт всё нужное из
`builtinInfo`. Это статический проход: ошибка в имени или арности отвергается
при компиляции макета, до первой отрисовки.

Объяви хост только имя — этих фактов для хост-функций взять неоткуда, и все три
диагностики переезжают в вычисление, то есть всплывают на конкретном кадре у
конкретного пользователя. Поля дескриптора покупают ровно сохранение уже
заявленного свойства.

Обязанность не разойтись с объявлением ложится на хост; в Swift она снимается
типами перегрузок (раздел 10).

### 5.2 Флаги одним полем, а не тремя `bool`

Три подряд идущих `bool` одного типа переставляются местами без единого слова
от компилятора, а `CHUPA_FN_PURE` и `CHUPA_FN_DETERMINISTIC` — соседи и по
смыслу. Ядро на C++17, именованной инициализации полей там ещё нет, значит
агрегатная запись у тестов и хостов будет позиционной.

Ноль при этом означает наибольшие ограничения: функция без значения, грязная,
недетерминированная. Хост, забывший заполнить поле, получает самый строгий
режим, а не самый вольный.

## 6. Флаги

**Переименование от 20.08.2026, после слияния ветки.** Имена флагов в
заголовке теперь другие, смысл прежний:

| было | стало |
|---|---|
| `CHUPA_FN_PURE` | `CHUPA_FN_EFFECT_FREE` |
| `CHUPA_FN_DETERMINISTIC` | `CHUPA_FN_CACHEABLE` |

Довод: `pure` в общем словаре значит и «без эффектов», и «тот же ответ на тех
же доводах». Из-за этого `CHUPA_FN_PURE` без `CHUPA_FN_DETERMINISTIC` читалось
как противоречие — а это ровно `now()`, самый частый случай хостовой функции в
props. Отвергнутая альтернатива — `CHUPA_FN_ELIDABLE`: она называет только
право пропустить вызов и молчит о праве позвать его повторно, а разрешение
на повтор — половина смысла флага.

Заодно из определения убрано «переставить с другим»: порядок вычисления
операндов языком задан, и разрешения переставлять вызовы движок никогда не
просил. Осталось «пропустить» и «позвать снова».

Ниже по разделу имена оставлены прежними — это запись того, что решали
20 августа. Действующие имена несут `core/include/chupascript/chupascript.h`,
`docs/semantics.md` §10.1 и `docs/grammar.md` §6.3.

Смысл разводится жёстко, потому что спутать их легко.

- **`CHUPA_FN_PURE`** — вызов не меняет наблюдаемого состояния. Решает,
  **где можно звать**.
- **`CHUPA_FN_DETERMINISTIC`** — при тех же аргументах и тех же данных даёт тот
  же результат. Решает, **можно ли кэшировать результат**.

| pure | deterministic | пример | смысл |
|---|---|---|---|
| да | да | `formatCurrency(x)` | в props можно, результат кэшируем |
| да | нет | `now()`, `screenWidth()` | в props можно, пересчитывать каждый кадр |
| нет | — | `track('tap')` | в выражении нельзя вовсе |
| нет | да | — | противоречие, регистрация отвергается |

Последняя строка — не педантизм: детерминированность обещает, что результат
можно взять из кэша, а грязная функция зовётся ради побочного эффекта, и
пропуск вызова этот эффект отменяет. Объявить оба — значит попросить движок
пропускать то, что пропускать нельзя.

**Грязная функция в выражении — ошибка компиляции**, со смещением вызова. Тот
же проход, что запрещает использовать результат `Void`-билтина. Отсюда
`docs/semantics.md` §3.2 остаётся верным дословно, а право хоста кэшировать
props — обоснованным.

**Но обоснование меняет природу, и это надо записать точно.** Сегодня
`docs/grammar.md` §6.3 не проверяет чистоту, а **выводит** её: «отдельной
проверки не требуется — билтин, изменяющий данные, не возвращает значения, а
использование результата `Void`-билтина запрещено §6.2». Вывод держится на
посылке «грязное не возвращает значения». Хост-функция вправе её нарушить:
`CHUPA_FN_RETURNS_VALUE` без `CHUPA_FN_PURE` — законное сочетание, и такая
функция в скрипте и меняет состояние, и отдаёт значение. Значит §6.3
перестаёт быть выводом и становится проверкой: у билтинов чистота держится по
устройству, у хост-функций — по объявлению плюс новая диагностика в `check`.

Код диагностики — `ErrorCode::Usage`. Три соседние проверки вызова в
`core/src/check.cpp` (`unknown function`, `wrong number of arguments`, `call
result is not used`) сегодня все ставят `ErrorCode::Name`, и это расхождение
намеренное: у новой проверки имя ни при чём. Привести к общему знаменателю
стоит все четыре разом и отдельной задачей, а не походя внутри этой.

**`CHUPA_FN_DETERMINISTIC` сегодня никем не читается.** Движок его хранит и
проверяет на противоречие; толковать начнёт кэш props (`docs/backlog.md` B29),
которого нет. Поле заводится сейчас, а не потом, чтобы не менять состав
дескриптора задним числом.

**Уточнение от 2026-08-20.** Определение `CHUPA_FN_PURE` в начале раздела —
«вызов не меняет наблюдаемого состояния» — не говорит, наблюдаемого кем. После
задачи 10 контекст на время вызова закрыт для входа через C API: хост-функция,
добравшаяся до контекста этим путём, не пишет глобальные, не вычисляет, не
компилирует. Хост, обошедший C API и получивший `CS::Context *` напрямую
(`CS::Context::registerFunction`, так делает `cli/echo.cpp`), в релизной сборке
всё ещё может позвать `setGlobal`/`setGlobalString` — там только `assert` в
отладочной сборке, релиз отказа не даёт (`docs/backlog.md` B34). При чтении
«наблюдаемого ядром» определение поэтому истинно для входа через C API и
неабсолютно для прямого входа через C++ — то есть основанием служить не может:
для одних хост-функций оно тавтология, для других — дыра. Прежнее определение
сохранено выше как запись того, что решали 20 августа; действующее определяет
флаги не через состояние движка, а через то, что каждый **разрешает** сделать
с вызовом, и от closure-аргумента не зависит:

| флаг | что разрешает | кто наблюдатель |
|---|---|---|
| `CHUPA_FN_PURE` | пропустить вызов, повторить, переставить — и никто не заметит | продукт: аналитика, навигация, показанный алерт |
| `CHUPA_FN_DETERMINISTIC` | не звать второй раз, взять ответ из кэша | программа: значение выражения |

Отсюда видно, зачем нужны оба и почему ни один не поглощает другой: чистота
бережёт право хоста не вычислять props (положи вызов с побочным эффектом в
пропс — и эффект будет теряться при кэшировании, ленивом вычислении и
пропуске невидимых вьюх, без единой ошибки), а детерминированность бережёт
верность значений. Отсюда же — обязательство хоста, нигде раньше не
записанное: побочный эффект хост-функции попадает в язык единственным путём —
через другую хост-функцию, читающую изменённое состояние хоста; значит функция,
читающая изменяемое состояние хоста, обязана быть объявлена недетерминированной.
Проверить это ядро не может, это на совести хоста, как и UTF-8 из раздела 5.
Флаги, их число и правило компиляции не меняются — правится только чтение
определения.

### 6.1 Билтины объявляют то же самое

`BuiltinInfo` (`core/src/builtin.hpp`) получает два столбца:

```cpp
struct BuiltinInfo {
    std::string_view name;
    std::uint8_t minArgs;
    std::uint8_t maxArgs;
    bool returnsValue;
    bool pure;           ///< false — меняет данные (docs/grammar.md §6.3)
    bool deterministic;  ///< задел под кэш props (docs/backlog.md B29)
};
```

У сегодняшних двенадцати билтинов `pure` совпадает с `returnsValue`: `push` и
`pop` — единственные, кто и возвращает `Void`, и меняет данные. Это не
совпадение, а буквально доказательство `docs/grammar.md` §6.3.

Выводить одно из другого в коде тем не менее нельзя: вывод верен, только пока
верна посылка, и сломает её первый билтин, который и меняет данные, и
возвращает значение. Тогда `pure` молча стал бы `true` для мутирующей функции,
а ошибка вылезла бы в кэше props. Явные столбцы делают расхождение осознанным
решением, а не побочным эффектом.

### 6.2 Чего проверить нельзя

Чистота и детерминированность, объявленные хостом, движком не проверяются и
проверены быть не могут: `now()` выражается в коде и от честного форматирования
неотличим.

`docs/grammar.md` §6.3 получает оговорку: право хоста кэшировать значения props
держится на билтинах **по устройству**, а на хост-функциях — **по объявлению**.

## 7. Имена

Пространство имён общее с билтинами: макетчик пишет `formatDate(item.ts)` и не
думает, откуда функция.

**Столкновение отвергается при регистрации** — `CHUPA_ERR_NAME` плюс
утверждение в отладочной сборке. Отвергается, а не разрешается с приоритетом:
иначе `count` переопределяется хостом и семантика `docs/semantics.md` §8
перестаёт быть свойством языка.

Рассмотренный и отвергнутый вариант — **отдельное пространство с приставкой**
(`@formatDate`). Довод за него: движок сохраняет право заводить новые билтины,
не рискуя столкнуться с чужой регистрацией у клиента, который уже обновился.
Довод против, решивший дело: код регистрации статичен и выполняется безусловно
при старте, поэтому столкновение всплывает утверждением на машине
разработчика в первом же запуске, а не на устройстве пользователя. Цена риска
оказалась не той, какой выглядела, а приставка стоила бы токена в лексере, вида
узла и абзаца в грамматике.

Остаётся узкий хвост: макет, уже уехавший на бэкенд со старым именем, после
переименования на хосте начнёт разрешаться в билтин. Это ровно та же проблема,
что при любом переименовании хост-функции, и она у потребителя есть независимо
от этой работы.

## 8. Порядок использования

```
регистрация функций → постановка корней → компиляция → вычисления
```

Тот же порядок, что у данных, и по той же причине: `check` сверяет имена ровно
в момент своего вызова и полагается, что состав имён после этого не меняется
(`docs/backlog.md` B23).

Для функций порядок **обеспечивается**: контекст держит признак «уже
компилировали», и `chupa_register` после первой компиляции отвергается. Правило
жёстче необходимого — хватило бы «до компиляции того, кто зовёт», — и жёстче
намеренно: одна точка, после которой состав имён неизменен, проверяется одним
сравнением и не требует от хоста помнить, что он уже скомпилировал. B23 для
корней остаётся открытым.

Реестр только пополняется. Снятия и переопределения нет: скомпилированная
единица разрешила имя раз и навсегда, и снятие сделало бы её негодной без
всякого признака этого в ней самой.

### 8.1 Отказы регистрации

`chupa_register` возвращает `false` и ставит ошибку контекста, если:

| причина | код |
|---|---|
| `name` не идентификатор по `docs/grammar.md` §4.4 либо зарезервированное слово | `CHUPA_ERR_NAME` |
| имя занято билтином | `CHUPA_ERR_NAME` |
| имя уже зарегистрировано | `CHUPA_ERR_NAME` |
| `call == NULL` | `CHUPA_ERR_USAGE` |
| `min_args > max_args` | `CHUPA_ERR_USAGE` |
| `CHUPA_FN_DETERMINISTIC` без `CHUPA_FN_PURE` | `CHUPA_ERR_USAGE` |
| контекст уже что-то компилировал | `CHUPA_ERR_USAGE` |
| вызвана изнутри коллбэка | `CHUPA_ERR_USAGE` |

Каждый отказ сопровождается утверждением в отладочной сборке. Возврат `bool`
остаётся настоящим контрактом: в релизе утверждения выключены.

## 9. Что хост-функция вправе делать

**Контекст закрыт.** На нём заводится признак «идёт вычисление»: ставится в
`Context::eval` и `Context::run`, снимается на выходе, в том числе по ошибке.
При поднятом признаке разрешены только `chupa_make_string`, `chupa_fail` и
чтение ошибки; `chupa_context_set_*`, `chupa_run`, `chupa_eval*`,
`chupa_compile_*`, `chupa_register` отказывают с `CHUPA_ERR_USAGE`.

Чтение самих значений — `chupa_value_kind`, `chupa_array_at`,
`chupa_object_get` и прочие — контекста не касается вовсе и потому не
ограничено ничем.

Вложенность считать не нужно: повторный вход как раз запрещён, а признак
булев.

Почему запрет, а не выборочные стражи, как в спеке 14.08. Во-первых,
`chupa_eval` изнутри коллбэка открывает неограниченную рекурсию через
C-границу, если вложенное выражение зовёт ту же функцию. Во-вторых, всякая
запись на контексте — это граница операции (`Context::setGlobal`), а она
сливает список отложенного освобождения, который прямо сейчас удерживает
значения идущего вычисления; это дефект семейства Б1, и в переработке модели
памяти он всплывал дважды. Перечислять, что именно опасно, значит поддерживать
этот список верным вечно; запретить всё — значит не поддерживать ничего.

Страж работает в релизе, а не только под `assert`: цена — сравнение целого на
входе публичной функции, а без него ошибка хоста проявляется порчей памяти на
чужом устройстве.

**Этим закрывается B34** — «чужой код посреди вычисления двигает пулы» — не
аккуратностью каждого места, а устройством: писать в контекст изнутри вызова
нечем. Верно это для C-слоя: страж стоит на каждой двери `c_api.cpp` и
работает в релизе.

**C++-слой закрыт не так, и разницу надо знать.** Хост вправе регистрировать
функции прямо через `CS::Context::registerFunction`, минуя C API (так делает
`cli/echo.cpp`), и тогда коллбэк может получить `CS::Context *` через
`user_data`. Двери `CS::Context` признак `evaluating_` тоже спрашивают, но
отвечают тем, что позволяет сигнатура: `setVariableText` — `false` с
диагностикой, `compileExpression` и `compileScript` — ненулевым числом ошибок
с диагностикой, и всё это в релизе; `setGlobal` и `setGlobalString`
возвращают `void`, и им остаётся `assert`, то есть только отладочная сборка.
Менять сигнатуры двух `void`-методов ради этого пути не стали: они тронули бы
всех своих вызывающих. Про остаток — `docs/backlog.md` B34.

**Остаётся контрактом,** непроверяемым движком: коллбэк не бросает исключение
через C-границу; хост не хранит `args[i]` дольше вызова, не удержав их.

## 10. Ошибки и диагностика

Три места, у каждого свой адресат.

**Регистрация** — таблица в §8.1. Адресат: разработчик хоста, на своей машине.

**Компиляция.** Неизвестное имя и неверная арность дают ровно то же, что
сегодня дают билтины — код и текст общие, потому что и проверка общая.
Добавляется одна диагностика: вызов функции без `CHUPA_FN_PURE` в дереве,
скомпилированном как выражение, `ErrorCode::Usage` (обоснование кода — §6).
Адресат: автор макета, до первой отрисовки.

**Выполнение.** Коллбэк вернул `false`. Код — тот, что задан через
`chupa_fail`, либо `CHUPA_ERR_HOST`, если `chupa_fail` не звался. Смещение —
позиция вызова в исходнике. Сообщение — скопированное из `chupa_fail` либо
`"host function failed"`.

### 10.1 Следствие для контракта `ChupaError.message`

Сегодня заголовок обещает: сообщение — «строковый литерал времени жизни
процесса, никогда не выделяется, поэтому переживает даже сам ctx».
`chupa_fail` это обещание нарушает: байты копируются в буфер контекста.

Обещание ослабляется до **«действительно до следующего вызова на этом
контексте»** — то же правило, что у всякого заимствованного значения. Для
сообщений самого движка при этом ничего не меняется: они как были литералами,
так и остаются, просто на это больше нельзя опираться.

Формулировка не новая: заголовок уже говорит «stay valid until the next call on
ctx» про заимствованные байты (правило 1 в применении к строке). То есть
сообщение переходит из исключения в общее правило заголовка, а не заводит
третий вид времени жизни.

Альтернатива — заставить хост подавать литерал времени жизни процесса —
рассмотрена и отвергнута. Для Swift она естественна, но для JNI источник
сообщения это текст брошенного `Throwable`, живущий в `jstring`; хост-функция
на Kotlin потеряла бы диагностику целиком и подставляла бы одну статическую
строку на все случаи. Копия на пути отказа не стоит ничего: отказы редки.

Буфер под сообщение — **отдельное поле контекста**, а не что-либо, откуда
читают аргументы. Само по себе это уже не критично, раз пулов нет, но правило
записывается явно, чтобы не восстанавливать его заново при следующей правке.

### 10.2 Проверка типов аргументов остаётся на хосте

Движок арность сверяет, а виды аргументов — нет: как и у билтинов, которые
проверяют свои типы сами в момент вычисления.

Рассмотренный вариант — маска допустимых видов на аргумент в дескрипторе,
чтобы движок отказывал до вызова и сам собирал сообщение. Отвергнут на этом
этапе: он заводит второй идиом рядом с билтинами, добавляет времени жизни
массиву масок и покупает главным образом то, что каждая обвязка иначе напишет
сама. Довод «Swift не сможет предложить типизированные замыкания» оказался
неверным — обвязка вправе проверить виды в трамплине сама, и прикладной код
`ChupaValue` всё равно не увидит.

К вопросу стоит вернуться, когда появится **вторая** обвязка: тогда
дублирование проверки станет фактом, а не предсказанием, а на JNI отказ до
пересечения границы экономит апколл целиком. Отложить дёшево: под собирается из
исходников, ABI никто не замораживал, поле в дескриптор добавляется без
последствий для потребителей.

## 11. Устройство в ядре

### 11.1 Новый модуль

`core/src/host.hpp` / `host.cpp` — по образцу `builtin.hpp`: таблица, поиск,
применение. Включает публичный заголовок: `ChupaHostFunction` и `ChupaFunction`
— типы границы по определению, и заводить в ядре их параллельные копии значило
бы держать две правды об одном.

### 11.2 Таблица

Живёт в `Context`, той же длительности жизни:

```cpp
struct HostFunction {
    std::string       name;
    std::uint8_t      minArgs;
    std::uint8_t      maxArgs;
    std::uint32_t     flags;
    ChupaHostFunction call;
    void             *userData;
    void            (*release)(void *);
};
std::vector<HostFunction> hosts_;
```

`~Context` проходит по таблице и зовёт каждый непустой `release` ровно один
раз. Порядок относительно освобождения значений контекста безразличен: коробки
считают ссылки сами и от контекста не зависят.

### 11.3 Резолв — одна функция на двух потребителей

```cpp
enum class CalleeKind : std::uint8_t { Unknown, Builtin, Host };

struct Callee {
    CalleeKind        kind;
    Builtin           builtin;   // при kind == Builtin
    ChupaHostFunction call;      // при kind == Host
    void             *userData;  // при kind == Host
    std::uint8_t      minArgs, maxArgs;
    bool              returnsValue;
    bool              pure;
};

Callee resolveCallee(const Context &ctx, std::string_view name) noexcept;
```

Иначе `check.cpp` и `eval.cpp` обрастут каждый своей парой веток «билтин или
хост», и правило «что считается вызовом» размажется по двум файлам.

Коллбэк лежит в `Callee` целиком, а не индексом в `hosts_`: структура
самодостаточна, второго обращения к таблице нет и вопрос «не устарел ли индекс»
не возникает.

`deterministic` в `Callee` не попадает: ни `check`, ни `eval` его не читают.
Хранится он в `HostFunction` и `BuiltinInfo`, откуда его возьмёт кэш props,
когда появится.

Билтины ищутся первыми; коллизия имён невозможна, её отсекает
`chupa_register`.

### 11.4 Статический проход

`checkCall` перестаёт звать `findBuiltin`/`builtinInfo` и зовёт
`resolveCallee`. `Unknown` даёт прежнее `unknown function`, сверка арности идёт
по тем же полям, требования к использованию результата не меняются.

`check` начинает знать режим: `compileExpression` передаёт «выражение»,
`compileScript` — «скрипт». Сегодня он его не знает, и без этого правило
«грязные только в скриптах» проверить негде.

### 11.5 Узел и вычисление

Узел — тот же `NodeKind::Call`. Сегодня он несёт значение перечисления
`Builtin`; станет нести число с признаком в старшем бите: свой билтин либо
номер в таблице контекста. Парсер не трогается: он о функциях ничего не знает,
имя перед скобкой для него обычный идентификатор.

Аргументы вычисляются слева направо. Буфер `Value args[kMaxFixedArgs]`
(`kMaxFixedArgs == 2`) для хост-функций не годится, а вариадичность исключает и
любой фиксированный потолок. Значит `Execution` заводит **стек аргументов** —
`std::vector<Value>`, где каждый вызов занимает отрезок и освобождает его на
выходе.

Почему стек, а не один буфер: аргумент внешнего вызова сам может содержать
вызов, и вложенный занял бы тот же буфер до того, как внешний собрал свои
аргументы. Указатель на отрезок берётся **после** того, как все аргументы
внешнего вызова уложены, а во время самого коллбэка вектор вырасти не может —
контекст закрыт и вычислять изнутри нечего. Поэтому `data() + base`
действителен на всё время вызова.

Проверки чистоты в `eval` нет: дереву доверяем (`docs/backlog.md` B31).

## 12. Обвязка Swift

```swift
public struct FunctionFlags: OptionSet {
    public let rawValue: UInt32
    public static let returnsValue  = FunctionFlags(rawValue: 1 << 0)
    public static let pure          = FunctionFlags(rawValue: 1 << 1)
    public static let deterministic = FunctionFlags(rawValue: 1 << 2)
}

extension Context {
    public func register<A: CSValue, B: CSValue, R: CSValue>(
        _ name: String,
        flags: FunctionFlags = [.returnsValue, .pure, .deterministic],
        _ body: @escaping (A, B) throws -> R
    ) throws
}
```

Перегрузок по одной на арность от нуля до четырёх плюс сырая
`([Value]) throws -> Value?` для вариадичных и агрегатных случаев. Умолчание
флагов — чистая, детерминированная, со значением: самый частый случай, а
грязную придётся объявить явно. В C ноль означает обратное, и это не
рассогласование: в C ноль получается у того, кто поле не заполнил, а в Swift
умолчание пишет автор обвязки осознанно.

Виды аргументов проверяет трамплин (§10.2): `guard let a = A(args[0]) else`.
Прикладной код `ChupaValue` не видит.

**Бокс и `user_data`.** Замыкание в `@convention(c)`-указатель не
превращается. Обвязка кладёт `body` в класс-коробку, передаёт
`Unmanaged.passRetained(box).toOpaque()` в `user_data`, а в `release` —
функцию, снимающую удержание. Массив боксов в `Context` при этом не нужен:
владение выражено самим дескриптором, а не тем, что кто-то не забыл сложить
бокс в поле.

**Ошибка.** `body` бросает — трамплин ловит, зовёт `chupa_fail` с кодом и
текстом и возвращает `false`. Текст динамический и доезжает до хоста целиком,
потому что `chupa_fail` копирует байты (§10.1). Ловить надо `Swift.Error`:
`Error` внутри модуля — наш собственный тип. Публичный почленный инициализатор
`Error` нужен, чтобы прикладной код мог бросить свою.

**Известная цена.** Строковый аргумент, развёрнутый в `String`, копирует байты
на каждом вызове — для чистой функции в props это на каждый кадр. Величина
известна: прогон харнесса OKBDUI от 2026-08-20 даёт 19 нс на двенадцати байтах
и 70–77 нс на пяти с половиной сотнях, причём сам движок с C-границей отдаёт
длинную строку за 15 нс, то есть материализация — это четыре пятых цены. Нулевое
копирование выразимо, но делает API неудобным; решение — начать с копии и
вернуться по замерам.

> Прогон в репозиторий пока не положен: `docs/benchmarks/` содержит замеры по
> 18 августа включительно. Цифры выше стоит закоммитить туда же перед началом
> работы, иначе ссылаться в реализации будет не на что.

## 15. Открытые вопросы

Не решаются этой работой и решения для неё не требуют:

- **Возврат агрегатов** — нужен строитель в C API и доступ к таблице ключей.
- **Маски видов аргументов** — вернуться при второй обвязке (§10.2).
- **JNI и Kotlin.** Android заявлен как требование к релизу. Форма API к нему
  готова: `user_data` ложится на глобальную ссылку, `release` — на её удаление,
  `chupa_fail` принимает текст `Throwable`. Открыто остальное: где кэшируется
  `JavaVM *`, кто ставит рамку локальных ссылок вокруг вызова, что делать с
  вычислением вне присоединённого потока, и во сколько обходится апколл — на
  Android он сопоставим по цене со всем выражением, а не пренебрежим.
- **B38 (UAF-2)** — слушатель перерисовки по-прежнему не знает, когда умирает
  его `user_data`. Эта работа заводит второе место с `user_data`, но своё
  закрывает `release`; слушатель остаётся как был.
- **Кэш значений props** — B29; `deterministic` заведён под него.
