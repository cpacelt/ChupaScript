# Параметры выражения

**Дата:** 2026-08-21
**Статус:** проектирование, разделы 1–4 — механизм описан целиком

Хост порождает вьюшки по элементам массива: один разобранный прототип,
сколько-то детей, у каждого свой элемент. Выражения в пропсах ребёнка
должны добраться до **своего** элемента, не зная при этом, из какой
переменной он взят, — иначе прототип годен для одного места макета и
переиспользовать его нельзя.

Этот документ описывает то, что для этого нужно от движка. Раздел 1 —
понятие параметра и его объявление, раздел 2 — передача значений, раздел 3 —
зависимости, раздел 4 — диагностика.

---

## 1. Параметр выражения

### 1.1 Что это

**Параметр** — имя, объявленное при компиляции конкретного выражения, у
которого нет ячейки. Значение поставляется на каждое вычисление и между
вычислениями не хранится. Принадлежит параметр самому скомпилированному
выражению, а не контексту.

Отличие от глобального имени — **не в видимости, а в наличии хранилища**:

| | глобальное имя | параметр |
|---|---|---|
| ячейка в `Store` | есть | нет |
| значение между вычислениями | хранится | не существует |
| кто видит | все выражения контекста | одно выражение |
| откуда берётся значение | из ячейки | приходит с вызовом |
| можно ли присвоить самому имени | да | нет |

Слово «область видимости» здесь не употребляется намеренно. Область
предполагает участок текста, внутри которого имя видно, а снаружи нет; в
языке участков нет — ни блоков, ни объявлений, ни вложенности (программа
это одно выражение либо плоский список операторов, `docs/grammar.md` §5).
Вводить область ради одного случая значило бы завести понятие, которому в
языке не на что опереться. Параметр опирается на существующее: имя,
разрешаемое на компиляции.

### 1.2 Отношение к §7.1 семантики

`docs/semantics.md` §7.1 говорит: объявлений в языке нет, всякий
идентификатор — чтение из контекста, предоставленного хостом, и состав
контекста программа изменить не может.

Параметр этого не нарушает и не расширяет. Он **тоже** предоставлен хостом
и **тоже** не может быть заведён программой; разница лишь в том, что хост
предоставляет его на вызов, а не на всё время жизни контекста. Программа
по-прежнему не в силах создать имя: и глобальное, и параметр приходят
снаружи.

Формулировка §7.1 дополняется одним предложением: имя разрешается либо в
глобальную переменную контекста, либо в параметр выражения, объявленный при
его компиляции.

### 1.3 Объявление

Параметры объявляются **при компиляции**, списком имён, и порядок этого
списка значим: значения на вычислении передаются позиционно, по нему.

Позиционно, а не по имени, потому что имена уже разрешены — на компиляции,
там же, где разрешаются глобальные. Сопоставлять строки заново на каждом
вычислении означало бы делать работу, результат которой уже есть.

Требования к имени — те же, что у глобального (`chupa_context_set_*`): это
идентификатор и не зарезервированное слово. Иначе на него нельзя было бы
сослаться.

### 1.4 Столкновение с глобальным именем — отказ

Если объявляемый параметр совпадает по имени с существующей глобальной
переменной, компиляция **отказывает** (`CHUPA_ERR_NAME`).

Затенение решало бы за автора макета, какое из двух имён он имел в виду, и
решало бы молча. Отказ ставит вопрос там, где на него есть кому ответить:
имя параметра выбирает хост, и переименовать его дешевле, чем искать
причину, по которой кнопка показывает не свой счётчик.

Обратный случай — глобальная переменная с этим именем появилась **после**
компиляции — уже скомпилированного выражения не касается: имена в нём
разрешены, и разрешены они в параметр. Новая компиляция с тем же именем
параметра откажет.

### 1.5 Ссылка на необъявленный параметр — отказ

Выражение, помянувшее имя, которого нет ни среди глобальных, ни среди его
параметров, не компилируется. Это не новое правило, а то же самое, что для
неизвестного глобального имени: разрешение имён целиком происходит на
компиляции, и рантайму эта ошибка не достаётся.

Следствие, ради которого правило и держится: прототип, скомпилированный без
параметров, сослаться на элемент не может **по построению**. Опечатка в
имени параметра — отказ сборки, а не пустое место на экране, замеченное
через неделю тем, кто смотрит на экран, а не тем, кто правит макет.

### 1.6 Присваивание

Цель присваивания — ячейка либо путь внутри контекста (§7.2). Параметр не
ячейка, поэтому:

```
item = x;          // ошибка компиляции: писать некуда
item.count += 1;   // законно
```

Это одно правило, а не два. Во второй строке цель — не параметр, а путь,
ведущий в агрегат, на который параметр указывает; агрегат при этом
настоящий, лежащий в контексте, и запись меняет именно его.

Из чего следует главное свойство для порождающего контейнера: элемент,
переданный параметром, и элемент, лежащий в массиве, — **одно значение, а
не копия**. `Value` агрегата это box со счётчиком ссылок (`core/src/box.hpp`,
`core/src/store.hpp`), и передача параметром берёт ссылку, а не содержимое.
Поэтому запись сквозь параметр видна в массиве, эпоха массива двигается
обычным порядком, и колбэк перерисовки приходит без участия хоста.

Отказ по 1.6 — на компиляции: то, что цель является параметром, известно
там же, где имя разрешается.

### 1.7 Чего параметр не делает

- **Не меняет состав контекста.** `Store` о параметрах не знает; ни
  `chupa_context_set_*`, ни скрипт не могут ни создать параметр, ни увидеть
  его.
- **Не переживает вычисление.** Между двумя вычислениями значения у
  параметра нет; спрашивать «какое сейчас» не у кого.
- **Не вводит вложенности.** Прототип внутри прототипа объявляет свои
  параметры и получает свои значения; стека имён в движке не заводится.

## 2. Передача значений

### 2.1 Двери

Компиляция принимает имена, вычисление — значения. Обе двери — варианты
существующих, а не замена им: выражение без параметров компилируется и
вычисляется как прежде.

```c
/* Имя параметра. Байты не копируются: они нужны только на время
 * компиляции, где имя и разрешается. */
typedef struct ChupaName {
    const char *bytes;
    size_t      len;
} ChupaName;

CHUPA_API ChupaExpression *CHUPA_NULLABLE
chupa_compile_expression_with_params(ChupaContext *ctx,
                                     const char *source, size_t len,
                                     const ChupaName *params, size_t count);

CHUPA_API CHUPA_MUST_USE bool
chupa_eval_with_params(ChupaContext *ctx, ChupaExpression *e,
                       const ChupaValue *values, size_t count,
                       ChupaValue *out);

CHUPA_API CHUPA_MUST_USE bool
chupa_expression_eval_tracked_with_params(ChupaContext *ctx, ChupaExpression *e,
                                          const ChupaValue *values, size_t count,
                                          ChupaValue *out,
                                          ChupaDep deps[CHUPA_NONNULL CHUPA_MAX_DEPS],
                                          uint32_t *n);
```

Отслеживающая дверь нужна наравне с обычной, а не «когда-нибудь потом»:
порождённые дети — это большинство выражений на экране списка, и оставить их
вне кэша по эпохам значило бы завести механизм, мимо которого проходит его
основной случай.

### 2.2 Позиционность

Значения передаются в порядке объявления имён. Соответствие имени и значения
движок не проверяет и проверить не может: на вычислении имён уже нет, они
разрешены на компиляции.

Опасность здесь настоящая — перепутанный порядок даёт не отказ, а неверное
значение. Принимается она по одной причине: оба списка строит одно и то же
место хоста, порождающее детей, и построить их врозь оно не может. Разносить
эти два списка по разным местам — ошибка проектирования на стороне хоста, и
движок от неё защитить не в силах.

Плата за проверку была бы постоянной — сравнение строк на каждом вычислении
каждого пропса каждого кадра, — а защищала бы она от ошибки, которая
допускается один раз и видна сразу.

### 2.3 Несовпадение числа значений — отказ

Число переданных значений обязано **равняться** числу объявленных имён.
Меньше, больше — `false` и `CHUPA_ERR_USAGE`, вычисление не начинается.

Это ошибка хоста, а не данных, — отсюда `USAGE`, а не `TYPE` или `RANGE`.
Недостача не добирается `null`: выражение посчиталось бы и вернуло пустоту,
которую на экране не отличить от пустых данных. Излишек не отбрасывается:
он означает, что хост перепутал, какое выражение вычисляет, и молчаливо
согласиться с этим значит дать ошибке дожить до продакшена.

Два вырожденных случая — того же рода:

- выражение **с** параметрами, вычисленное через `chupa_eval` — `USAGE`:
  значений нет там, где они обязаны быть;
- выражение **без** параметров через `chupa_eval_with_params` при `count == 0`
  — законно и равносильно `chupa_eval`. Это позволяет хосту звать одну дверь
  всегда, не ветвясь на «есть ли у этого выражения параметры».

### 2.4 Время жизни значений

Переданные значения **заимствованы на время вызова** — правило 2 заголовка,
то же, что у аргументов функции хоста. Движок не берёт на них ссылку и не
продлевает им жизнь; держать их живыми на время вызова обязан хост.

Для порождающего контейнера это выполняется само: элемент он держит
`chupa_value_retain` всё время, пока жив ребёнок, — то есть заведомо дольше
одного вычисления.

Значение, вернувшееся в `out`, заимствовано по обычному правилу 1 и живёт до
следующего вызова на контексте, как у `chupa_eval`.

### 2.5 Какими бывают значения

Любого рода, включая скаляр и `null`. Ограничений движок не ставит, и
последствия обычные:

```
item.count           // item — число: ошибка Type на вычислении (§6.1)
item.count           // item — null: null, по мягкости чтения (§6.3)
item.count += 1      // item — не агрегат: ошибка Type, писать некуда
```

То есть массив скаляров источником для порождения годится, но элемент в нём
доступен только целиком: `item` прочитать можно, `item.x` — нет, записать
сквозь него — нет. Это не отдельное правило, а следствие уже существующих.

### 2.6 Вызов изнутри колбэка

Обе двери закрыты во время вызова функции хоста, наравне со всеми прочими:
из колбэка на контексте разрешены только `chupa_make_string`, `chupa_fail` и
чтение ошибки. Прочее — `CHUPA_ERR_USAGE`.

Отслеживающая дверь при отказе заполняет `deps` целиком тем же, чем при
переполнении, и ставит `CHUPA_DEPS_OVERFLOW` в `*n` — как это уже описано у
`chupa_expression_eval_tracked`.

## 3. Зависимости

### 3.1 Параметр — обычный участник набора

Значение параметра — агрегат, лежащий в контексте, и читается оно как всякое
другое. Специального правила ему не нужно: `chupa_expression_eval_tracked_with_params`
записывает эпоху прочитанной коробки в `ChupaDep` наравне с ячейками
глобальных переменных.

Отличие одно, и оно в поле `owner`. У глобальной переменной коробки нет —
эпоха её ячейки живёт столько же, сколько контекст, — и `owner` приходит
`CHUPA_KIND_NULL`. У параметра `owner` — сама коробка элемента, и держать её
обязательно.

### 3.2 Кто держит `owner`

Правило заголовка не меняется: `chupa_value_retain` при захвате набора,
`chupa_value_release` при следующем захвате.

Соблазн сэкономить здесь есть: порождающий контейнер и так держит элемент
удержанным всё время жизни ребёнка, то есть коробка заведомо жива. Экономия
отвергается — два держателя независимы. Ребёнку могут дать другой элемент
(§3.5), и тогда удержание «ради ребёнка» отпустится, а набор зависимостей,
захваченный прежде, останется смотреть на отпущенную коробку. Цикл
retain/release у набора обязан быть свой, замкнутый на сам набор.

### 3.3 Два уровня наблюдения

Контейнер и ребёнок следят за **разными** коробками, и это не соглашение, а
устройство: эпохи не всплывают вверх по дереву (`docs/backlog.md` B69,
замер на `state.items[0].id = 99`).

| что изменилось | двигается эпоха | кто должен узнать |
|---|---|---|
| `push`, `pop`, `items[0] = y` | коробки массива | контейнер: состав детей |
| `items[0].count += 1` | коробки элемента | ребёнок: своё содержимое |

Из чего следует ровно то поведение, которого мы хотим:

- тап по кнопке реакции двигает эпоху **своего** элемента — просыпается одна
  кнопка, соседние не знают об этом ничего;
- появление новой реакции двигает эпоху массива — просыпается контейнер,
  добавляет ребёнка, а уже существующие кнопки не пересчитываются.

### 3.4 Откуда контейнер берёт эпоху массива

Обычной дверью — не берёт. Его выражение `data` даёт агрегат, а по §2.8
спеки кэша результат-агрегат отравляет набор: `*n` приходит
`CHUPA_DEPS_OVERFLOW`, адреса — `NULL`.

Контейнер берёт эпоху коробки **по ручке** — вариант, выбранный в B69:

```c
CHUPA_API const ChupaEpoch *chupa_value_epoch(const ChupaValue *v);
```

Это не обход §2.8. Правило §2.8 отвечает на вопрос «годится ли значение,
которое я уже держу», и для агрегата ответ честно отрицательный: за
содержимое движок не ручается. Вопрос контейнера другой — «двигалось ли то,
от чего я завишу», — и на него ответ есть.

Время жизни адреса — то же, что у `epoch` в `ChupaDep`: он указывает внутрь
коробки, и коробку надо держать удержанной, пока адрес используется.

### 3.5 Смена элемента под ребёнком

Единственное место, где элемент у ребёнка меняется, — правка состава массива:
после удаления из середины (`docs/backlog.md` B70) индексы сдвигаются, и
ребёнок, стоявший на месте `i`, получает другую коробку.

Порядок при этом обязателен и прост: контейнер отдаёт ребёнку новый элемент,
ребёнок отпускает старый набор зависимостей и захватывает новый на ближайшем
вычислении. Пока набор не перезахвачен, он смотрит на прежнюю коробку — и
это безопасно ровно потому, что удержан ею же (§3.2): коробка жива, эпоха
читается, ответ «менялось» приводит к вычислению, которое набор и обновит.

Ошибиться этот порядок может только в сторону лишнего вычисления, никогда —
в сторону пропущенного.

### 3.6 Потолок

Выражения прототипа коротки, и в четвёрку укладываются с запасом:

```
item.count                  1 зависимость  — коробка элемента
item.key == selected        2              — коробка элемента и ячейка глобальной
```

Специальных правил для параметров нет: переполнение обрабатывается как
всегда — `CHUPA_DEPS_OVERFLOW`, выражение не кэшируется и перерисовывается
безусловно.

Остаётся и общее ограничение §2.8: пропс, дающий агрегат (`item.tokens`),
набор отравляет и отслеживаться не будет. Для параметров это не новый
случай — то же самое верно для любого выражения с таким результатом.

## 4. Диагностика

### 4.1 Два вида отказа

Отказы делятся не по важности, а по тому, **есть ли у них место в тексте**.

**Отказ двери** — ошибся хост в вызове: имя не идентификатор, имена
повторились, число значений не сошлось. В исходнике выражения такой ошибки
нет, и `offset` приходит `0`. Так уже устроены отказы регистрации функции и
простановки переменной (`core/src/c_api.cpp`).

**Отказ проверки** — ошибка в тексте: помянуто имя, которого нет; присваивание
в параметр. `offset` указывает на узел, как у всякой ошибки прохода `check`.

Смешивать их нельзя: хост, показывающий стрелку в исходник по `offset == 0`,
покажет её на первый байт и соврёт.

### 4.2 Таблица

| случай | код | сообщение | `offset` |
|---|---|---|---|
| имя параметра не идентификатор либо зарезервировано (§1.3) | `Name` | `parameter name must be an identifier, not a reserved word` | 0 |
| имя параметра занято глобальной переменной (§1.4) | `Name` | `a global variable already has this name` | 0 |
| имя повторяется в списке параметров (§1.4) | `Name` | `duplicate parameter name` | 0 |
| помянуто имя, которого нет ни в глобальных, ни в параметрах (§1.5) | `Name` | `unknown name` | узел |
| присваивание в само имя параметра (§1.6) | `Name` | `cannot assign to a parameter` | узел цели |
| число значений не равно числу имён (§2.3) | `Usage` | `parameter count does not match the compiled expression` | 0 |
| выражение с параметрами вычислено через `chupa_eval` (§2.3) | `Usage` | `this expression requires parameters` | 0 |
| вызов изнутри колбэка (§2.6) | `Usage` | `the context is closed while a host function is running` | 0 |

Последняя строка — существующее сообщение, новых дверей оно касается наравне
со всеми прочими и не переписывается.

### 4.3 `unknown name` не расщепляется

Соблазн выдать «это параметр, но он здесь не объявлен» отвергается: чтобы
такое сказать, движку нужно знать, что это имя где-то бывает параметром, — а
он не знает и знать не может. Имя, не объявленное этому выражению, ему просто
неизвестно, и честный ответ ровно такой.

Практический случай, ради которого правило стоит помнить: шаблон, поминающий
`item`, применён вне прототипа. Диагностика скажет `unknown name` с указанием
на `item` — то есть назовёт имя и место, а понять, что элемента здесь нет,
предстоит человеку. Это дешевле, чем механизм, угадывающий намерение.

### 4.4 Имени в сообщении нет

Сообщения движка — литералы, без сборки текста (заголовок, примечание к
`chupa_context_error`). Поэтому «имя занято» не говорит, **какое**.

Дополнить обязан хост, и ему это ничего не стоит: список имён он же и
передал. Правило для обвязки простое — отказ двери пересказывается вместе с
тем, что было передано, а не пересылается как есть. Иначе разработчик макета
получит «duplicate parameter name» без единой зацепки, хотя зацепка была у
вызывающего в руках.

### 4.5 Чего не проверяется

**Порядок значений.** Значения позиционны (§2.2), соответствие имени и
значения не проверяется и проверяться не будет: на вычислении имён уже нет.
Перепутанный порядок даёт неверное значение, а не отказ. Это записано здесь
второй раз намеренно — раздел про диагностику обязан честно называть то, чего
диагностика не ловит.

**Вид значения.** Скаляр, `null`, агрегат — принимается любое (§2.5).
Последствия наступают на чтении обычными ошибками `Type` и мягкостью §6.3, и
отдельного отказа при передаче нет.

## Без чего механизм не закрывает свою задачу

Параметр даёт ребёнку его элемент — и на этом останавливается. Двух вещей
рядом с ним недостаёт, и обе не косметические: без первой контейнер не может
быть чистой функцией от данных, без второй список делает экран медленнее, а
не быстрее. Держать их отдельным «потом» — значит выпустить механизм, который
не решает задачу, ради которой заводился.

**1. Удаление элемента из массива** — `docs/backlog.md` B70.

Состав детей есть функция от массива: элемент исчез — вьюшка исчезла. Но
убрать элемент из середины нечем, `pop` снимает только с конца. Основной
случай панели реакций — снятая реакция должна убрать кнопку — сегодня не
выражается. Обходные пути растаскивают решение: прятать нули средствами
контейнера значит отнять у состава детей свойство быть функцией от данных;
пересобирать массив нативно значит отнять у макета право менять данные, ради
которого всё и делалось.

**2. Адресное пробуждение вьюх** — частью `docs/backlog.md` B69, частью на
стороне хоста.

В движке механизм есть: `chupa_expression_eval_tracked` отдаёт зависимости
адресами эпох. К вьюхам он не подключён — хост будит всякий виджет на всякое
изменение любой переменной. Порождающий контейнер увеличивает число виджетов
на экране кратно длине массива, то есть **усугубляет** это, а не смягчает:
один тап по реакции пересчитывает всю ленту.

Порядок между ними: удаление — предпосылка правильности, пробуждение —
предпосылка скорости. Первое обязано быть готово к первому же экрану со
списком; второе — к первому такому экрану в ленте.
