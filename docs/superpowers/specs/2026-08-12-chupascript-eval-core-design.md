# ChupaScript: вычислитель, часть 1 — ядро и доступ к данным

Дата: 2026-08-12
Статус: принято

## 1. Область документа

Вычислитель разбит на три части. Документ описывает первую.

| Часть | Что входит | Главы семантики |
|---|---|---|
| **1. Ядро и доступ к данным** | драйвер, литералы, имена, `.` и `[]`, приведение к строке, ошибки выполнения | 3, 4, 6, 9.2 |
| 2. Операторы | унарные, арифметика, порядок, равенство, логические, `??`, тернарный | 5 |
| 3. Стейтменты и встроенные | присваивание, режим скрипта, тринадцать функций, статические проверки | 7, 8 |

Порядок вынужденный: части 2 не на чем проверяться без части 1, часть 3 изменяет
то, что часть 1 умеет читать.

Часть 1 не содержит **ни одного оператора**, включая `??`, и ни одного вызова.
После неё работают `user.profile.avatar`, `state.items[0]`, `obj[k]` с любым
скалярным ключом и агрегатные литералы.

Не входит: устройство хранилища
(`2026-08-11-chupascript-values-design.md`), наполнение контекста данными
(`2026-08-11-chupascript-data-design.md`), состав заголовка C API.

## 3. Форма вычисления

```cpp
// core/src/eval.hpp
namespace CS {

/// Вычисляет разобранное выражение и кладёт результат в *out.
///
/// Дерево обязано быть построено parseExpression **успешно**: у неудачного
/// разбора корень равен kNoNode, и вычислять там нечего. Буфер исходника обязан
/// пережить вычисление: имена и содержимое литералов в дереве — его срезы.
///
/// При отказе возвращает false и заполняет diag; смещение считается от начала
/// исходника выражения.
bool evalExpression(const Ast &ast, Context &ctx, Value *out, Diagnostic &diag);

}  // namespace CS
```

Внутри — рекурсивный `eval(const Ast &, NodeId, Context &, Value *, Diagnostic &)`,
спускающийся по узлам.

**Почему рекурсия, а не цикл.** Узлы лежат плоско и, больше того, в порядке
пост-обхода: парсер строит узел только после его детей, поэтому индекс ребёнка
всегда меньше индекса родителя, а поддерево занимает непрерывный отрезок
индексов. Прямой цикл `for (NodeId n = 1; n <= root; ++n)` был бы корректным
обходом — но ломается о два обстоятельства.

Первое: **короткое замыкание требует не вычислять часть дерева**. `false && X`
обязано не трогать `X` (§5.5), тернарный вычисляет только выбранную ветвь
(§5.7), `??` — правый операнд только при `null` слева. Это не оптимизация: на
этом стоит идиома `count(arr) > 0 && arr[0] == 1`, где правая часть без защиты
слева даёт ошибку. Цикл, вычисляющий всё подряд, превратил бы корректные
программы в ошибочные. Обойти можно пропуском отрезка индексов, но для этого
узел должен знать, где начинается его поддерево, — сейчас он этого не хранит.

Второе: **циклу нужен буфер под промежуточные значения на всё дерево,
рекурсии — только на глубину**. Цикл держит значение каждого узла до момента,
когда его заберёт родитель: шестнадцать байт на узел. У рекурсии промежуточные
значения живут в кадрах. Для типичного выражения в props это разница между
тремя десятками слотов и пятью кадрами, и она в пользу рекурсии.

**Собственного предела глубины у вычислителя нет.** Глубина обхода равна высоте
дерева, а её ограничил парсер — но ограничил не тем, что ограничил свою
рекурсию: `kMaxDepth` считает именно высоту дерева. Звено постфиксной цепочки
(`.k`, `[i]`) разбирается циклом и глубины разбора не добавляет, однако уровень
дерева даёт, поэтому тратит ту же единицу бюджета, что и вложенность. Без этого
цепочка `a.b.b.b…` любой длины разбиралась бы успешно и роняла бы вычислитель:
50 000 звеньев переполняли стек.

Измеренные пределы (`docs/grammar.md` Приложение C.1): 31 уровень вложенности
скобок и агрегатов, 23 уровня вложенных индексов, 93 звена в цепочке `.` или
`??`, 90 в цепочке `[]`. Числа вычитаются из одного бюджета, а не складываются:
цепочка внутри `k` уровней скобок короче на `3k`. Худший случай — порядка сотни
кадров. Предел вычислителя унаследованный, а не свой, и это записано здесь,
чтобы потом не искать, где он.

Переход на цикл возможен позже **без изменения раскладки дерева** — потребуется
лишь индекс первого потомка у узла. Записано в `docs/backlog.md`.

## 4. Литералы

| Вид узла | Что делает |
|---|---|
| `Number` | `Value::number` |
| `Boolean` | `Value::boolean` |
| `Null` | `Value::null` |
| `String` | раскодирование экранирования, затем `Context::makeString` |
| `Array` | `makeArray(childCount)`, затем `arrayPush` по вычисленным элементам |
| `Object` | `makeObject(childCount / 2)`, затем `objectSet` по парам |

Отличие от материализации данных, ради которого обходы и разошлись: **элемент
агрегата — произвольное выражение**, а не литерал. Ключ объектного литерала при
этом остаётся строковым литералом, потому что так велит грамматика
(`ObjectEntry ::= StringLiteral ':' Expression`), и приведение §4 к нему не
применяется.

Ёмкость известна заранее из `Ast::childCount`, поэтому агрегат строится точным
выделением, без переездов.

**Каждое вычисление литерала создаёт новый агрегат** (`docs/semantics.md` §2.3).
Это следует из того, что `makeArray` зовётся при каждом обходе, и не требует
кода — но требует теста: два вычисления одного узла обязаны дать
`sameAggregate() == false`.

## 5. Имена

Идентификатор — чтение корня (`docs/semantics.md` §7.1): объявлений в языке нет,
всякий идентификатор есть обращение к контексту.

Корня нет — **ошибка** `Name`, а не `null`. Спека C API отличает опечатку в
корне от опечатки глубже: `usre.name` обязано быть ошибкой, `user.prfoile.avatar` —
молчаливым `null`. Первое ловится тем, что состав корней контексту известен;
второе не ловится ничем и является ценой §6.3.

Различить отсутствующий корень и корень со значением `null` позволяет
`Context::hasRoot` — ровно для этого он и заведён.

Позже проверка переедет на этап компиляции макета, где состав корней известен до
вычисления, и `usre.name` будет отвергнут при разборе экрана, а не при первом
показе. Здесь она выполняется в момент обхода: результат тот же, время — позже.

## 6. Доступ к данным

### 6.1 `base.k`

База вычисляется; имя берётся из узла буквально как строка — приведение к нему
не применяется (`docs/semantics.md` §6.2).

| База | Результат |
|---|---|
| `Object` | значение ключа либо `null`, если ключа нет |
| `Null` | `null` (§6.3) |
| прочее | ошибка `Type` (§6.4) |

### 6.2 `base[i]`

**База и индекс вычисляются оба, слева направо, даже если база `null`.** Порядок
вычисления зафиксирован (§3.3), а короткое замыкание есть только у `&&`, `||`,
`??` и тернарного. Это проверяемо: `null[неизвестныйКорень]` обязано дать ошибку
имени, а не `null`.

| База | Индекс | Результат |
|---|---|---|
| `Array` | конечное целое `Number` ≥ 0, меньше длины | элемент |
| `Array` | конечное целое `Number` ≥ 0, не меньше длины | `null` (§6.1) |
| `Array` | дробный, отрицательный, `NaN` либо бесконечность | ошибка `Range` |
| `Array` | не `Number` | ошибка `Type` — приведения к числу в языке нет |
| `Object` | скаляр | приводится к строке (§7), затем чтение ключа |
| `Object` | `Object` либо `Array` | ошибка `Type` |
| `Null` | любой | `null` (§6.3) |
| прочее | любой | ошибка `Type` (§6.4) |

Индекс за границей — штатное чтение, а не ошибка: данные с сервера неполны.
Дробный и отрицательный — ошибка логики автора, потому что означают намерение,
которого нет.

## 7. Приведение к строке

Единственное приведение в языке (`docs/semantics.md` §4), и в части 1 оно нужно
ровно в одном месте — ключ `obj[k]`.

| Тип | Результат |
|---|---|
| `String` | сама строка |
| `Boolean` | `true` либо `false` |
| `Null` | `null` |
| `Number` | §7.1 |
| `Object`, `Array` | ошибка `Type` |

Форма — срез плюс буфер под результат, а не создание строки в контексте: строка
нужна на время одного поиска ключа, и класть её в пул значило бы копить мусор на
каждом чтении.

### 7.1 Число в строку

Кратчайшее десятичное представление, читающееся обратно в то же значение
`double`.

Порядок правил:

1. `NaN` → `nan`; `+Infinity` → `inf`; `-Infinity` → `-inf`.
2. Ноль → `0` либо `-0` по знаку. Отдельно потому, что общее правило дало бы
   `0e+00`.
3. `1e-7 ≤ |x| < 1e21` → `std::to_chars` с `chars_format::fixed`.
4. Иначе → `std::to_chars` с `chars_format::scientific`.

Порог выбран так, чтобы удовлетворять всем примерам §4.3, включая границу:
`1000000` даёт `1000000`, а `1e21` даёт `1e+21`. Это та же граница, которую
выбрал JavaScript, и большинство бэкендов отдают числа, прошедшие через него.

За порогом запись — ровно то, что даёт `to_chars`, включая двузначный
показатель: `1e-8` становится `1e-08`, а не `1e-8`. Расхождение с JavaScript
сознательное: примеры §4.3 его не касаются, а лишнее правило форматирования не
окупается.

Буфер — 48 байт. Худшая фиксированная запись внутри порога занимает около
тридцати символов, худшая научная — двадцать четыре; запас взят, чтобы вопрос
не возвращался.

**Следствия, которые обязана учитывать реализация** (§4.3): `-0 == 0` истинно,
но `obj[-0]` и `obj[0]` — разные ключи; `obj[null]` и `obj['null']` — один
ключ; `obj[0.30000000000000004]` даёт ключ, который невозможно набрать вручную.

## 8. Ошибки

| Класс | Когда |
|---|---|
| `Name` | неизвестный корень |
| `Type` | доступ у неподходящего типа, нечисловой индекс массива, приведение агрегата к строке |
| `Range` | дробный, отрицательный, `NaN` либо бесконечный индекс массива |

Смещение — от узла, на котором вычисление остановилось. Первая ошибка выигрывает:
дальше обход не идёт, диагностика не переписывается.

Сообщения — по-английски, как в лексере, парсере и слое данных.

### 8.1 Виды узлов, которых часть 1 не знает

Парсер принимает `1 + 1` и `count(x)` — часть 1 их вычислить не может. Такой
узел даёт ошибку `Type` с сообщением `expression form is not supported`.

Эта ветка временная по составу и постоянная по существованию. С приходом частей
2 и 3 из неё уйдут операторы, вызовы и тернарный; останутся `Program`, `Assign`
и `CallStatement` — узлы, которых в дереве от `parseExpression` быть не может по
построению. То есть ветка выродится из «ещё не сделано» в защитную заглушку, и
удалять её не надо.

## 9. Общие листья

Раскодирование экранирования переезжает из `data.cpp` в отдельный файл: оно
нужно и слою данных, и вычислителю, и — в части 3 — билтинам `str` и `format`.
Туда же ложится представление числа.

```cpp
// core/src/text.hpp — преобразования текст ↔ значение
namespace CS {

/// Раскодирует экранирование строкового литерала в scratch.
/// Набор — из docs/grammar.md Приложение A: \\ \' \" \n \t.
std::string_view decodeEscapes(std::string_view raw, std::string &scratch);

/// Содержимое строкового литерала: срез исходника, если экранирования нет,
/// иначе раскодированное в scratch.
std::string_view literalText(const Ast &ast, NodeId node, std::string &scratch);

/// Число в строку по docs/semantics.md §4.3.
std::string_view formatNumber(double value, char *buffer, std::size_t size);

inline constexpr std::size_t kNumberBufferSize = 48;

}  // namespace CS
```

`literalText` знает про `Ast`, поэтому заголовок его включает. Разнести на два
файла ради чистоты зависимостей значило бы дублировать четыре строки в каждом
вызывающем — не окупается.

## 11. Тесты

Помимо очевидных проверок каждого вида узла, набор обязан закрыть то, ради чего
дизайн именно такой.

**Новый агрегат при каждом вычислении.** Одно и то же дерево вычисляется дважды;
результаты не `sameAggregate`. Без этого §2.3 держится на честном слове.

**Индекс вычисляется даже при базе `null`.** `null[неизвестныйКорень]` даёт
ошибку имени, а не `null`. Это единственный наблюдаемый способ проверить
зафиксированный порядок вычисления: побочных эффектов в выражениях нет.

**Опечатка в корне и опечатка глубже различаются.** `usre.name` — ошибка `Name`;
`user.prfoile.avatar` — `null`. Обе половины обязательны: без первой правило
вырождается, без второй §6.3 перестаёт работать.

**Ключи по §4.3.** `obj[-0]` и `obj[0]` — разные ключи; `obj[null]` и
`obj['null']` — один; `obj[true]` и `obj['true']` — один.

**Представление числа.** Все пять примеров §4.3, четыре особых значения и обе
границы порога: значение чуть меньше `1e21` даёт фиксированную запись, само
`1e21` — научную; то же на нижней границе `1e-7`.

Дальше по операциям: чтение ключа существующего и отсутствующего; чтение у
`null` любой глубины; чтение у числа, строки и логического значения — ошибка;
индекс в границах, за границей, дробный, отрицательный, `NaN`, бесконечный, не
число; пустые `[]` и `{}`; вложенные агрегатные литералы с путями внутри.

## 12. Бенчмарки

- короткий путь `user.name` — самое частое выражение в props;
- глубокий путь из пяти сегментов — цена спуска;
- чтение по числовому ключу — цена приведения в горячем месте;
- построение агрегатного литерала из десяти элементов;
- `formatNumber` отдельно, на числе с длинной мантиссой.

Записываются в `benchmarks/baseline.json` тем же механизмом, что у прошлых
этапов. Строки `BM_Lex_*`, `BM_Parse_*`, `BM_Store_*` и `BM_Data_*` при этом
меняться не обязаны — но проверять их надо по факту, а не по предположению:
в прошлом этапе такое предположение оказалось неверным.

## 13. Правки в нормативных документах

`docs/semantics.md` §4.3 — предложение «Соответствует `std::to_chars` без
указания формата» заменяется правилом §7.1 настоящего документа. Оно
противоречит собственной таблице примеров: без формата `to_chars` выбирает
кратчайшую из двух записей, и `1000000` превращается в `1e+06`, тогда как
таблица требует `1000000`. Таблица остаётся как есть — ей и следуем.

## 14. Что остаётся отложенным

- **Обход циклом вместо рекурсии.** Узлы лежат в порядке пост-обхода, поэтому
  прямой цикл по индексам корректен; мешают короткое замыкание, требующее
  пропуска отрезков, и буфер промежуточных значений на всё дерево. Потребуется
  индекс первого потомка у узла. Новый пункт `docs/backlog.md`.
- **B11** — статические проверки арности и `Void`. Приходят с частью 3, где
  появляется таблица встроенных функций.
- **B15** — равенство. Приходит с частью 2, где определена вся глава 5.
- **B23** — запрет заводить корень после первой компиляции. Ждёт слоя
  компиляции; проверка неизвестного корня, описанная в §5, переедет туда же.
