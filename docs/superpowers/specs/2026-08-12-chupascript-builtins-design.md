## 3. Таблица билтинов

```cpp
// core/src/builtin.hpp
/// Порядок совпадает с алфавитным порядком имён: таблица ищется двоично, и
/// номер в enum служит индексом в неё.
enum class Builtin : std::uint8_t {
    Abs, Count, Format, Has, Keys, Last, Max, Min, Pop, Push, Round, Str, Typeof
};

/// Переменное число аргументов: только у format (§8.9).
inline constexpr std::uint8_t kVariadic = 255;

struct BuiltinInfo {
    std::string_view name;
    std::uint8_t minArgs;
    std::uint8_t maxArgs;   ///< kVariadic — без верхней границы
    bool returnsValue;      ///< false — Void (§2.2)
};

/// Находит билтин по имени. false — такой функции нет.
bool findBuiltin(std::string_view name, Builtin *out) noexcept;

const BuiltinInfo &builtinInfo(Builtin id) noexcept;

/// Применяет билтин к уже вычисленным аргументам. Все, кроме format (§7).
///
/// Число аргументов и то, что билтин возвращает значение, гарантированы
/// статическим проходом (§5): здесь они не перепроверяются.
bool applyBuiltin(Builtin id, Context &ctx, const Value *args,
                  std::uint32_t count, std::uint32_t offset, Value *out,
                  Diagnostic &diag);
```

Таблица отсортирована по имени, поиск двоичный — тот же приём, что у ключей
объекта (`context.cpp`, `findKey`).

Арности из §8: `count`, `keys`, `last`, `pop`, `str`, `typeof`, `abs`, `round` —
один аргумент; `has`, `push`, `min`, `max` — два; `format` — от одного.
`push` и `pop` возвращают `Void`, остальные одиннадцать — значение.

`builtin.*` относится к `check.*` и `eval.cpp` так же, как `operator.*` из части
2 относится к обходу: чистая функция от значений, отделённая от управления.

### 3.1 Две тонкости, которые легко реализовать неверно

**`count` у строки считает байты, а не символы** (§8.1): `count('привет')` даёт
`12`, `count('😀')` — `4`. Наши строки и так срезы байт, поэтому верная
реализация проще неверной; тест нужен, чтобы её не «починили».

**Порядок в `keys` не определён** (§8.2). Пары в объекте у нас отсортированы по
ключу, поэтому `keys` вернёт их по возрастанию. Это совпадение реализации, а не
обещание языка: в документах оно не фиксируется, а тест не вправе на него
опираться — иначе обещание возникнет само собой.

## 4. Компиляция

```cpp
// core/src/compile.hpp
/// Разбирает и проверяет выражение. Возвращает число найденных ошибок; 0 —
/// успех. В out кладёт не больше capacity первых.
std::uint32_t compileExpression(const char *source, std::uint32_t length,
                                Ast &ast, const Context &ctx, Diagnostic *out,
                                std::uint32_t capacity);

std::uint32_t compileScript(const char *source, std::uint32_t length, Ast &ast,
                            const Context &ctx, Diagnostic *out,
                            std::uint32_t capacity);
```

Ошибка разбора даёт ровно единицу: парсер останавливается на первой. Ошибок
проверки может быть сколько угодно.

Фасад — одна дверь для обычного пути и будущая подложка `chupa_compile_*`.
Парсер при этом остаётся чистой грамматикой и про билтины по-прежнему не знает,
как требует `docs/grammar.md` §6.

## 5. Статический проход

```cpp
// core/src/check.hpp
/// Проверяет дерево правилами docs/grammar.md §6.
///
/// Возвращает, сколько ошибок нашлось; в out кладёт не больше capacity первых.
/// Ноль — дерево пригодно к вычислению, и на нём ставится отметка (§5.3).
///
/// Из ctx читается только состав имён (§5.4): значения проверкам не нужны.
std::uint32_t check(Ast &ast, const Context &ctx, Diagnostic *out,
                    std::uint32_t capacity);
```

### 5.1 Семь проверок

| Проверка | Норма |
|---|---|
| Вызов неизвестной функции | §9.1 |
| Неверное число аргументов | §9.1 |
| Значение-возвращающий билтин в позиции стейтмента | `grammar.md` §6.1 |
| Использование результата `Void`-билтина | `grammar.md` §6.2 |
| Число плейсхолдеров `format` при литеральном шаблоне | §8.9 |
| Цель присваивания — само имя | §7.2, переезжает из вычислителя |
| Обращение к необъявленному имени | §9.1 после переезда, см. §5.5 |

Предпоследняя закрывает B27: правило решается по одному дереву, и в вычислителе
оно стояло лишь потому, что прохода не существовало.

### 5.2 Проход не останавливается и не рекурсивен

**Все ошибки, а не первая.** Иначе валидатор в CLI заставляет исправлять по
одной. Возвращаемое число может превысить `capacity`: вызывающий узнаёт, что
нашлось больше, чем поместилось.

**Плоский цикл, а не рекурсия.** Узлы лежат в порядке пост-обхода, поэтому
`for (NodeId n = 1; n <= root; ++n)` — корректный обход (B25). Рекурсия нужна
была вычислителю ради короткого замыкания: часть дерева не должна вычисляться.
Проверкам пропускать нечего, они смотрят на всё, — значит цикл, и предела
глубины у прохода нет вовсе.

Определить, использован ли результат вызова, цикл умеет без родительских
ссылок: каждый узел смотрит на **своих детей**, и `Call` среди них означает, что
его результат употреблён. Родитель у узла один, а пост-обход гарантирует, что
дети идут раньше. Единственный случай без родителя — `Call` в корне дерева
выражения (`count(items)` как целый props); он разбирается отдельно и считается
употреблённым.

### 5.3 Проход обязателен

**Вычислитель дереву доверяет и арность не перепроверяет.**

Обсуждался и обратный порядок — пропускать проход на устройстве в релизе. Тогда
вычислитель обязан был бы оставаться тотальным на непроверенном дереве: без
проверки арности `min(a)` читает `ast.child(node, 1)` за границей списка детей,
а это порча памяти, не ошибка выполнения. Правило пришлось бы держать в двух
местах, где оно со временем разъезжается, — та же беда, что была у правил
индекса между чтением и записью.

Решено обязательным проходом: правило записано один раз, обязанности не
размазаны. **Проход отвечает за правильность дерева, вычислитель — за
вычисление.**

Удерживается отметкой: `check` при нуле ошибок ставит на `Ast` признак
«проверено», вычислитель требует его утверждением. Забытый проход падает на
первом же тесте, в релизе не стоит ничего. Тот же приём, которым `runScript`
требует дерева от `parseProgram`.

Довод, решивший вопрос: пропуск прохода был гипотезой без измерений; после
задачи 7 цена прохода измерена (`BM_Check_Props` против `BM_Parse_Props`,
делённого на сто, `benchmarks/eval_benchmark.cpp`). Проход стоит около **98 нс**
против **244 нс** разбора того же выражения — разбор дороже примерно **в 2.5
раза**; та же разница в другой рамке — проход добавляет около **40 процентов**
к цене компиляции выражения. Обе рамки указывают одно направление: разница
реальная, но не на порядок. Решение не меняется ни при одной из рамок: сто
наносекунд однократно при компиляции — ничто рядом с вычислением, которое
повторяется на каждом кадре.

Погрешность метода: `BM_Parse_Props` разбирает сто копий выражения, склеенных
через `+`, и склейка добавляет девяносто девять узлов `Binary`, которых у
отдельно взятого выражения нет. Деление на сто поэтому немного завышает цену
разбора; настоящее отношение ближе к **2.3**, чем к 2.5. Смещение
консервативное — работает против измеряемого утверждения, не за него.

Отложить оптимизацию дешевле, чем отложить устройство кода. Записано как B31.

### 5.4 Проходу нужны имена, а не значения

Шесть проверок — функция от одного дерева. Седьмой нужен состав имён, и только
он: `Context::hasRoot` отвечает на всё, что ей требуется.

Разница важна для инструмента валидации. Он читает `variables` из того же
макета, что и разбирает, кладёт эти имена в пустой `Context` со значением `null`
каждое — и проверка работает. **Данные не нужны, нужен состав.**

### 5.5 Имя проверяется на этапе компиляции

Сегодня обращение к неизвестному имени — ошибка выполнения (§9.2). Спека C API
выводит из порядка «данные поставлены → компиляция» обратное: состав имён
компилятору виден, поэтому `usre.name` следует отвергать при разборе макета, а
не при первом показе экрана. Глава 10 семантики числит этот вопрос открытым.

Три документа расходятся; проход разрешает расхождение в пользу компиляции.
Для автора макета это самая ценная из проверок: опечатка в имени переменной
иначе всплывает лишь тогда, когда конкретная вью окажется на экране.

**Ключи объектов при этом не проверяются никогда, и это не пробел.** `user.profil.name`
с опечаткой не даёт ошибки ни на какой стадии: чтение отсутствующего ключа даёт
`null` (§6.2), чтение у `null` даёт `null` (§6.3). Так решено потому, что данные
приходят неполными и падать на каждом недостающем поле нельзя. Цена — асимметрия:
опечатка в имени переменной ловится компилятором, опечатка в поле не ловится
ничем. Статически ключи проверяла бы только схема данных, которой в языке нет.

### 5.6 Инвариант, на котором держится проверка

**Состав имён известен на момент компиляции.**

Свойство это несущее: без него седьмая проверка не сложна, а невозможна. Всякая
будущая возможность языка обязана его сохранять. Объявления с литеральным
именем в исходнике сохраняют — состав виден в дереве, и даже использование до
объявления ловится статически. Имя, вычисляемое во время выполнения, ломает.

Инвариант записывается именно свойством, а не запретом динамических имён:
запрет закрыл бы один способ его нарушить, свойство закрывает все, включая ещё
не придуманные.

Отсюда следствие для порядка вызовов: проверка верна, только если хост ставит
все имена **до** компиляции. Механизма, гарантирующего этот порядок, нет —
`setVariable` сегодня можно звать когда угодно. Это B23, и после части 3b он из
желательного становится несущим: на нём держится правильность новой проверки.

## 6. Вызов в обходе

Ветка `NodeKind::Call` в `eval`:

1. `findBuiltin` по имени узла — **утверждение, а не ошибка**: неизвестное имя
   отсеял проход (§5.3), и вычислитель дереву доверяет;
2. `format` уходит своим путём (§7);
3. остальные двенадцать: аргументы вычисляются слева направо в буфер на стеке,
   затем `applyBuiltin`.

Буфер фиксирован двумя элементами — по самому «широкому» невариадическому
билтину. Верхнюю границу даёт таблица, а не догадка.

`CallStatement` в `runScript` вычисляет вызов и результат отбрасывает; у
`Void`-билтина результата и нет.

**`Void` не становится значением.** `applyBuiltin` для `push` и `pop` не трогает
`*out`; вызывающий, знающий из таблицы, что значения нет, его и не читает. Тип
`Void` остаётся пометкой компилятора, как обещает §2.2.

## 7. `format`

Единственный билтин, строящий новую строку из кусков.

```cpp
// core/src/context.hpp — добавляется
/// Начинает сборку строки в отдельном буфере build_. Возвращает метку для endString.
std::uint32_t beginString() noexcept;
void appendToString(std::string_view bytes);
/// Копирует собранное в пул текста и возвращает готовую строку.
Value endString(std::uint32_t mark) noexcept;
/// Усекает буфер сборки обратно к метке: сборка не удалась.
void abortString(std::uint32_t mark) noexcept;
```

Один проход: шаблон читается слева направо, каждый аргумент приводится к строке
по разу.

**`format` — единственный билтин, чьи аргументы вычисляются по мере надобности,
а не заранее.** Он вариадичен, а буфер под заранее вычисленные аргументы
потребовал бы верхней границы, которой §8.9 не устанавливает: появился бы предел
числа аргументов, придуманный реализацией. Лениво выходит и проще, и без
предела, потому что шаблон потребляет аргументы строго слева направо и ровно по
одному на плейсхолдер.

Из этого следует, где живёт код. Ленивое вычисление требует доступа к дереву,
поэтому цикл `format` стоит в ветке `Call` вычислителя, а в `builtin.*`
выносится разбор шаблона — функция `nextFormatPiece`, находящая очередной кусок
шаблона (литеральный пробег, `${}` или `$${}`) и различающая их. Так `builtin.*`
остаётся не знающим про `Ast`, а проход §5.1 (`countPlaceholders`) и вычислитель
(`evalFormat`) считают и разбирают плейсхолдеры **одной и той же функцией**, а не
двумя похожими копиями одного правила: правило «`$${}` — литерал, `${}` —
плейсхолдер» записано в `nextFormatPiece` один раз, и оба потребителя вызывают
именно её — совпадение держится на устройстве, а не на аккуратности при переносе
кода.

**Сборка идёт в собственном буфере (`build_` в `Context`), отдельном от пула
текста (`text_`), а не в самом пуле текста.** Первая версия этого раздела
описывала обратное — сборку прямо в `text_`, с обоснованием, что `abortString`
безопасен, «потому что между `beginString` и `endString` в пул не пишет никто
другой: аргументы уже вычислены». Это обоснование ложно и противоречит тремя
абзацами выше написанному: аргументы `format` вычисляются по мере надобности,
то есть **внутри** промежутка между `beginString` и `endString`, а не до него.
Вычисление аргумента-плейсхолдера само пишет в `text_` — строковый литерал зовёт
`makeString`, `str` и вложенный `format` кладут туда результат, — и эти байты
ложились прямо между уже собранными кусками текущей сборки, попадая в результат
как есть. (Присваивание вида `obj.k = v` сюда не относится — это стейтмент, а
не выражение, и аргументом format быть не может; запись через `objectSet`
происходит только для объектного литерала, а его как аргумент format всё равно
отверг бы по типу — агрегат.) Наблюдалось на самых
обычных выражениях: `format('Hello, ${}!', 'world')` давал
`'Hello, worldworld!'`, `format('${}', str(2))` — `'22'`. ASan это не ловил:
память вся в границах, порча была логической, а не за-границной.

Раздельные хранилища снимают вопрос целиком: что бы ни писало в `text_` между
`beginString` и `endString`, буфер `build_` этого не видит, потому что это другая
память. Тем же свойством вложенная сборка становится безопасной сама по себе —
без него внешний `format('${}', format('${}', 1))` захватил бы вывод внутреннего
себе в результат. `endString` копирует собранное из `build_` в `text_` через
`makeString` и усекает `build_` обратно к метке; `abortString` усекает `build_`
без копирования. У обоих метка — позиция в `build_`, а не указатель: рост
`build_` при накоплении вправе переселить данные, и, как и везде в этом проекте,
через границу такого переезда держится смещение, а не адрес.

Разбор шаблона в `evalFormat` берёт `ctx.string(tmpl)` заново перед каждым
вызовом `nextFormatPiece`, а не один раз до цикла — по той же причине: значение
шаблона лежит в `text_`, а вычисление аргумента-плейсхолдера вправе переселить
`text_` кем-то из перечисленного выше. Смещение, на которое указывает `tmpl`,
переезд не портит; кэшированный указатель — портит.

Правила §8.9: плейсхолдер — `${}`, `$${}` даёт литеральное `${}`, аргументы
подставляются слева направо, агрегат в аргументе — ошибка. Число плейсхолдеров
обязано совпадать с числом аргументов: при литеральном шаблоне это уже сделал
проход (§5.1), иначе проверяется здесь и даёт ошибку выполнения.

## 8. Ошибки

Новых классов не появляется; появляется новая **стадия**, и два условия через
границу стадий переезжают.

| Стадия | Что ловит |
|---|---|
| Компиляция (§9.1) | семь проверок §5.1 |
| Выполнение (§9.2) | аргумент неподходящего типа (§8), несовпадение плейсхолдеров при нелитеральном шаблоне |

Ошибка компиляции означает, что макет не применяется целиком; ошибка выполнения
прерывает вычисление посреди работы.

### 8.1 Таблицы главы 9 перестают быть верными, и их надо чинить

Часть 3b **переносит два условия между стадиями**, поэтому оставить §9 как есть
нельзя — таблицы начнут врать. Строки «Неизвестное имя» и «Цель присваивания —
само имя» переезжают из §9.2 в §9.1.

Заодно чинится то, чего в главе 9 не было изначально: **ни одна таблица не
говорит, какой `ErrorCode` соответствует условию и кто его диагностирует.**
Чтобы ответить на вопрос «что будет, если парсер не найдёт нужный токен»,
приходится читать код. Таблицы получают две колонки — код и источник: лексер,
парсер, проход или вычислитель, — и лексические с синтаксическими условиями
перечисляются наравне с прочими, а не прячутся за ссылкой на другой документ.

Третье: глава 10 числит открытым вопрос «обращение к отсутствующему имени —
выполнение или компиляция». Часть 3b на него отвечает, и вопрос из главы 10
уходит вместе с условием, при котором ответ верен (§5.6).

Это единственное место, где часть 3b растёт сверх обещанного, и растёт она на

## 10. Тесты

Около 65. По каждому билтину: верный тип, неверный тип, край (пустой массив,
пустая строка, отсутствующий ключ).

Отдельного внимания требуют:

- **`count` у строки считает байты** — `count('привет')` даёт `12`, `count('😀')`
  даёт `4`;
- **`pop` и `push` ничего не возвращают** — и результат их использовать нельзя
  (ошибка компиляции, а не `null`);
- **`last` на пустом массиве даёт `null`**, а `arr[count(arr) - 1]` на нём же —
  ошибку, как объясняет §8.4;
- **`round` округляет от нуля**: `round(-0.5)` даёт `-1`, а не `0`;
- **`has` отличает отсутствующий ключ от ключа со значением `null`** — обе
  половины, иначе правило вырождается;
- **`format`**: `$${}` даёт литеральное `${}`; несовпадение при литеральном
  шаблоне — ошибка компиляции, при нелитеральном — выполнения; агрегат в
  аргументе — ошибка;
- **`keys`**: возвращает все ключи; на порядок тест не опирается (§3.1).

Проход: каждая из семи проверок ловится; **несколько ошибок возвращаются
разом**; возвращаемое число больше `capacity` при переполнении; проверенное
дерево получает отметку, непроверенное — нет.

Проверка имени отдельно: неизвестное имя даёт ошибку **компиляции**, а не
выполнения; известное проходит; **опечатка в ключе не даёт ошибки ни на какой
стадии** и возвращает `null` — обе половины, иначе асимметрия §5.5 не
зафиксирована; контекст, содержащий одни имена со значением `null`, проверке
достаточен.
