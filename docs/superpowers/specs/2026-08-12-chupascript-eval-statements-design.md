## 3. Как пишется значение

Отдельной машинерии для левого значения не требуется, и это прямое следствие
модели значений: **агрегаты — хендлы**.

`varName.items[0] = x` распадается на две части:

- **база** `varName.items` — обычное выражение, которое умеет вычислять часть 1;
- **последнее звено** `[0]` — место записи.

База даёт хендл массива, `Context::arraySet` меняет его содержимое, и изменение
видно всем, кто на этот массив ссылается. Для `a.b.c = v` база `a.b` даёт хендл
объекта, пишет `objectSet`.

То есть присваивание — это «вычислить всё, кроме последнего сегмента, затем
записать». Ни ссылок, ни адресов, ни разрешения левых значений.

### 3.1 Порядок вычисления

`docs/semantics.md` §7.2: **все подвыражения цели вычисляются до вычисления
правой части**. Порядок такой:

1. база цели;
2. индекс, если последнее звено — `[…]`;
3. правая часть;
4. для составного присваивания — чтение текущего значения и применение операции;
5. запись.

Шаг 4 стоит после шага 3, тогда как буквальное раскрытие `x = x + e` читало бы
`x` раньше `e`. Разница ненаблюдаема по той же причине, по которой ненаблюдаема
однократность (§4): выражения чисты, а чтение по уже проверенной базе не
отказывает.

### 3.2 Куда можно писать

| Последнее звено | База | Действие |
|---|---|---|
| `.k` | `Object` | `objectSet` — создаёт ключ либо заменяет значение (§6.2) |
| `.k` | `Null` | **ошибка** `Type` |
| `.k` | прочее | ошибка `Type` |
| `[i]` | `Array`, целое ≥ 0 в границах | `arraySet` |
| `[i]` | `Array`, целое ≥ 0 за границей | **ошибка** `Range` |
| `[i]` | `Array`, дробный или отрицательный | ошибка `Range` |
| `[i]` | `Array`, не `Number` | ошибка `Type` |
| `[k]` | `Object` | приведение ключа к строке (§4), затем `objectSet` |
| `[…]` | `Null` | **ошибка** `Type` |
| `[…]` | прочее | ошибка `Type` |
| звена нет — цель есть имя | — | **ошибка** `Name` (§5) |

**Две асимметрии с чтением намеренны.**

Запись в `null` — ошибка, хотя чтение у `null` даёт `null` (§6.3). Мягкость §6.3
распространяется только на чтение: `user.profile.name = 'Вася'` при `profile`
равном `null` записывать некуда, и молчаливое пропускание записи потеряло бы
данные без следа.

Запись за границу массива — ошибка, хотя чтение за границей даёт `null` (§6.1).
Чтение за границей штатно, потому что данные с сервера неполны; запись за
границу означает намерение создать элемент, для чего существует `push`.

## 4. Составное присваивание

`x += e` есть `x = x + e`, где операция берётся из `applyBinary`. Ради этого
часть 2 и разводилась надвое: составному присваиванию нужна ровно функция
«применить операцию к двум значениям».

Соответствие: `+=` → `Plus`, `-=` → `Minus`, `*=` → `Star`, `/=` → `Slash`.
Операции `%=` в языке нет (`grammar.md` §5.2).

**Отсюда следует неочевидное поведение на записи за границу.** `arr[5] += 1` на
массиве из двух элементов даёт ошибку `Type`, а не `Range`: по эквивалентности
сначала читается `arr[5]`, что штатно даёт `null`, затем вычисляется `null + 1`,
что и есть ошибка типа. До проверки границы записи дело не доходит. Это следствие
§7.3, а не отдельное решение, и записано здесь потому, что читается двояко.

### 4.1 Однократность цели ненаблюдаема

`docs/grammar.md` §6.4 требует вычислять подвыражения цели ровно один раз:
наивное раскрытие `arr[idx()] += 1` в `arr[idx()] = arr[idx()] + 1` позвало бы
`idx()` дважды.

Схема §3.1 этого достигает сама: база и индекс вычисляются по разу, дальше
чтение и запись идут по одному и тому же хендлу.

**Но проверить требование тестом на поведение нельзя.** §3.2 гарантирует, что
выражения не имеют побочных эффектов; билтин, который их имеет, не возвращает
значения и в выражении стоять не может (§6.2). Значит `idx()` обязан быть чистым,
и второй его вызов дал бы тот же ответ.

Требование остаётся — оно про стоимость, а не про смысл, — но держится оно на
устройстве кода, а не на тесте. Записано явно, чтобы никто не написал проверку,
проходящую при любой реализации.

## 5. Присваивание имени запрещено

Грамматика разрешает имя как цель: `LeftHandSide ::= Identifier ( '[' Expression
']' | '.' Identifier )*`, и §5.2 прямо называет `a` корректной целью. Семантика
— нет: §7.1 говорит, что программа изменяет только **содержимое агрегатов**,
лежащих в контексте.

Разрешается в пользу семантики. Имя — входной слот от хоста, а не переменная
скрипта: хост ставит его вызовом на имя, скрипт меняет то, что внутри.
`varName = {...};` разбирается, но отвергается с ошибкой `Name`.

Довод, решивший вопрос, — ссылочность. Замена значения имени целиком выбрасывает
агрегат, на который могли остаться ссылки из других имён, а §2.3 обещает, что
мутация через одно имя видна через второе. После `varName = {}` алиас продолжил
бы указывать на прежний массив, и данные разъехались бы тихо.

Этим закрывается пункт из ненаписанной главы 10 семантики: «допустимо ли
присваивание корневому имени целиком» получает ответ «нет».

Проверка выполняется при обходе. Она решаема статически — цель видна в дереве, —
и на этапе 3b переедет к §6.1 и §6.2, где ей место.

## 6. Режим скрипта

```cpp
// core/src/eval.hpp
/// Выполняет разобранный скрипт: последовательность стейтментов.
///
/// Дерево обязано быть построено parseProgram **успешно**: у неудачного разбора
/// корень равен kNoNode. Значения нет — результат это признак успеха
/// (docs/semantics.md §3.1).
///
/// Ошибка прерывает выполнение посередине, и сделанное остаётся сделанным.
bool runScript(const Ast &ast, Context &ctx, Diagnostic &diag);
```

Корень — `Program`, дети — стейтменты, выполняются по порядку. Пустой стейтмент
`;` узла не порождает и до вычислителя не доходит: парсер его пропускает.

**Цикл по стейтментам различает виды сам**, не отдавая их в `eval`: узел `Assign`
идёт в присваивание, всё прочее отвергается. Прочее сегодня — это только
`CallStatement`, который придёт с частью 3b; отдавать его в `eval` значило бы
получить сообщение про выражение там, где речь о стейтменте.

**Ошибка не откатывается.** Обработчик, упавший на третьем присваивании из пяти,
оставит первые два применёнными: откатывать нечего, предыдущих состояний
хранилище не держит. Записано в спеке C API как принятая цена модели памяти.

## 7. Ошибки

Новых классов не появляется.

| Класс | Когда |
|---|---|
| `Name` | неизвестное имя; цель присваивания есть имя |
| `Type` | запись у неподходящей базы, запись в `null`, нечисловой индекс, всё из глав 4–6 |
| `Range` | запись за границу массива, дробный или отрицательный индекс |

Смещение — от узла, на котором остановились. Первая ошибка выигрывает.

## 9. Тесты

Помимо очевидных, набор обязан закрыть асимметрии — каждую обеими половинами,
иначе правило вырождается в одностороннее:

- **`null`**: чтение у `null` даёт `null`, запись в `null` — ошибка.
- **Граница массива**: чтение за границей даёт `null`, запись за границу —
  ошибка `Range`.
- **`arr[5] += 1` за границей даёт `Type`, а не `Range`** — следствие §7.3,
  разобранное в §4.
- **Цель-имя**: `varName = 1;` — ошибка `Name`; `varName.k = 1;` — работает.

Дальше: создание нового ключа записью; замена существующего; запись по числовому
ключу с приведением; цепочка любой глубины `a.b.c[0].d = x`; все четыре
составных оператора; составное присваивание к отсутствующему ключу
(`obj.missing += 1` — чтение даёт `null`, сложение даёт ошибку `Type`).

**Скрипт**: несколько стейтментов применяются по порядку; ошибка на третьем из
пяти оставляет первые два применёнными и третий не применённым; пустой скрипт
выполняется успешно; `CallStatement` отвергается как неподдержанный.

**Ссылочность**: запись через одно имя видна через второе, если хост положил
один агрегат под двумя именами.

## 10. Бенчмарки

- присваивание в путь из двух сегментов — самая частая форма в обработчике;
- составное присваивание туда же — цена чтения плюс операции плюс записи;
- скрипт из пяти присваиваний — цена обхода `Program`.

Записываются в `benchmarks/baseline.json` тем же механизмом. Прежние семейства
проверяются по факту: этап трогает `eval.cpp`, поэтому `BM_Eval_*` под
подозрением.
