## Что эти числа говорят

**Поиск имени на вычислении устранён полностью.** Отдельный замер
(`NameLookupBenchmark_Tests`) читает одну переменную при разном числе
глобальных имён:

| глобальных имён | до | после |
|---|---|---|
| 1 | 25.7 | 10.2 |
| 5 | 30.9 | 10.2 |
| 19 | 44.6 | 10.0 |
| 100 | 57.6 | 10.0 |
| 1000 | 63.1 | 10.1 |

Константа в том же прогоне стоит 9.2–9.7 нс — это пол, цена захода в C и обхода
дерева из одного узла. То есть чтение переменной сошлось с полом и перестало
зависеть от размера контекста вовсе.

**Разброс `int` / `double` / `bool` объяснился и исчез.** Было 37 / 54 / 68 при
одинаковой работе; стало 10.5 / 10.7 / 10.3. Весь разброс был поиском: у имён
разная длина и разное место в отсортированном массиве. Гипотеза о
неспециализированных обобщённых вызовах на стороне Swift, которая жила в [B49],
оказалась неверной — см. следующий пункт.

**Обвязка Swift не стоит ничего.** Замер `BridgeCostBenchmark_Tests` зовёт те же
выражения напрямую по хэндлу, мимо `Expression.eval()` и протокола `CSValue`:
отношения 0.98–1.04 на всех кейсах. Пометка `@inlinable` на путях вычисления
ничего не меняет (проверено отдельным прогоном и откачено).

**Вся оставшаяся просадка — построение `String` на стороне Swift.** Тот же замер
с вариантом «не доводить до `String`» раскладывает длинную строку так:

| | нс |
|---|---|
| весь путь чтения | 434 |
| движок + граница C + `std::string` + `ChupaString` + malloc/free | 110 |
| **`String(decoding:as:UTF8.self)`** | **324** |

Причина — в устройстве Swift. `validateUTF8`
(`stdlib/public/core/StringUTF8Validation.swift`) начинается с векторной
проверки `_allASCII` по 16 байт за шаг, а при первом же не-ASCII байте уходит в
**побайтовый цикл через итератор**. Отдельный микрозамер на macOS: 552 байта
ASCII — 53.6 нс, те же 552 байта кириллицей — 289.4 нс, а ASCII с **одним**
кириллическим символом — 202 нс независимо от его позиции.

Публичного способа собрать `String` из байт без проверки нет:
`unsafeUninitializedCapacity` медленнее (355 нс — он валидирует уже после
заполнения), `String(cString:)` — 307, `NSString(bytes:)` — 880.

Отсюда вывод: ускорять построение строки бессмысленно, мы уже на самом быстром
способе. Экономить можно только **не строя её** — кэшем результата со счётчиком
поколений хранилища.

## Чему здесь верить

Своего стенда у проекта нет ([B42]), поэтому оговорка та же, что и в [B49]:
пригодны **отношения сторон внутри одного прогона**. Абсолютные наносекунды
между прогонами гуляют в пределах ±10% — это видно по неизменной прежней
стороне, которая между двумя прогонами дала 15.3 и 17.0 на одном и том же
кейсе. Сравнения «до/после» выше построены на колонке движка и этот же предел
имеют: сдвиги меньше 10% результатом не считаются.

Три строки помечены шумом и результатом не являются.

## Как повторить

```sh
cd ~/odnoklassniki-ios
xcodebuild test \
  -workspace OK.xcworkspace \
  -scheme OKBDUI-Unit-Tests \
  -configuration Release \
  -destination 'platform=iOS Simulator,name=iPhone 16 Pro,OS=18.4' \
  -only-testing:OKBDUI-Unit-Tests/WidgetPropertyBenchmark_Tests \
  -only-testing:OKBDUI-Unit-Tests/ExpressionEvalBenchmark_Tests \
  -only-testing:OKBDUI-Unit-Tests/PropertyParsingBenchmark_Tests \
  ENABLE_TESTABILITY=YES CODE_SIGNING_ALLOWED=NO
```

`ENABLE_TESTABILITY=YES` обязателен: замер объявляет `@testable import OKBDUI`,
а в Release тестируемость по умолчанию выключена.

Замеры `BridgeCostBenchmark_Tests` и `NameLookupBenchmark_Tests` — временные,
писались под этот разбор и в монорепозитории не оставлены.
