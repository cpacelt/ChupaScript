# Грамматика ChupaScript

**Версия:** 0.1
**Дата:** 2026-08-10
**Статус:** нормативный документ

Этот документ — **единственный источник правды о грамматике ChupaScript**. При
расхождении с любым другим текстом, комментарием в коде или реализацией
правильным считается этот документ.

История принятия решений и их обоснования вынесены в
`docs/superpowers/specs/2026-08-10-chupascript-grammar-design.md`. Тот документ
описательный, этот — нормативный.

---

## 1. Область применения

Документ определяет **лексическую** и **синтаксическую** грамматику ChupaScript:
какие последовательности байт являются корректной программой и какое дерево
разбора им соответствует.

Документ **не** определяет: систему типов, вычислительную семантику, набор и
поведение встроенных функций, модель ошибок времени выполнения, модель памяти,
устройство рантайма. Там, где грамматика вынуждена сослаться на эти области
(например, «билтин не возвращает значения»), ссылка помечена явно.

ChupaScript встраивается в JSON, описывающий иерархию вьюх. Способ извлечения
исходного текста из JSON — разметка полей, обрамление, экранирование — лежит вне
языка и вне этого документа. Рантайм получает **готовую строку с исходным
текстом**.

## 2. Нотация

Грамматика записана в EBNF со следующим метасинтаксисом.

| Запись | Значение |
|---|---|
| `Символ ::= ...` | определение нетерминала |
| `A \| B` | альтернатива |
| `A?` | ноль или одно вхождение |
| `A*` | ноль или более вхождений |
| `A+` | одно или более вхождений |
| `( A B )` | группировка |
| `'текст'` | терминал, записывается буквально |
| `[A-Za-z]` | любой символ из диапазона |
| `кроме X` | любой символ, не входящий в X |

Имена нетерминалов пишутся в `CamelCase`. Правила, которые невозможно выразить в
EBNF, вынесены в разделы «ранние ошибки» (§4.9, §5.5) и §6 — по образцу
*Early Errors* в ECMA-262. Реализация обязана их проверять; они являются частью
определения языка наравне с продукциями.

> **Почему ранние ошибки вынесены отдельно.** Часть ограничений языка невыразима
> контекстно-свободной грамматикой — например, «вызванный билтин не должен
> возвращать значение» требует знания таблицы билтинов, а её в грамматике нет.
> Попытка втащить такие правила в продукции сделала бы грамматику неоднозначной
> или неразрешимой. Стандартный приём — оставить грамматику широкой, а лишнее
> отсечь отдельным списком проверок.

## 3. Исходный текст

Исходный текст — последовательность байт в кодировке **UTF-8**.

Лексер обрабатывает текст **побайтово**. Декодирование UTF-8 не выполняется
нигде: все синтаксически значимые символы лежат в ASCII (`< 0x80`), а свойство
самосинхронизации UTF-8 гарантирует, что байт ASCII-символа не может встретиться
внутри многобайтовой последовательности. Байты `>= 0x80` допустимы только внутри
строковых литералов и комментариев и переносятся в результат без интерпретации.

Метка порядка байт (BOM, `EF BB BF`) в начале текста не распознаётся и приводит к
ошибке лексера как недопустимый байт.

Корректность UTF-8 не проверяется. Некорректная последовательность внутри
строкового литерала попадёт в результирующую строку как есть.

## 4. Лексическая грамматика

Лексер преобразует исходный текст в поток токенов. Пробельные символы и
комментарии токенов не порождают и отбрасываются.

```
Token ::= Identifier | Keyword | NumericLiteral | StringLiteral
        | BooleanLiteral | NullLiteral | Punctuator
```

### 4.1 Пробельные символы

```
Whitespace ::= ' ' | '\t' | '\n' | '\r'
```

Пробельные символы разделяют токены и отбрасываются. **Переводы строк не
значимы**: `\n` и `\r` — обычные разделители, парсер о них не знает.

`\r` включён в список ради текстов с переводами строк CRLF: исходник, прошедший
через тулинг под Windows, обязан разбираться без изменений.

### 4.2 Комментарии

```
LineComment  ::= '//' ( кроме '\n' )*
BlockComment ::= '/*' ( любой байт )* '*/'
```

Блочные комментарии **не вкладываются**: первое встреченное `*/` закрывает
комментарий, открытый последним `/*`.

Комментарий эквивалентен пробельному символу.

> **Зачем нужен блочный комментарий.** Исходный текст часто хранится в JSON
> одной строкой — переводы строк там требуют экранирования, и авторы их обычно
> не ставят. В такой записи `//` закомментирует весь остаток программы, не
> вызвав никакой ошибки. Блочная форма — единственная, которой можно
> прокомментировать фрагмент внутри однострочной программы.

### 4.3 Токены и правило максимального жевания

Лексер применяет **правило максимального жевания** (maximal munch): в каждой
позиции читается самый длинный токен, который может быть образован начиная с
неё.

Следствия:

| Текст | Токены |
|---|---|
| `<=` | `<=` (не `<` `=`) |
| `??` | `??` (не `?` `?`) |
| `?.` | `?.` (не `?` `.`) |
| `+=` | `+=` (не `+` `=`) |
| `3.foo` | `3` `.` `foo` — `3.` не является числовым литералом (§4.6) |
| `a?.b` | `a` `?.` `b` |
| `a ? .b` | `a` `?` `.` `b` — пробел разрывает `?.` |

Правило применяется к последовательности **соседних** байт. Пробельный символ
всегда завершает токен.

> **Про конфликт `?.` и тернарного оператора.** Запись `cond ?.5 : 1` могла бы
> читаться и как безопасный доступ, и как тернарный оператор с числом `.5`.
> Конфликта нет, потому что `.5` не является числовым литералом ChupaScript
> (§4.6): дробная часть требует цифр перед точкой. Запрет формы `.5` выбран в
> том числе ради этого свойства.

### 4.4 Идентификаторы

```
Identifier      ::= IdentifierStart IdentifierPart*    // кроме ReservedWord
IdentifierStart ::= [A-Za-z] | '_'
IdentifierPart  ::= [A-Za-z0-9] | '_'
```

Идентификаторы **ограничены ASCII**. Последовательность, совпадающая с
зарезервированным словом (§4.5), идентификатором не является — ключевое слово
имеет приоритет.

Ограничение касается только имён переменных. Ключи объектов — строковые литералы
и юникоду не препятствуют:

```
let имя = 1;            // ошибка
let x = obj['ключ'];    // корректно — строковый литерал
let y = obj.ключ;       // ошибка — после '.' требуется Identifier
```

> **Почему не UAX #31.** Юникодные идентификаторы требуют декодирования UTF-8
> перед каждой проверкой символа и таблиц свойств `XID_Start` / `XID_Continue` —
> десятки килобайт данных либо зависимость от ICU. Дополнительно они допускают
> визуально неразличимые имена (`а` U+0430 и `a` U+0061 — разные переменные),
> что в коде, приезжающем с сервера, является вектором маскировки.

### 4.5 Зарезервированные слова

Все перечисленные слова зарезервированы и не могут использоваться как
идентификаторы.

**Активные** — имеют значение в текущей грамматике:

```
let    var    true    false    null
```

**Зарезервированные на будущее** — грамматикой не используются, но запрещены как
идентификаторы:

```
if        else      while     for       in        break     continue  do
function  func      return
const     void      typeof
this      self      new       delete
switch    case      default
try       catch     throw
import    export    class
```

> **Почему резерв с запасом.** Цена ошибки асимметрична. Лишнее
> зарезервированное слово стоит автору макета одного переименования. Слово,
> которое зарезервировать забыли, будет использовано как имя переменной, макет
> уйдёт в продакшн — и в момент, когда конструкция появится в языке, этот макет
> перестанет компилироваться на устройствах, где приложение уже обновилось.
> Откатить это нельзя.

### 4.6 Числовые литералы

```
NumericLiteral ::= Digit+ ( '.' Digit+ )?
Digit          ::= [0-9]
```

Дробная часть, если есть, обязана содержать хотя бы одну цифру. Целая часть
обязательна всегда.

| Запись | Результат |
|---|---|
| `3` | корректно |
| `3.0` | корректно |
| `0.5` | корректно |
| `.5` | ошибка — нет целой части |
| `3.` | ошибка — нет дробной части |
| `1e3` | не число: токены `1` и `e3` |
| `0x1F` | не число: токены `0` и `x1F` |
| `1_000` | не число: токены `1` и `_000` |

**Знак в литерал не входит.** `-1` — это унарный оператор `-` и литерал `1`
(§5.3). Лексер никогда не включает знак в числовой токен, благодаря чему
остаётся независимым от контекста.

Реализация обязана конвертировать литерал через `std::from_chars` с
`std::chars_format::fixed`. Использование `strtod` запрещено: его поведение
зависит от локали, и в локали с запятой как десятичным разделителем `3.0`
разберётся как `3`.

### 4.7 Строковые литералы

```
StringLiteral ::= "'" SingleChar* "'"
                | '"' DoubleChar* '"'

SingleChar    ::= Escape | ( любой байт кроме  '  \  \n  \r )
DoubleChar    ::= Escape | ( любой байт кроме  "  \  \n  \r )

Escape        ::= '\' ( '\' | "'" | '"' | 'n' | 't' )
```

Обе формы кавычек равноправны и порождают одинаковые значения. Кавычка другого
вида внутри литерала экранирования не требует:

```
'он сказал "да"'        // корректно
"это 'цитата'"          // корректно
'C:\\Users'             // корректно, один обратный слэш в результате
'строка1\nстрока2'      // корректно
```

**Юникод.** Байты `>= 0x80` копируются в результат без интерпретации, поэтому
любой символ вписывается в литерал напрямую:

```
'Привет 😀'             // корректно
```

Юникодных escape-последовательностей (`\uXXXX`, `\u{...}`) в языке **нет**. Они
не требуются: символ вписывается напрямую, а для случаев, когда нужна явная
запись кода (невидимые символы), эту работу выполняет уровень JSON, через
который исходный текст доставляется.

> **Почему обе формы кавычек.** Исходный текст живёт внутри JSON-строки. Литерал
> в двойных кавычках требует там экранирования (`\"`), а обратный слэш внутри
> такого литерала — учетверения: `"format(\"C:\\\\Users\", n)"`. Одинарные
> кавычки убирают оба уровня: `"format('C:\\Users', n)"`.

### 4.8 Пунктуаторы и операторы

```
Punctuator ::= '(' | ')' | '[' | ']' | '{' | '}'
             | ',' | ':' | ';' | '.' | '?.' | '?'
             | '+'  | '-'  | '*'  | '/'  | '%'  | '!'
             | '='  | '+=' | '-=' | '*=' | '/='
             | '==' | '!=' | '<'  | '>'  | '<=' | '>='
             | '&&' | '||' | '??'
```

Любой байт, не начинающий ни один из перечисленных токенов и не являющийся
началом идентификатора, числа, строки или комментария, — ошибка лексера. В
частности, недопустимы `&`, `|`, `^`, `~`, `#`, `@`, `$`, `\` вне строкового
литерала, а также одиночные `&` и `|`.

### 4.9 Ранние ошибки лексера

Реализация обязана сообщать об ошибке в следующих случаях:

| Условие | Пример |
|---|---|
| Неизвестная escape-последовательность | `'\q'`, `'\u0041'` |
| Незавершённый строковый литерал | `'abc` до конца текста |
| Перевод строки внутри строкового литерала | `'abc` `\n` `def'` |
| Незавершённый блочный комментарий | `/* abc` до конца текста |
| Числовой литерал с точкой без дробной части | `3.` |
| Байт, не начинающий ни один токен | `@`, `#`, BOM |

> **Почему сырой перевод строки в литерале — ошибка.** Забытая закрывающая
> кавычка иначе поглотила бы весь остаток программы, и сообщение об ошибке
> указало бы на место, не имеющее отношения к причине.

## 5. Синтаксическая грамматика

Терминалы синтаксической грамматики — токены из §4. Пробельные символы и
комментарии на этом уровне не существуют.

### 5.1 Стартовые символы

Грамматика имеет **два стартовых символа**. Выбор делает вызывающая сторона; по
тексту программы режим не определяется.

```
Program    ::= Statement*        // режим скрипта:    runScript(source, ctx)
Expression ::= Ternary           // режим выражения:  evalExpression(source, ctx)
```

В обоих режимах после разбора стартового символа обязан следовать конец текста;
остаток — ошибка.

`Program` допускает ноль стейтментов. `Expression` требует ровно одно выражение и
**не допускает завершающей `;`** — стейтментов в этом режиме не существует.

Грамматика выражения является строгим подмножеством скриптовой: реализуется тем
же лексером и тем же парсером, отличается только точкой входа.

### 5.2 Стейтменты

```
Statement  ::= LetDecl | VarDecl | Assignment | CallStatement | EmptyStatement

LetDecl    ::= 'let' Identifier '=' Expression ';'
VarDecl    ::= 'var' Identifier '=' Expression ';'
Assignment ::= LeftHandSide AssignOp Expression ';'
CallStatement  ::= CallExpression ';'
EmptyStatement ::= ';'

AssignOp   ::= '=' | '+=' | '-=' | '*=' | '/='

LeftHandSide ::= Identifier ( '[' Expression ']' | '.' Identifier )*
```

Точка с запятой **обязательна**. Автоматической вставки точки с запятой (ASI) в
языке нет, поэтому переводы строк ни на что не влияют.

`LeftHandSide` допускает произвольную цепочку индексов и полей: `a`, `a[0]`,
`a.b`, `a.b[i].c` — все корректные цели присваивания. Безопасный доступ `?.` в
цели **запрещён** грамматикой: он не входит в `LeftHandSide`.

> **Почему присваивание — стейтмент, а не выражение.** В C и JavaScript
> присваивание является выражением, что делает `if (x = 1)` синтаксически
> корректным и порождает классический класс ошибок. Причина такого решения в C —
> необходимость писать `for (i = 0; ...; i++)`; у ChupaScript циклов нет, и
> причина отсутствует. Побочное следствие: в режиме выражения присваивания
> недоступны по построению, без единой дополнительной проверки.

### 5.3 Выражения

Правила перечислены от низшего приоритета к высшему. Каждое правило ссылается на
следующее, чем и задаётся приоритет.

```
Ternary        ::= LogicalOr ( '?' Expression ':' Expression )?
LogicalOr      ::= LogicalAnd ( '||' LogicalAnd )*
LogicalAnd     ::= Comparison ( '&&' Comparison )*
Comparison     ::= NilCoalesce ( CompOp NilCoalesce )?
NilCoalesce    ::= Additive ( '??' NilCoalesce )?
Additive       ::= Multiplicative ( ( '+' | '-' ) Multiplicative )*
Multiplicative ::= Unary ( ( '*' | '/' | '%' ) Unary )*
Unary          ::= ( '!' | '-' ) Unary | Postfix
Postfix        ::= Primary ( '[' Expression ']'
                           | '.'  Identifier
                           | '?.' Identifier )*

CompOp         ::= '==' | '!=' | '<' | '>' | '<=' | '>='

Primary        ::= NumericLiteral | StringLiteral | BooleanLiteral | NullLiteral
                 | ArrayLiteral | ObjectLiteral
                 | CallExpression
                 | Identifier
                 | '(' Expression ')'

CallExpression ::= Identifier '(' ArgumentList? ')'
ArgumentList   ::= Expression ( ',' Expression )*

ArrayLiteral   ::= '[' ( Expression ( ',' Expression )* )? ']'
ObjectLiteral  ::= '{' ( ObjectEntry ( ',' ObjectEntry )* )? '}'
ObjectEntry    ::= StringLiteral ':' Expression

BooleanLiteral ::= 'true' | 'false'
NullLiteral    ::= 'null'
```

**Вызов — это выражение.** `CallExpression` входит в `Primary`, поэтому вызов
может быть операндом: `count(arr) + 1`. Отдельная продукция `CallStatement`
(§5.2) лишь разрешает выражению-вызову стоять отдельным стейтментом; второго
вида вызова в языке нет.

**Вызывать можно только именованный билтин.** Форма `obj.f(x)` грамматикой не
предусмотрена, поскольку функция не является значением языка.

**Ключи в литерале объекта — только строковые литералы.** `{ x: 1 }` и
`{ [k]: 1 }` некорректны. Значения — произвольные выражения.

**Висячая запятая запрещена** во всех списках: `[1, 2,]`, `{ 'a': 1, }`,
`f(a, b,)` — ошибки.

### 5.4 Приоритет и ассоциативность

Порядок соответствует Swift.

| Уровень | Операторы | Ассоциативность |
|---|---|---|
| 1 (низший) | `? :` | правая |
| 2 | `\|\|` | левая |
| 3 | `&&` | левая |
| 4 | `==` `!=` `<` `>` `<=` `>=` | **нет** |
| 5 | `??` | правая |
| 6 | `+` `-` | левая |
| 7 | `*` `/` `%` | левая |
| 8 | `!` `-` (унарные) | правая |
| 9 (высший) | `[]` `.` `?.` `()` | левая |

Уровень 4 **неассоциативен**: `a < b < c` — синтаксическая ошибка. В правиле
`Comparison` квантификатор `?`, а не `*`, поэтому второе сравнение подряд не
разбирается.

> **Почему сравнения неассоциативны.** При левой ассоциативности `a < b < c`
> разобралось бы как `(a < b) < c`, то есть «сравнить булево значение с числом»
> — почти всегда не то, что имел в виду автор. Swift принимает то же решение
> (группа `ComparisonPrecedence` объявлена `associativity: none`).

Обратите внимание на положение `??` **выше** сравнений:

```
a ?? b == c      разбирается как  (a ?? b) == c
a ?? b + c       разбирается как  a ?? (b + c)
a ?? b ?? c      разбирается как  a ?? (b ?? c)
```

### 5.5 Ранние ошибки парсера

| Условие | Пример |
|---|---|
| Два сравнения подряд | `a < b < c` |
| Висячая запятая | `f(a, b,)`, `[1, 2,]`, `{ 'a': 1, }` |
| Ключ объекта не строковый литерал | `{ x: 1 }` |
| `?.` в цели присваивания | `a?.b = 1;` |
| Текст после стартового символа | `1 + 1 2` в режиме выражения |
| `;` в режиме выражения | `a + b;` |
| Стейтмент, не сводящийся ни к одной продукции | `a + 1;`, `user.name;` |

## 6. Статические проверки после разбора

Правила, требующие информации за пределами грамматики. Проверяются после
построения дерева, до исполнения.

### 6.1 Результат вызова в позиции стейтмента

`CallStatement` допускает **только вызов билтина, не возвращающего значения**.
Вызов билтина, возвращающего значение, в позиции стейтмента — ошибка
компиляции «результат не используется».

```
push(arr, 1);              // корректно  — push значения не возвращает
count(arr);                // ошибка     — результат не используется
let n = count(arr);        // корректно  — результат использован
setValueForKey(o, 'k', count(arr));   // корректно — вложенный вызов
```

Проверке подлежит только вызов, являющийся **корнем** `CallStatement`; вложенные
вызовы находятся в позиции выражения и под правило не подпадают.

`Void` — внутренняя пометка компилятора, а не тип значения. Языку она не видна:
`let n = push(arr, 1);` отвергается, а не даёт `n` какое-либо значение.

### 6.2 Использование результата вызова

Аналогично: `let n = push(arr, 1);`, `f(push(arr, 1))`, `push(arr,1) + 1` —
ошибки компиляции по той же причине.

### 6.3 Чистота режима выражения

В режиме `Expression` вызов билтина, помеченного как **мутирующий**, — ошибка
компиляции. К мутирующим относятся, в частности, `push`, `pop`,
`setValueForKey`.

Присваивания в этом режиме недоступны грамматически (§5.2), отдельной проверки
не требуют.

Ограничение оставляет за хостом право кэшировать значения props, вычислять их
лениво, вне порядка обхода дерева и пропускать для невидимых вьюх.

### 6.4 Однократное вычисление цели составного присваивания

Составное присваивание к сложной цели обязано вычислять подвыражения цели
**ровно один раз** и переиспользовать результат для чтения и для записи.

```
arr[idx()] += 1;
```

Наивное раскрытие в `arr[idx()] = arr[idx()] + 1` вызвало бы `idx()` дважды.
Требуемая схема:

```
tmp = idx()
arr[tmp] = arr[tmp] + 1
```

## 7. Свойства грамматики

Раздел для тех, кто реализует лексер и парсер.

**Лексер не зависит от контекста.** Ни одно лексическое решение не требует
знания о том, что разбирает парсер. Достигнуто тремя решениями: знак не входит в
числовой литерал; формы `.5` и `3.` запрещены; переводы строк не значимы.
Следствие — лексер является конечным автоматом, работает за один проход без
откатов и не нуждается в обратной связи от парсера.

**Грамматика однозначна.** Все конфликты токенов разрешаются правилом
максимального жевания (§4.3). Синтаксических неоднозначностей нет.

**`{` не может начинать стейтмент.** Блочного стейтмента в языке нет, `ObjectLiteral`
встречается только в позиции выражения. Поэтому классическая для JavaScript
неоднозначность «блок или литерал объекта» отсутствует, и парсер не нуждается в
специальном правиле для начала стейтмента.

**Класс грамматики — LL(1) везде, кроме начала стейтмента.** Стейтменты
`Assignment` и `CallStatement` оба начинаются с `Identifier`; для различения
достаточно одного дополнительного токена (`(` против `[`, `.`, `=`, `+=`, …).
Рекомендуемая стратегия реализации — разобрать постфиксную цепочку, затем
классифицировать по следующему токену: `AssignOp` даёт `Assignment`, `;` требует,
чтобы разобранный узел был `CallExpression`.

**Выражения разбираются восхождением по приоритету** (precedence climbing) —
таблица §5.4 переносится в код напрямую, отдельная функция на уровень не нужна.

**Любая программа завершается.** В языке нет ни циклов, ни рекурсии, ни
пользовательских функций. Число исполняемых шагов ограничено сверху размером
программы. Недоверенный исходный текст не может подвесить исполнение, и рантайму
не требуются ни счётчик шагов, ни watchdog. Свойство будет утрачено при
добавлении `while` и сохранено при добавлении `for-in`.

**Строковые литералы допускают zero-copy.** Литерал без единого символа `\` в
результате совпадает с фрагментом исходного текста побайтово, и представим
парой «указатель + длина» без копирования. Это накладывает на рантайм
требование: буфер с исходным текстом обязан пережить скомпилированную программу.

## 8. Умышленные отсутствия

Перечисленного в языке нет намеренно. Раздел существует, чтобы отсутствие не
принималось за упущение.

| Отсутствует | Причина | Добавление сломает существующие макеты |
|---|---|---|
| `if` / `else` | отложено | нет — слова зарезервированы |
| `for` / `while` | отложено; `while` уничтожает гарантию завершения (§7) | нет — слова зарезервированы |
| `return` | без ветвления ранний выход бессмыслен | нет — слово зарезервировано |
| Пользовательские функции | отложено | нет — слова зарезервированы |
| Общий expression-statement (`a + 1;`) | почти всегда опечатка вместо `+=` или присваивания | нет |
| Присваивание как выражение | порождает `if (x = 1)` | да — не добавлять |
| Метод-подобный вызов `a.f(b)` | расщепил бы `obj.push` и `obj['push']`, заявленные эквивалентами | нет |
| Юникодные escape (`\uXXXX`) | символ вписывается напрямую; явная запись доступна на уровне JSON | нет |
| Экспонента в числах (`1e3`) | усложняет лексер, в разметке не востребована | нет |
| Шестнадцатеричные числа, разделители разрядов | то же | нет |
| Формы `.5` и `3.` | делают лексер контекстно-зависимым, конфликтуют с `?.` | нет |
| `?[ ]` (безопасный индекс) | неразрешимо без чувствительности лексера к пробелам: `a ? [1] : [2]` и `a ?[1]` — одни токены | нет |
| Цепочки сравнений | `(a < b) < c` — сравнение булева с числом | нет |
| Висячая запятая | `f(a, b,)` вероятнее незаконченная правка | нет |
| Вложенные блочные комментарии | не требуются | нет |
| Автовставка `;` (ASI) | делает переводы строк значимыми | нет |
| Битовые операторы, `++`, `--` | не востребованы разметкой | нет |
| Юникод в идентификаторах | таблицы UAX #31; визуально неразличимые имена | нет |

## Приложение A. Сводная грамматика

Полная грамматика без пояснений.

### A.1 Лексическая

```
Token           ::= Identifier | Keyword | NumericLiteral | StringLiteral
                  | BooleanLiteral | NullLiteral | Punctuator

Whitespace      ::= ' ' | '\t' | '\n' | '\r'
LineComment     ::= '//' ( кроме '\n' )*
BlockComment    ::= '/*' ( любой байт )* '*/'

Identifier      ::= IdentifierStart IdentifierPart*        // кроме ReservedWord
IdentifierStart ::= [A-Za-z] | '_'
IdentifierPart  ::= [A-Za-z0-9] | '_'

NumericLiteral  ::= Digit+ ( '.' Digit+ )?
Digit           ::= [0-9]

StringLiteral   ::= "'" SingleChar* "'" | '"' DoubleChar* '"'
SingleChar      ::= Escape | ( любой байт кроме  '  \  \n  \r )
DoubleChar      ::= Escape | ( любой байт кроме  "  \  \n  \r )
Escape          ::= '\' ( '\' | "'" | '"' | 'n' | 't' )

BooleanLiteral  ::= 'true' | 'false'
NullLiteral     ::= 'null'

Punctuator      ::= '(' | ')' | '[' | ']' | '{' | '}'
                  | ',' | ':' | ';' | '.' | '?.' | '?'
                  | '+'  | '-'  | '*'  | '/'  | '%'  | '!'
                  | '='  | '+=' | '-=' | '*=' | '/='
                  | '==' | '!=' | '<'  | '>'  | '<=' | '>='
                  | '&&' | '||' | '??'

ReservedWord    ::= 'let' | 'var' | 'true' | 'false' | 'null'
                  | 'if' | 'else' | 'while' | 'for' | 'in' | 'break'
                  | 'continue' | 'do'
                  | 'function' | 'func' | 'return'
                  | 'const' | 'void' | 'typeof'
                  | 'this' | 'self' | 'new' | 'delete'
                  | 'switch' | 'case' | 'default'
                  | 'try' | 'catch' | 'throw'
                  | 'import' | 'export' | 'class'
```

### A.2 Синтаксическая

```
Program         ::= Statement*
Expression      ::= Ternary

Statement       ::= LetDecl | VarDecl | Assignment | CallStatement | EmptyStatement
LetDecl         ::= 'let' Identifier '=' Expression ';'
VarDecl         ::= 'var' Identifier '=' Expression ';'
Assignment      ::= LeftHandSide AssignOp Expression ';'
CallStatement   ::= CallExpression ';'
EmptyStatement  ::= ';'

AssignOp        ::= '=' | '+=' | '-=' | '*=' | '/='
LeftHandSide    ::= Identifier ( '[' Expression ']' | '.' Identifier )*

Ternary         ::= LogicalOr ( '?' Expression ':' Expression )?
LogicalOr       ::= LogicalAnd ( '||' LogicalAnd )*
LogicalAnd      ::= Comparison ( '&&' Comparison )*
Comparison      ::= NilCoalesce ( CompOp NilCoalesce )?
NilCoalesce     ::= Additive ( '??' NilCoalesce )?
Additive        ::= Multiplicative ( ( '+' | '-' ) Multiplicative )*
Multiplicative  ::= Unary ( ( '*' | '/' | '%' ) Unary )*
Unary           ::= ( '!' | '-' ) Unary | Postfix
Postfix         ::= Primary ( '[' Expression ']'
                            | '.'  Identifier
                            | '?.' Identifier )*

CompOp          ::= '==' | '!=' | '<' | '>' | '<=' | '>='

Primary         ::= NumericLiteral | StringLiteral | BooleanLiteral | NullLiteral
                  | ArrayLiteral | ObjectLiteral
                  | CallExpression | Identifier
                  | '(' Expression ')'

CallExpression  ::= Identifier '(' ArgumentList? ')'
ArgumentList    ::= Expression ( ',' Expression )*

ArrayLiteral    ::= '[' ( Expression ( ',' Expression )* )? ']'
ObjectLiteral   ::= '{' ( ObjectEntry ( ',' ObjectEntry )* )? '}'
ObjectEntry     ::= StringLiteral ':' Expression
```

## Приложение B. Примеры разбора

### B.1 Режим выражения

```
user.name ?? 'Гость'
```

```
Expression
└── NilCoalesce '??'
    ├── Postfix
    │   ├── Primary → Identifier 'user'
    │   └── '.' Identifier 'name'
    └── Primary → StringLiteral 'Гость'
```

### B.2 Приоритеты

```
a + b * c == d
```

```
Comparison '=='
├── NilCoalesce → Additive '+'
│   ├── Multiplicative → Unary → Postfix → Identifier 'a'
│   └── Multiplicative '*'
│       ├── Identifier 'b'
│       └── Identifier 'c'
└── NilCoalesce → Identifier 'd'
```

### B.3 Вызов в трёх позициях

```
let n = count(arr);                   // CallExpression внутри LetDecl
total = count(arr) + 1;               // CallExpression как операнд '+'
push(arr, 1);                         // CallStatement
```

Во всех трёх строках вызов — один и тот же узел `CallExpression`. Различается
только то, во что он вложен.

### B.4 Что стейтментом не является

```
x + builtin_rand()
```

Корень дерева — `Additive '+'`. Ни одна продукция `Statement` не подходит:
`LetDecl` и `VarDecl` требуют ключевого слова, `Assignment` требует `AssignOp`,
`CallStatement` требует, чтобы корнем был `CallExpression`. В режиме скрипта —
синтаксическая ошибка; в режиме выражения — корректная программа.

### B.5 Программа целиком

```
var items = getValueForKey(state, 'items');
push(items, product);
setValueForKey(state, 'badge', count(items));
items[count(items) - 1] += 1;
```

| Строка | Продукция |
|---|---|
| 1 | `VarDecl` |
| 2 | `CallStatement` — `push` значения не возвращает |
| 3 | `CallStatement` — `setValueForKey` не возвращает; `count` вложен как аргумент |
| 4 | `Assignment` с `AssignOp` `+=`; цель вычисляется однократно (§6.4) |

## Приложение C. Незакрытые области

Грамматика зафиксирована полностью. Перечисленное относится к другим слоям и
влияет на этот документ только косвенно.

**Семантика:** представление `Number`; что именно является ссылочным и как
обрабатываются циклы ссылок; запрещает ли `let` переприсваивание биндинга или
мутацию содержимого; приведение типов; модель ошибок времени выполнения; что
возвращают `?.` и `??`, а также обращение к отсутствующему ключу и выход за
границы массива — единственное «пусто» в языке — `null`.

**Билтины:** полный набор и сигнатуры; пометка «мутирует» (используется §6.3);
отдельная пометка «детерминирован» — `builtin_date()` ничего не мутирует, но
возвращает разное, и кэш props обязан это различать; синтаксис `format`; единица
измерения `len` для строк.

**Рантайм:** способ передачи контекста в программу и возврата результатов хосту;
кэш скомпилированных программ; время жизни буфера исходного текста (§7).
