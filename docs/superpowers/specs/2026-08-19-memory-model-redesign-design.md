# ChupaScript: модель памяти — переработка

## 1. Область документа

Модель памяти движка целиком: представление значения, владение, время жизни,
аллокация и граница с хостом. Проектируется заново, не наследуя решений
текущей реализации там, где они не выдерживают проверки.

Неизменной остаётся **семантика языка**: `docs/semantics.md` и
`docs/grammar.md` не меняются ни в одном пункте. Что программа вычисляет —
зафиксировано; как это хранится — предмет этого документа.

Отменяет: `docs/superpowers/specs/2026-08-19-chupascript-memory-model-design.md`
(разделы Р1–Р11) и план `docs/superpowers/plans/2026-08-19-store-arena-split.md`.
Предшествующий документ описывал промежуточное состояние — переход от арен к
счётчику ссылок — и местами формулирует задачи как ещё не сделанные. Здесь
описано целевое состояние.

## 2. Постановка

### 2.1 Что не так с нынешней реализацией

Модель памяти перестраивалась трижды: арены → водяная метка ([B1]) → регионы
([B57]) → счётчик ссылок. Каждая перестройка сносила механику, но оставляла
**абстракции, скроенные под предыдущую модель**. В итоге типы и сигнатуры
отвечают на вопросы, которых в текущей модели уже не существует.

Остатки, найденные аудитом:

| остаток | под какую модель скроен |
|---|---|
| `Store::Role` — два типа в одном классе | арены: оба экземпляра были хранилищами |
| `applyBinary` берёт два хранилища | две арены: операнды могли лежать в разных |
| ветка `Boxed` в `Store::string` | арены: у значения было хранилище-владелец |
| `Execution` держит `Store scratch` + `Store &` | то же |
| `Value::length_` | арены: длина среза не хранилась больше нигде |

`Value::length_` пишется в двух местах и читается в одном —
`store.cpp:89`, ветка `Region::Scratch`. У коробки длина своя (`StringBox::len`).

### 2.2 Найденные дефекты

**Б1. `Context::setGlobal` продвигает значение из арены, которую сам только
что стёр.**

```cpp
void setGlobal(std::string_view name, Value v) {
    beginOperation();                                 // exec_.scratch.clear()
    store_.setGlobal(name, exec_.promote(v), ...);    // promote читает scratch
}
```

`promote` для строки региона `Scratch` зовёт `scratch.string(v)` → `textAt` по
усечённому пулу → `text_.empty()` → пустой срез. Строка молча становится
пустой. `assert(materialized(v))` внутри `setGlobal` не срабатывает: он
проверяет результат `promote`, а тот честно коробка — просто пустая.

Воспроизведено (`probe.cpp` против `build-dbg`, 19.08.2026):

```
сразу после eval:            'привет, Вася'
  kind=3 region=1 (0=Boxed, 1=Scratch)
после setGlobal('saved', v): ''  (длина 0)
```

Через C API сегодня недостижимо: `chupa_context_set_bool/_number` передают
только скаляры, `set_string` идёт через `setGlobalString`. Но метод публичный,
принимает произвольный `Value`, и контракта на нём не записано.

**Б2. `Context::store()` отдаёт хранилище наружу изменяемым.** Инвариант
«всякая запись в корень происходит внутри операции» держится на дисциплине
вызывающих, а не на типе.

**В1. Гонка в счётчике живых коробок.** `box.cpp:14` — процессно-глобальный
`static std::size_t g_liveBoxes` без атомарности. Контракт разрешает двум
контекстам работать на двух потоках; счётчик у них общий.

**В2. Выражение чужого контекста молча читает чужую ячейку.** Номер ячейки
разрешается на компиляции и адресует `globalValues_` конкретного хранилища.
Несовпадение ловит `assert` (`store.cpp:158`) — то есть только отладочная
сборка. В релизе вернётся чужое значение либо мусор.

### 2.3 Где движок проигрывает по скорости

Единственное место — строки. По замерам BDUI от 17.08.2026
(`docs/benchmarks/bdui-after-borrowed-string-2026-08-17.md`, отношения
«прежняя реализация / движок», больше единицы — выигрывает движок):

| кейс | нс | отношение |
|---|---|---|
| константа: число, флаг | 2.3 | 4.38 |
| отображение, попадание | 52.0 | 4.10 |
| переменная: число | 11.0 | 1.51 |
| **интерполяция** | 141.8 | **0.85** |
| **переменная: строка** | 26.7 | **0.69** |

Замер сделан **до** прихода счётчика ссылок. Счётчик добавил `malloc` на
каждую строку, попадающую в агрегат, — там, где раньше был бамп в арене.
Пост-замера нет.

### 2.4 Требования

1. Одно правило времени жизни вместо четырёх.
2. Дефекты Б1, Б2, В1, В2 закрыты **устройством**, а не проверкой.
3. Строки перестают быть слабым местом.
4. `sizeof(Value) == 16` и тривиальная копируемость сохраняются.
5. Семантика языка не меняется.

## 3. Global Constraints

Требования, действующие на весь код этой работы.

**К1. Язык комментариев — английский**, технический регистр. Публичный
заголовок `chupascript.h` и все `Diagnostic::message` уже английские;
комментарии внутри становятся с ними одноязычными. Правило распространяется на
**новый и переписанный** код; файлы, эта работа не затрагивающие
(`lexer`, `parser`, `ast`, `check`, `operator`, `builtin`), остаются с
русскими комментариями до своей очереди.

Явно: правило связывает **новые и переписанные куски**, а не файлы целиком.
Файл, задетый этой работой лишь частично, не обязан стать англоязычным
полностью — обязаны быть английскими только куски, которые эта работа
добавила или переписала. Так и вели себя все одиннадцать задач плана. Из
этого следует, что несколько заголовков остаются двуязычными — старый
русский текст соседствует с новым английским, — и это отдельная, самим этим
правилом не покрываемая работа: довести их до одного языка целиком.

**К2. Схема раскладки первой.** Всякий тип, который чем-то владеет,
начинается с диаграммы: что где лежит и кто чему хозяин.

**К3. Каждое существительное — названная сущность.** Не «то, что заводит
хост», а `the global variables the host defines`.

**К4. У всякого утверждения о времени жизни названы оба конца.** Не «живёт
столько же», а `is destroyed with the Context that owns it`.

**К5. Одна строка на неочевидное решение**, и в ней — отвергнутая
альтернатива с причиной. Не «почему так хорошо», а «почему не иначе».

**К6. Повествование о ходе мысли — в этот документ и в сообщение коммита**,
не в заголовок типа.

Образец, задающий планку:

```cpp
/// Per-context state that outlives every evaluation: the global variables the
/// host defines, and the field-name table that objects intern their keys into.
/// A Store is owned by exactly one Context and is destroyed with it.
///
///   Store
///    ├── names_    TextPool             global-variable name bytes, append-only
///    ├── slots_    vector<GlobalName>   name -> slot, sorted by name bytes
///    ├── values_   vector<Value>        slot -> value; a ROOT: holds one reference
///    └── keys_     KeyTable*            field names, shared with every ObjectBox
///
/// A slot index stays valid for the lifetime of its Store: values_ only grows
/// and its elements never move. check() therefore resolves a name to a slot
/// once, during compilation, and eval() indexes values_ directly (check.cpp).
///
/// The value lives in values_ rather than in the GlobalName record because
/// inserting a name shifts slots_ to keep it sorted; a shifted record would
/// invalidate a slot index that compilation has already handed out.
```

**К7. Прочие ограничения.** C++17, без расширений компилятора.
`static_assert(sizeof(Value) == 16)` и
`static_assert(is_trivially_copyable_v<Value>)` не снимаются.

## 4. Принятые решения

### Р1. Всякое `Value` самодостаточно

> Прочитать значение можно всегда и где угодно, в том числе когда контекста,
> породившего его, уже нет.

Это единственное правило времени жизни в модели. Всё остальное — следствия.

Отменяет три правила, которые приходилось держать в голове одновременно: «в
каком регионе значение», «пережило ли оно границу операции», «надо ли его
продвигать перед записью».

### Р2. Раскладка `Value`: встроенные короткие строки, шестнадцать байт

```
        0        1                                              15
      ┌────┬────────────────────────────────────────────────────┐
Inline│ tag│ b0 b1 b2 b3 b4 b5 b6 b7 b8 b9 b10 b11 b12 b13 b14  │  строка ≤15 байт
      └────┴────────────────────────────────────────────────────┘
      ┌────┬───────────────────┬───────────────────────────────┐
Number│ tag│      набивка      │            double             │
      └────┴───────────────────┴───────────────────────────────┘
      ┌────┬───────────────────┬───────────────────────────────┐
Boxed │ tag│      набивка      │           Box *               │  строка >15, массив, объект
      └────┴───────────────────┴───────────────────────────────┘
      ┌────┬─┐
Bool  │ tag│b│                                     Null: только tag
      └────┴─┘
```

Байт `tag`:

```
   бит  7   6 5 4 3   2 1 0
        │   └───┬───┘ └─┬─┘
        │       │       └── вид: Null 0, Boolean 1, Number 2,
        │       │            String 3, Object 4, Array 5
        │       └────────── длина встроенной строки, 0..15;
        │                    осмысленна только при виде String
        └────────────────── строка встроенная (1) либо коробка (0);
                             осмыслен только при виде String
```

Реализация — объединение двух раскладок, обе по шестнадцать байт:

```cpp
struct Inline { std::uint8_t tag; char bytes[15]; };
struct Wide   { std::uint8_t tag; std::uint8_t pad[7];
                union { double number; bool flag; detail::Box *box; }; };
union { Inline inline_; Wide wide_; };
```

`tag` лежит нулевым байтом в обеих и читается через любую: у стандартно
раскладываемых структур с общим начальным подмножеством это определённое
поведение ([class.mem]). Выравнивание задаёт `double` — восемь; размер
объединения шестнадцать.

**Байты за пределами длины у встроенной строки обнулены.** Это инвариант, а не
случайность: он делает равенство двух встроенных строк сравнением двух
восьмибайтовых слов, без обращения к длине и без `memcmp`.

**Почему не NaN-boxing (B2).** Восемь байт целиком уходят под `double` и теги;
места под байты строки не остаётся, и каждая строка осталась бы аллокацией.
Замеры BDUI называют строки единственным слабым местом движка — представление
выбирается под них. B2 закрывается насовсем.

**Почему пятнадцать.** Столько остаётся от шестнадцати после байта тега. В
разобранных макетах BDUI в этот предел укладывается большинство строк: ключи,
цвета (`#FF0000`), идентификаторы, `center`, `medium`, короткие подписи, а
также почти всякий результат `str` над числом.

**Что это отменяет:**

| было | стало |
|---|---|
| `Value::Region::Scratch` | нет |
| `Value::length_` | нет — длина в теге либо в коробке |
| `Execution::promote` | нет |
| `detail::materialized` и четыре `assert` на него | нет |

### Р3. Арены операции нет

Со встроенными строками у арены не остаётся работы: результаты `str` над
числом почти всегда короче пятнадцати байт и становятся встроенными.
Остаются длинные результаты `format` — ради них отдельный регион не окупается.

**Что уходит вместе с ареной:** `Store::Role`, `Store::clear`,
`Store::clearSlow`, `Store::makeString`, `Store::string`, весь набор сборки
строк у `Store`, правило «строка годна до следующей операции» и дефект Б1 —
последний **невыразим по построению**: продвигать нечего, стирать нечего.

**Граница операции сжимается до двух строк:**

```
   было                                 стало
   scratch.clear()                      deferred_.drain()
   deferred_.drain()                    release(lastResult_)
```

**Цена.** `format`, дающий результат длиннее пятнадцати байт, платит
аллокацию вместо бампа. Взамен исчезает подсистема и класс дефектов.

**Сборщик строк остаётся, но регионом не является.** `format` по-прежнему
нужен растущий буфер: длина результата заранее неизвестна.

```
   АРЕНА (была)                     СБОРЩИК (стал)
   на неё указывают Value           на него не указывает ничто
   живёт до границы операции        живёт до конца одного endString
   сброс — часть модели памяти      сброс — деталь одной функции
```

Буфер переезжает в `Execution` обычным членом. Ёмкость между операциями
сохраняется — тот же выигрыш, что давала арена, без её роли в модели.
Вложенная сборка держится тем же приёмом (метка — позиция, не указатель) и по
той же причине: рост буфера переселяет данные.

### Р4. Коробки: три вида, хвостовое размещение, без слэба

```
   Box                       8 байт
  ┌────────────┬────┬───────┐
  │ rc  uint32 │kind│ 3 сво-│
  │            │u8  │ бодны │
  └────────────┴────┴───────┘
```

Виртуальных функций нет: видов ровно три, список закрыт спецификацией языка,
`release` разбирает их `switch`'ем. Vtable удвоил бы заголовок ради
расширяемости, которой у языка не бывает.

**Агрегат — одна аллокация вместо двух.** Сегодня агрегат стоит две: сама
коробка и буфер `std::vector` внутри неё. Убирается тем же приёмом, которым
уже сделан `StringBox`, — хвостом за заголовком:

```
   ArrayBox                              одна аллокация
  ┌──────────────────────────────┐
  │ rc, kind                     │ Box
  │ len, cap                     │
  │ data ──────────┐             │      указывает в хвост, пока хватает cap;
  ├────────────────▼─────────────┤      после роста — на отдельный буфер
  │ Value  Value  Value  ...     │ хвост, cap штук
  └──────────────────────────────┘
```

**Адрес коробки не меняется никогда**, даже когда массив перерос хвост:
двигается только `data`. Поэтому все `Value`, указывающие на эту коробку,
остаются верными — чего нельзя было бы добиться, растя саму коробку.

Для литералов хвост подходит точно: размер известен заранее, и `makeArray`
уже сегодня выделяет по точной ёмкости. `[1, 2, 3]` и `{'a': 1, 'b': 2}` —
ровно одна аллокация; рост случается только у массива, растимого через `push`.

`ObjectBox` устроен так же, хвост из `Entry`.

**Слэб-аллокатора не будет.** После Р2 и Р3 ни один горячий путь BDUI не
аллоцирует вовсе:

| кейс из замера | аллокаций после Р2–Р4 |
|---|---|
| константа: число, флаг | 0 |
| переменная: число | 0 |
| переменная: строка ≤15 байт | 0 |
| отображение, попадание | 0 |
| интерполяция, результат ≤15 байт | 0 |
| константа: строка длинная | 0 — литерал уложен на компиляции |

Аллокация остаётся у построения литерала-агрегата и у длинных строк. Пул при
этом стоил бы настоящей сложности: коробки переживают свой контекст, значит
пул нельзя разрушить вместе с ним — нужен либо указатель на пул в каждой
коробке (+8 байт), либо выравнивание слэбов и маскирование адреса.

**Порог пересмотра называется заранее:** если после всех правок
`BM_Eval_ArrayLiteral` или `BM_Eval_ObjectLiteral` окажутся в верху профиля
живого экрана — возвращаемся к вопросу.

### Р5. Владение: три отношения

```
КОРНИ — держат ссылку:
   ячейка глобальной переменной   Store::values_
   коробка-литерал                Ast::literals_          (Р6)
   ячейка последнего результата   Context::lastResult_    (Р9)
   хост                           chupa_value_retain

СОДЕРЖАНИЕ — родитель держит ребёнка:
   ArrayBox   элементы
   ObjectBox  значения пар

ОТЛОЖЕННОЕ — держит до ближайшей границы, корнем не является:
   Deferred   ссылка новорождённого + всякая вытесненная
```

`Deferred` не меняется. Его довод от арены не зависел: вычислитель держит
прочитанные значения голым `Value` без RAII, и освобождение вытесненного на
месте уронило бы счётчик в ноль между чтением и записью (`x = a.pop()`).
Меняется только нагрузка — короткие строки в список не попадают вовсе, им
нечего отпускать.

### Р6. Литералы принадлежат `Ast`, а не `Store`

Сегодня коробки строковых литералов лежат в `Store::literals_`, и это одна из
двух причин, почему скомпилированная единица годна только своему контексту.
Причина слабая: литерал — часть **программы**, а не состояния контекста.

```
   БЫЛО                                  СТАЛО
   Ast.node.literal ──┐                  Ast
                      ▼                   ├── nodes_
   Store::literals_ ──> StringBox         ├── children_
                                          └── literals_ ──> StringBox
```

Связь единицы с контекстом остаётся одна — номера ячеек глобальных, — и она
честная (Р10 её проверяет).

**Литералы остаются коробками, а не встроенными, даже короткие.** Узел дерева
— 24 байта, из них под литерал отведено 8, а встроенное `Value` требует 16;
растить узел нельзя, за его ужатие уже заплачено. И коробка литералу
подходит лучше: байты существуют в одном экземпляре на всю жизнь единицы, а
попадание в агрегат стоит инкремента счётчика вместо копии байт.

### Р7. Что остаётся от `Store`

```
                     ДО                          ПОСЛЕ
text_                имена + промежуточные       names_: только имена
build_               черновик format             → Execution::builder_
keys_                KeyTable*                   keys_: без изменений
literals_            коробки литералов           → Ast::literals_    (Р6)
globalNames_         имя → номер                 slots_
globalValues_        номер → значение            values_
Role                                             нет
makeString                                       нет
begin/append/end/abortString                     → Execution::builder_
string(Value)                                    нет — значение читает себя само
clear / clearSlow                                нет
```

Одиннадцать сущностей превращаются в четыре, и все четыре про одно:
глобальные переменные и имена.

### Р8. Чтение строки — одна свободная функция

```
   stringBytes(Value v)
       tag говорит «встроенная»  →  байты в самом v
       иначе                     →  box->view()
```

Ни хранилища, ни арены, ни контекста в вопросе. Пять нынешних входов в одно и
то же — `Store::string`, `Execution::string`, `Context::string`,
`coerceScalarToString`, ручной каст в `c_api.cpp:397` — сходятся сюда.

### Р9. `Context` и `Execution`

```
                    ДО                              ПОСЛЕ

  Context                                Context
   ├── Store store_                       └── Store      store_      globals, keys, uint32 id_ (Р10)
   └── Execution exec_                         └── Execution exec_
        ├── Store scratch      ← ушла               ├── Value    lastResult_ корень
        ├── Deferred deferred_                       ├── Deferred deferred_
        └── Store &persistent_                       ├── Builder  builder_
                                                       └── Store &store_
```

`Execution` остаётся отдельным типом, и довод у него теперь один, зато
твёрдый: **вычислитель не должен уметь открыть границу операции.**
`Context::beginOperation` приватен, а `eval` видит только `Execution`, где
`drain()` недостижим. Вызови `eval` границу посреди выражения — она отпустила
бы живые промежуточные значения. Тип это запрещает. Прежний довод
(«вынесено, чтобы единицу можно было разделять между вьюшками») остаётся
верным, но становится вторым по важности.

`Context::store()` наружу изменяемым больше не отдаётся — это дефект Б2.
Наружу выставляются только те операции, что нужны оболочке и C API, и каждая
из них — операция с границей.

**`lastResult_` — корень для заимствованных байт.** Ярлык `chupa_eval_string`
отдаёт указатель на байты результата. Для встроенной строки байты лежат внутри
значения, и локальная переменная внутри `c_api.cpp` умерла бы на выходе.
Результат кладётся в `lastResult_`, откуда байты и заимствуются; следующий
вызов перезаписывает ячейку и отпускает прежнее. Контракт заголовка — «байты
живы до следующего вызова, трогающего контекст» — выполняется буквально и
теперь по одной причине вместо трёх.

### Р10. Единица помнит свой контекст

Дефект В2. Четыре байта закрывают его целиком:

```
   Store        id_  uint32   ← монотонный, выдаётся при создании
   Expression   id   uint32   ← id хранилища, на котором компилировали

   chupa_eval:  id не совпал → false, ChupaError{CHUPA_ERR_USAGE, ...}
```

Идентичность лежит на `Store`, а не на `Context`: номера ячеек, против
которых единица проверяется при вычислении, — это адреса в пространстве
слотов `Store` (`Store::values_`), а пространство слотов принадлежит
хранилищу, а не паре «хранилище плюс исполнитель». Совпадение `id_`
проверяет ровно то, что должно совпасть, — не больше и не меньше.

Одно сравнение на вычисление против молчаливо неверного результата в проде.
Код `CHUPA_ERR_USAGE` уже существует и сейчас не используется ни разу.

### Р11. Потоковый контракт — в заголовок

Дефект В1. Контракт закрепляется: **контекст — единица однопоточности.** Один
контекст — не более одного потока в момент времени; два разных контекста на
двух потоках — законно.

Счётчик живых коробок нужен только тестам и существует только в отладочной
сборке:

```cpp
/// Number of live boxes in this process. Debug builds only: a leaked box is
/// invisible to every other metric, since box memory belongs to no Store.
///
/// Atomic because two Contexts may run on two threads (chupascript.h,
/// threading contract), and this counter is the one piece of box state that
/// is process-wide rather than per-Context. Relaxed ordering is enough: the
/// count is read after all evaluation has stopped, never to synchronise.
#ifndef NDEBUG
std::atomic<std::size_t> g_liveBoxes{0};
#endif
```

В релизе счётчика нет вовсе — ни байта, ни инструкции.

Счётчик ссылок коробки остаётся **неатомарным**, и довод записывается в
заголовок явно: атомарность стоила бы на каждом `retain`/`release`
однопоточного пути, а это каждый путь, который мы мерили.

### Р12. Циклы: не собираются, но видны

Цикл создаётся двумя строками, и обе разрешены семантикой:

```
state.self = state           присваивание по имени поля
push(state.items, state)     билтин push
```

Счётчик ссылок их не соберёт никогда.

**Сборщика циклов не будет.** Это отдельная подсистема, стоящая больше, чем
весь остальной проект, и решающая задачу, которой в разобранных макетах BDUI
не бывает: данные приходят деревом с бэкенда.

Вместо этого:

1. **Ограничение записывается в `docs/semantics.md`** рядом с §6, а не только
   в этот документ. Сегодня оно известно тому, кто читал design-документ; оно
   должно быть известно тому, кто пишет скрипт.
2. **Утечка становится видимой в тестах.** Контекст в отладочной сборке ведёт
   список созданных им коробок. При разрушении контекста всё, что живо после
   освобождения корней и не удержано хостом, — цикл: печатается и роняет
   ASan-прогон. В релизе ни списка, ни проверки, ни байта.

## 5. Граница с хостом

### 5.1 Три правила, и заголовок этим исчерпан

```
1. ЗНАЧЕНИЕ ЗАИМСТВОВАНО, пока его не удержали.
   chupa_eval отдаёт значение, живущее до следующего вызова на этом
   контексте. Нужно дольше — chupa_value_retain, потом _release.

2. БАЙТЫ ЗАИМСТВОВАНЫ У ЗНАЧЕНИЯ, адрес которого ты передал.
   Строка и ключ живут ровно столько, сколько живёт ТВОЯ переменная,
   адрес которой ушёл в chupa_value_string. Не NUL-терминированы.

3. ВЛОЖЕННОЕ ЗАИМСТВОВАНО У РОДИТЕЛЯ.
   chupa_array_at и прочие ссылки своей не берут. Должно пережить
   родителя — удержи явно.
```

### 5.2 Значение всегда передаётся по адресу

Дефект В3. Со встроенными строками байты лежат **внутри** значения:

```c
/* СЕГОДНЯ — безвредно: байты вне v */
void chupa_value_string_borrowed(ChupaValue v, const char **bytes, size_t *len);

/* ПОСЛЕ Р2 — та же строка читает освобождённый кадр:
   для короткой строки байты лежат в копии параметра, а она умирает
   при возврате. */
```

Правило: **все функции над значением берут `const ChupaValue *`, без
исключений.** Единый способ передачи убирает эту ошибку из числа выразимых, а
не из числа задокументированных. Стоимость — косвенность на чтении вида и
скаляра; выигрыш — ни одного места, где надо помнить, какая функция как берёт.

### 5.3 Поверхность

```c
/* ─── Version ───────────────────────────────────────────────────────────── */
const char *chupa_version(void);

/* ─── Context ───────────────────────────────────────────────────────────── */
ChupaContext *chupa_context_create(void);
void          chupa_context_destroy(ChupaContext *ctx);

bool chupa_context_set_data  (ChupaContext *, const char *name, size_t,
                              const char *literal, size_t);
bool chupa_context_set_bool  (ChupaContext *, const char *name, size_t, bool);
bool chupa_context_set_number(ChupaContext *, const char *name, size_t, double);
bool chupa_context_set_string(ChupaContext *, const char *name, size_t,
                              const char *text, size_t);

void chupa_context_on_redraw(ChupaContext *, ChupaRedrawListener, void *user);

/* ─── Errors: one call, one struct ──────────────────────────────────────── */
typedef struct ChupaError {
    ChupaErrorCode code;         /* CHUPA_ERR_NONE when the last call succeeded */
    size_t         offset;       /* byte offset into the compiled source        */
    const char    *message;      /* borrowed; valid until the next call on ctx  */
    size_t         message_len;
} ChupaError;

void chupa_context_error(const ChupaContext *ctx, ChupaError *out);

/* ─── Compilation ───────────────────────────────────────────────────────── */
ChupaExpression *chupa_compile_expression(ChupaContext *, const char *, size_t);
ChupaScript     *chupa_compile_script    (ChupaContext *, const char *, size_t);
void chupa_expression_destroy(ChupaExpression *);
void chupa_script_destroy    (ChupaScript *);

/* ─── Evaluation ────────────────────────────────────────────────────────── */
bool chupa_eval(ChupaContext *, ChupaExpression *, ChupaValue *out);
bool chupa_run (ChupaContext *, ChupaScript *);

/* Shortcuts. Same semantics as chupa_eval followed by a kind check, in one
 * crossing of the C boundary. They exist because the constant and variable
 * cases are the ones a scrolling frame runs thousands of times.
 *
 * Return false when no value of that kind was produced. The error tells which:
 *   CHUPA_ERR_NONE   the expression evaluated to null
 *   CHUPA_ERR_TYPE   it produced a value of another kind
 *   anything else    evaluation failed                                      */
bool chupa_eval_number(ChupaContext *, ChupaExpression *, double *out);
bool chupa_eval_bool  (ChupaContext *, ChupaExpression *, bool *out);
bool chupa_eval_string(ChupaContext *, ChupaExpression *,
                       const char **bytes, size_t *len);

/* ─── Values: every one of these takes the value BY ADDRESS ─────────────── */
typedef struct ChupaValue { uint64_t _bits[2]; } ChupaValue;

ChupaKind chupa_value_kind(const ChupaValue *);

bool   chupa_value_bool  (const ChupaValue *);
double chupa_value_number(const ChupaValue *);
void   chupa_value_string(const ChupaValue *, const char **bytes, size_t *len);

size_t chupa_array_count(const ChupaValue *);
void   chupa_array_at   (const ChupaValue *, size_t i, ChupaValue *out);

size_t chupa_object_count   (const ChupaValue *);
void   chupa_object_key_at  (const ChupaValue *, size_t i,
                             const char **bytes, size_t *len);
void   chupa_object_value_at(const ChupaValue *, size_t i, ChupaValue *out);
bool   chupa_object_get     (const ChupaValue *, const char *key, size_t,
                             ChupaValue *out);

void chupa_value_retain (const ChupaValue *);
void chupa_value_release(const ChupaValue *);
```

### 5.4 Что уходит из C API как понятие

| уходит | почему |
|---|---|
| `CHUPA_NULL` как исход | значение бывает null; это вид, а не исход |
| `ChupaStatus` целиком | исход стал двузначным — `bool` |
| `chupa_context_error_code` / `_offset` / `_error` | одна структура вместо трёх вызовов |
| `_borrowed` в имени `chupa_eval_string` | заимствование — общее правило, а не свойство одной функции |
| абзац про переезд пула | пула нет |
| абзац про освобождение временного региона | региона нет |
| «строка материализуется здесь, чтобы retain не был ложью» | материализовывать нечего |
| `chupa_context_set` | переименован в `chupa_context_set_data`: он принимает текст литерала, а не значение |

Трёхзначный исход существовал ровно потому, что в `double *out` некуда
положить «получился null». Значение это выражает само.

## 6. Проверка

**Тесты.** Каждое решение Р1–Р12 закрывается тестом. Отдельно:

- Б1 — тест, воспроизводящий сценарий из 2.2, теперь невыразим: `promote` нет.
  Взамен — тест, что строка любой длины, положенная в глобальную переменную,
  читается после произвольного числа последующих операций.
- В1 — счётчик в отладочной сборке атомарен; тест на два контекста в двух
  потоках. Прогон под TSan требует своей сборки: сегодня в `tools/` есть
  только `asan.sh`, и `tools/tsan.sh` заводится этой же работой.
- В2 — вычисление единицы на чужом контексте даёт `CHUPA_ERR_USAGE`,
  а не мусор, **в релизной сборке тоже**.
- В3 — тест, что байты, взятые у значения по адресу, читаются после возврата
  из функции, их выдавшей (под ASan).
- Р12 — тест, что `state.self = state` под ASan роняет прогон отчётом о цикле.

**Замеры.** Обязательны на трёх рубежах: после Р2 (встроенные строки), после
Р3 (снятие арены), после Р4 (хвостовое размещение). Сравнение против
`benchmarks/baseline.json`. Ожидания, названные заранее:

| замер | ожидание |
|---|---|
| `BM_Eval_StringLiteral` | без изменений — литерал уложен на компиляции |
| `BM_Eval_FormatNumber` | заметно быстрее: результат встроенный |
| `BM_Eval_ArrayLiteral` | быстрее: одна аллокация вместо двух |
| `BM_Eval_ObjectLiteral` | быстрее: то же |
| `BM_Eval_Constant` | без изменений |
| `BM_Eval_ShortPath` | без изменений либо быстрее |

**Замер BDUI обязателен** — `ExpressionEvalBenchmark_Tests` и
`WidgetPropertyBenchmark_Tests` в монорепозитории. Он единственный отвечает на
вопрос, ради которого всё затевалось: перестали ли строки быть слабым местом.
Целевые отношения: интерполяция и переменная-строка выходят выше 1.0.

**Выполненность (задача 11, 2026-08-20).** Три рубежа сняты и сведены —
`docs/benchmarks/2026-08-19-memory-model-checkpoint-{a,b,c}.md`.
`BM_Eval_ArrayLiteral` ожидание не подтвердило: рубеж C (после хвостового
размещения, Р4) не подешевел относительно рубежа B (+0.9%, в пределах
шума) — ожидалось «быстрее», `BM_Eval_ObjectLiteral` в тот же момент
подешевел на 10.8%, той же самой правкой. Причина расхождения не
установлена. Замер BDUI **не выполнен**: харнесс монорепозитория
(`ok/sdk/OKBDUI/Tests/Performance/ExpressionEvalBenchmark_Tests.swift`)
ссылается на C API, отменённый задачами 6–7 этого же плана
(`chupa_context_set`, `CHUPA_OK`, `chupa_eval_string_borrowed`) — правка
Swift-обвязки монорепозитория в объём задачи 11 не входила. Подробности —
`docs/benchmarks/2026-08-19-bdui-after-memory-model-redesign.md`.

## 7. Нерешённое

**7.1. Хост не умеет строить значение.** Хост читает агрегаты, но собрать
`ChupaValue` и положить его в глобальную переменную не может — данные заводятся
только текстом литерала (`chupa_context_set_data`). Для BDUI этого хватает:
данные приходят с бэкенда текстом. Если понадобится — API конструирования
добавляется отдельной работой, эта модель ему не мешает.

**7.2. Дедупликация байт.** Равные строки лежат столькими копиями, сколько раз
их создали. Со встроенными строками вопрос сузился: копия короткой строки
ничего не стоит. Для длинных остаётся открытым ([B1], [B51]).

**7.3. Разрешение ключей объекта на компиляции.** Интернирование ключей
позволяет класть в узел номер ключа вместо байт. Отдельная работа.

## 8. Что в работу не входит

- Изменение семантики языка. `docs/semantics.md` правится только в одном
  месте — ограничение про циклы (Р12).
- Перевод комментариев в файлах, которых эта работа не касается (К1).
- Сборщик циклов (Р12), слэб-аллокатор (Р4), NaN-boxing (Р2) — три решения,
  принятые отрицательно, с названными порогами пересмотра.
