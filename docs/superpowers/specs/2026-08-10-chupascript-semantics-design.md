# ChupaScript: семантика — журнал решений

Дата начала: 2026-08-10
Статус: в работе

Продолжение `2026-08-10-chupascript-grammar-design.md`. Грамматика закрыта и
описана нормативно в `docs/grammar.md`; этот документ накапливает решения по
семантике до того, как они попадут в нормативный текст.

## Принятые решения

### Числа

**Единственный числовой тип — double** (IEEE 754 binary64). Разделения на int и
float нет.

Обоснование: числа приезжают из JSON, где различения нет; разделение типов
породило бы правила смешивания и вопрос «что приехало» на пустом месте. Путь
Lua, разделившей типы в 5.3, продиктован системным программированием — задачей,
которой у нас нет.

**NaN и Infinity — полноценные значения**, семантика IEEE без проверок.
`1 / 0` даёт `Infinity`, `0 / 0` даёт `NaN`, `5 % 0` даёт `NaN`.

Следствия, требующие явного описания в нормативном тексте:

- `==` не рефлексивно: `x == x` ложно, если `x` — NaN. Это не дефект реализации.
- Кэш props, сравнивающий значения, на NaN промахивается всегда.
- `format` обязан определить представление `Infinity`, `-Infinity`, `NaN`.

### Представление значения

**Тегированное объединение** — тег типа плюс union, как в текущем `value.hpp`.
NaN-boxing отложен как оптимизация: он не влияет на семантику и вводится позже
по результатам замеров.

### Арифметика

`+` `-` `*` `/` `%` принимают **только Number**. Любой другой тип операнда —
ошибка. Конкатенации строк через `+` нет: строки собираются только `format`.

`%` берёт **знак делимого** — поведение `std::fmod`, как в C, JS и Swift.
`-5 % 3` даёт `-2`, `5 % -3` даёт `2`, `5.5 % 2` даёт `1.5`. Вариант floored
(знак делителя, как в Python и Lua) отвергнут: он требует поправки поверх
`fmod`, а расходятся они только на отрицательных, которых в разметке
практически нет.

### Приведение типов

Единственное приведение в языке, **односторонее**:

> В позиции, где требуется String, скаляр (Number, Bool, null, String)
> приводится к строке. Обратного приведения — из строки во что-либо — нет
> нигде. Агрегаты не приводятся никуда.

Позиции, где требуется String:

- ключ объекта: `obj[k]`, а также аргумент-ключ у `has`
- аргументы `format`
- будущие строковые билтины

Во всех прочих местах несовпадение типов — ошибка. В частности, правило **не**
применяется к операциям:

```
1 + '1'       // ошибка — арифметика требует Number
1 == '1'      // ошибка — сравнение типов не приводит
1 < '2'       // ошибка
'a' && true   // ошибка — логика требует Bool
arr['0']      // ошибка — String → Number не существует
```

Рассматривался и отвергнут вариант «привести скаляр к строке и повторить
операцию». Сегодня он изменил бы только `==` (для `+`, `<`, `&&` операции над
строками не определены, результат остался бы ошибкой), но сломал бы главную
проверку языка: строка `'null'`, пришедшая с сервера, стала бы равна `null`.
Плюс он превратился бы в поведение JS в тот момент, когда у строк появилась бы
конкатенация.

Для явного приведения нужен билтин `str(x)`.

**Number → String** — кратчайшее представление, читающееся обратно без потерь
(`std::to_chars` без указания формата):

```
1          → '1'
1.5        → '1.5'
0.1 + 0.2  → '0.30000000000000004'
1000000    → '1000000'
1e21       → '1e+21'
```

Особые значения печатаются так, как их выдаёт `to_chars`: `'inf'`, `'-inf'`,
`'nan'`, `'-0'`.

Следствия, которые надо описать в нормативном тексте:

- `-0 == 0` истинно, но `obj[-0]` и `obj[0]` — **разные ключи** (`'-0'` и `'0'`).
- `obj[null]` и `obj['null']` — один ключ. Аналогично для `true`, `1` и прочих
  скаляров. Неизбежно при любом приведении к строке.
- `obj[0.1 + 0.2]` даёт ключ `'0.30000000000000004'`, который человек не наберёт.

### Логические операции

В логической позиции — операнд `!`, операнды `&&` и `||`, условие тернарного
оператора — допустим **только Bool**. Truthiness отсутствует. `&&` и `||`
возвращают Bool, а не операнд.

`&&` и `||` **замыкаются коротко**: правый операнд не вычисляется, если левый
определил результат. Это позволяет защищать правую часть проверкой слева:
`count(arr) > 0 && arr[0] == 1`.

### Сравнения

Операторы порядка `<` `>` `<=` `>=` принимают **только Number**. Строки
сравнивать нельзя: побайтовый порядок не соответствует алфавитному
(`'Я' < 'а'` было бы истинно), а collation по UAX #10 для встраиваемого языка
неподъёмна.

`==` и `!=` между **разными типами — ошибка**. Исключение: `null` сравним с
любым типом.

`==` для Object и Array — **по идентичности**. Равны только если это один и тот
же объект. Структурное сравнение отвергнуто: неограниченная стоимость в горячем
пути и обязательная защита от циклов (`a['self'] = a;` роняет
наивную рекурсию переполнением стека, которое в C++ не перехватывается).

### Модель ошибок

Ошибки делятся на два сорта:

- **Компиляции** — грамматика, арность билтинов, `count(arr);` отдельной
  строкой, использование результата `Void`-билтина. Программа не компилируется.
- **Выполнения** — все типовые несоответствия. Типы данных заранее не известны,
  данные приходят с сервера.

**Ошибка выполнения прерывает вычисление.** Никакого поглощения, никаких
неявных подстановок.

- `evalExpression` возвращает хосту признак ошибки; хост подставляет своё
  значение и пишет в диагностику.
- `runScript` прерывается в точке ошибки; изменения состояния, сделанные до
  неё, остаются.
- `??` ловит **только `null`**, ошибку не гасит.
- `&&` и `||` ошибку не поглощают: `ошибка && false` — ошибка. (Модель CEL с
  коммутативным поглощением рассмотрена и отвергнута.)

### Доступ к данным

**Чтение отсутствующего — `null`:**

```
obj['missing']     // null
arr[100]           // null
```

Это то, ради чего введены `??` и `?.`: данные с сервера штатно неполны.

**Индекс массива — Number, целое, ≥ 0.** Дробный индекс — ошибка (почти всегда
следствие деления). Отрицательный — ошибка, отсчёта с конца нет. Индекс другого
типа — ошибка: приведения к Number в языке не существует, поэтому `arr['0']` не
работает.

**Ключ объекта — любой скаляр**, приводимый к строке по правилу выше:
`obj[1]` эквивалентно `obj['1']`.

**Запись за границу массива — ошибка.** Массив расширяется только через `push`.

**Доступ к полю у не-объекта:**

```
null.foo      // ошибка
null?.foo     // null
(5).foo       // ошибка
(5)?.foo      // ошибка
```

`?.` гасит **только `null`** и остаётся узким инструментом. Если бы `.` у `null`
давало `null`, оператор `?.` был бы не нужен вовсе.

### Имена

**Объявлений в языке нет.** Всякий идентификатор — чтение из контекста,
предоставленного хостом. Создать имя средствами языка невозможно.

Обоснование: все данные экрана известны заранее и приходят с бэкенда. Раз язык
ничего не создаёт, из рантайма исчезают слоты, разрешение областей видимости и
фреймы окружения; из семантики — правила объявления, видимости и переобъявления.

Мутация идёт через контекст, а не через имена:

```
state.count = state.count + 1;
push(state.items, item.id);
```

Слова `let`, `var`, `val`, `const` зарезервированы.

### Команды и запросы разделены

**Билтин либо изменяет данные и возвращает `Void`, либо возвращает значение и
ничего не изменяет.**

Следствия:

- Ни одно выражение не может ничего изменить: `Void`-вызов не может быть ни
  операндом, ни аргументом. Свойство действует в обоих режимах.
- Отдельная пометка «мутирует» не нужна — она читается из типа возврата.
- Проверка чистоты props не нужна как отдельное правило: её обеспечивают
  грамматика и правило `Void`.

### Порядок вычисления

**Слева направо, зафиксирован спекой.** Аргументы вызова и операнды бинарных
операторов вычисляются в порядке записи.

На значение порядок не влияет — побочных эффектов в выражениях нет. Он влияет на
диагностику: при двух ошибочных операндах (`user.age + item.price`) порядок
определяет, о какой ошибке будет сообщено. Незафиксированный порядок дал бы
разные сообщения на разных сборках для одного макета.

### Строки

**`count` для строки считает байты.** `count('привет')` даёт 12, `count('😀')`
даёт 4. O(1), без прохода по строке.

Обоснование: единственное применение длины в разметке, где единица не важна, —
проверка на пустоту, и там все варианты совпадают. Обрезка текста, где единица
критична, в языке отсутствует и остаётся за платформой, которая делает это
лучше — с учётом ширины, шрифта и многоточия.

**`format`** использует плейсхолдер `${}`, аргументы подставляются слева
направо. Экранирование — `$${}` даёт литеральное `${}`.

```
format('Привет, ${}!', name)
format('${} из ${}', a, b)
format('цена $${}', x)          // 'цена ${}'
```

Аргументы приводятся к строке по общему правилу (скаляры — да, агрегаты —
ошибка).

**Несовпадение числа плейсхолдеров и аргументов — ошибка.** Если строка формата
является строковым литералом, компилятор считает плейсхолдеры и проверяет
арность до исполнения; иначе проверка выполняется в рантайме.

### Билтины

Тринадцать функций. Стиль единый: короткое строчное имя, первый аргумент — то,
над чем действуем.

| Билтин | Сигнатура | Детерминирован |
|---|---|---|
| `count(x)` | Array \| Object \| String → Number | да |
| `keys(obj)` | Object → Array of String | да |
| `has(obj, k)` | Object, скаляр → Bool | да |
| `last(arr)` | Array → Value | да |
| `push(arr, v)` | Array, Value → Void | да |
| `pop(arr)` | Array → Void | да |
| `str(x)` | скаляр → String | да |
| `typeof(x)` | Value → String | да |
| `format(fmt, ...)` | String, ... → String | да |
| `min(a, b)` | Number, Number → Number | да |
| `max(a, b)` | Number, Number → Number | да |
| `abs(x)` | Number → Number | да |
| `round(x)` | Number → Number | да |

Аргумент неверного типа — ошибка выполнения.

Детали:

- `count` для String возвращает **байты**.
- `last` на пустом массиве даёт `null`. Через индексацию не выражается:
  `arr[count(arr) - 1]` на пустом массиве даёт `arr[-1]`, то есть ошибку.
- `pop` ничего не возвращает и на пустом массиве ничего не делает. Имя сохранено
  ради парности с `push`; прецедент разделения — `std::stack` в C++, где `pop()`
  тоже `void`, а значение читается через `top()`.
- `typeof` возвращает строчные имена типов из спеки: `'number'`, `'string'`,
  `'boolean'`, `'null'`, `'object'`, `'array'`.
- `round` округляет **от нуля** (`std::round`): `round(0.5)` → `1`,
  `round(2.5)` → `3`, `round(-0.5)` → `-1`.
- `min` и `max` принимают ровно два аргумента. Переменная арность потребовала бы
  правила для нуля аргументов; вложенность решает: `min(a, min(b, c))`.
- **Порядок ключей в `keys(obj)` не определён.** Реализация вольна выбрать любую
  структуру. Следствие, требующее описания в нормативном тексте: `keys(o)[0]`
  может отличаться между версиями рантайма, и макет, полагающийся на порядок,
  не переносим.

Отдельных билтинов для чтения и записи по ключу нет: это покрывает синтаксис —
`obj['k']` и `obj['k'] = v`, поскольку `LeftHandSide` допускает индекс и поле.
Удаления ключа тоже нет.

`typeof` существует потому, что при строгой типизации у автора макета иначе нет
способа защититься от непостоянных типов в данных: несовпадение — ошибка, а `??`
ловит только `null`.

## Отложено

**Граница с хостом.** Как программа получает контекст и что происходит со
значением, переданным хосту и пережившим кадр. От этого зависит модель памяти:
если значения не покидают вычисление, арена закрывает вопрос целиком, без GC и
счётчиков ссылок. Обсуждение отложено по решению заказчика.

## Открытые вопросы

1. Судьба `strictEqual` / `looseEqual` в `core/src/value.hpp`: докстринги
   ссылаются на операторы `===` и `==`. Оператор `===` в языке отсутствует, а
   `==` определён выше — сравнение по идентичности для агрегатов, ошибка при
   разных типах. Функции нуждаются в переименовании и переописании.
