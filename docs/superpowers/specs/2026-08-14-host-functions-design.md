`2026-08-20-host-functions-design.md`.

## 1. Область документа

Документ определяет, как хост объявляет собственные функции и как программа на
ChupaScript их зовёт: состав заголовка, порядок использования, что происходит на
компиляции и на вычислении, что сторожится, а что остаётся контрактом.

Грамматика вызова уже определена (`docs/grammar.md` §5.3): синтаксис
`имя(аргументы)` не меняется, новых форм в языке не появляется. Меняется только
то, откуда берётся смысл имени: сегодня — исключительно из таблицы билтинов
(`core/src/builtin.cpp`), после этой работы — из таблицы билтинов либо из
таблицы, наполненной хостом.

Документ пересматривает решение ревизии 2026-08-13
(`2026-08-13-chupascript-swift-wrappers-design.md` §4.1), которым тип значения
был убран с границы. Основание пересмотра — в §3.

## 2. Зачем

Хост-функция закрывает три сценария, каждый из которых сегодня не выражается:

1. **Действия.** Тап по кнопке отправляет аналитику, открывает экран, показывает
   алерт. Скрипт умеет менять данные, но не умеет попросить хост что-то сделать.
2. **Чистые функции в props.** Локализация, форматирование даты и валюты —
   значения, вычисляемые правилами, которые живут на стороне платформы и
   переносить их в язык бессмысленно.
3. **Запросы состояния хоста.** `isFeatureEnabled('x')`, `screenWidth()` —
   данные, которые не приходят с бэкенда и класть их в корни неудобно.

Первый сценарий даёт `Void`-функции, второй и третий — возвращающие значение.
Механизм регистрации у всех трёх один.

## 3. Что пересекает границу

**Только скаляры, в обе стороны.** `Null`, `Boolean`, `Number`, `String`.
Агрегат в аргументе отвергается движком до вызова коллбэка; вернуть агрегат
нечем.

Это решение — то, ради чего можно не возвращать на границу тип значения.
Ревизия 2026-08-13 убрала `ChupaValue` не из вкусовых соображений: значение,
адресующее пул индексом, живёт «до следующего вычисления», и это правило хост
обязан соблюдать без всякой помощи со стороны типа. Со скалярами правила
времени жизни становятся тривиальными и локальными:

- байты строки-аргумента лежат в пуле контекста и действительны **на время
  вызова коллбэка**; хост читает их сразу либо копирует себе;
- байты строки-результата принадлежат хосту, и движок копирует их **до возврата
  из вызова**, поэтому им достаточно пережить `return` — годится стековый буфер.

Ни в одном из направлений нет ссылки, переживающей вызов. Правило «до
следующего вычисления», которое и похоронило `ChupaValue`, не возникает.

Цена названа прямо: `track('tap', params)` с объектом параметров не
выражается, и `buildRows()` с массивом на возврате — тоже. Расширение до
агрегатов отложено (`docs/backlog.md`), и заголовок к нему готов: добавление
новых `kind` в `ChupaScalar` ABI не ломает, добавление функций чтения агрегата —
тоже.

## 4. Заголовок

Добавляется к `core/include/chupascript/chupascript.h`.

```c
/* Скаляр на границе. kind — только NULL | BOOL | NUMBER | STRING:
   агрегат сюда не переводится и до коллбэка не доходит. */
typedef struct ChupaScalar {
    ChupaKind   kind;
    bool        b;
    double      n;
    const char *CHUPA_NULLABLE s;
    size_t      s_len;
} ChupaScalar;

/* Возврат false — отказ; перед ним коллбэк вправе позвать chupa_fail.
   out == NULL, если функция объявлена не возвращающей значения. */
typedef bool (*ChupaHostFn)(ChupaContext *ctx,
                            const ChupaScalar *args, size_t count,
                            ChupaScalar *CHUPA_NULLABLE out,
                            void *CHUPA_NULLABLE user_data);

typedef struct ChupaFunction {
    const char *name;           /*  0 */
    size_t      name_len;       /*  8 */
    uint8_t     arg_count;      /* 16 — фиксированная арность */
    bool        returns_value;  /* 17 — false: только вызов-стейтментом */
    bool        pure;           /* 18 — true: допустима в режиме выражения */
    bool        deterministic;  /* 19 — задел под кэш props (B29) */
    ChupaHostFn call;           /* 24 */
    void       *CHUPA_NULLABLE user_data; /* 32 */
} ChupaFunction;                /* 40 байт */

CHUPA_API CHUPA_MUST_USE bool
chupa_register(ChupaContext *ctx, const ChupaFunction *fn);

CHUPA_API void chupa_fail(ChupaContext *ctx, ChupaErrorCode code,
                          const char *msg, size_t len);
```

### 4.1 Почему дескриптор, а не имя с коллбэком

Регистрация — прежде всего объявление сигнатуры; коллбэк к нему приложен.

`core/src/check.cpp` сегодня выдаёт три диагностики — `unknown function`,
`wrong number of arguments`, `call result is not used` — и берёт всё нужное из
`builtinInfo`. Это статический проход: ошибка в имени или арности отвергается
при компиляции макета, до первой отрисовки, наравне с `usre.name`
(`docs/semantics.md` §9.1).

Если хост объявляет только имя, для хост-функций этих фактов взять неоткуда, и
все три диагностики переезжают в вычисление — то есть всплывают на конкретном
кадре у конкретного пользователя. Четыре поля дескриптора покупают ровно
сохранение уже заявленного свойства.

Обязанность не разойтись с объявлением ложится на хост. В Swift это закрывается
макросом, выводящим `arg_count` и `returns_value` из сигнатуры функции; макрос
отложен (`docs/backlog.md`).

### 4.2 Фиксированная арность

Вариадичности у хост-функций нет: `arg_count` — одно число, а не пара
`min/max`. `format` остаётся единственной вариадичной функцией и остаётся
билтином.

Следствие для вычислителя: буфер `Value args[kMaxFixedArgs]` рассчитан на
`kMaxFixedArgs == 2` — это потолок билтинов, и `static_assert` в `builtin.cpp`
его сторожит. Хост-функциям двух мало, поэтому заводится собственный потолок
`kMaxHostArgs` (8) и собственный буфер `ChupaScalar hostArgs[kMaxHostArgs]`.
`chupa_register` отвергает `arg_count > kMaxHostArgs`: `check` этого не поймает,
потому что арность приходит от хоста, а не из таблицы.

### 4.3 Отказы регистрации

`chupa_register` возвращает `false`, если:

- `name` не является идентификатором по `docs/grammar.md` §4.1;
- имя занято билтином либо прежней регистрацией;
- `call == NULL`;
- `arg_count > kMaxHostArgs`;
- `deterministic == true` при `pure == false` (см. §6);
- контекст уже что-то компилировал (см. §5).

Совпадение с билтином отвергается, а не разрешается с приоритетом: иначе `count`
переопределяется хостом и семантика `docs/semantics.md` §8 перестаёт быть
свойством языка.

### 4.4 Отказ функции

Коллбэк, вернувший `false`, валит вычисление. Перед возвратом он вправе позвать
`chupa_fail` и задать код с сообщением; смещение подставляет движок — узел
вызова, как у `applyBuiltin`. Без `chupa_fail` берётся `CHUPA_ERR_USAGE` и
сообщение по умолчанию.

`chupa_fail` — единственная функция, которой хосту позволено писать в контекст
во время вызова (§7). Байты сообщения копируются немедленно, поэтому буфер
вызывающего дальше не нужен. Копия ложится в **отдельный буфер контекста, а не в
пул текста `text_`** — обоснование в §8.

## 5. Порядок использования

```
регистрация функций → постановка корней → компиляция → вычисления
```

Тот же порядок, что у данных, и по той же причине: `check` сверяет имена ровно в
момент своего вызова и полагается, что состав имён после этого не меняется
(`docs/semantics.md` §9.1, `docs/backlog.md` B23).

Для функций этот порядок, в отличие от корней, обеспечивается: контекст держит
флаг «уже компилировали», и `chupa_register` после первой компиляции
отвергается. B23 остаётся открытым для корней.

## 6. Два флага

Флаги легко спутать, поэтому смысл разводится жёстко.

- **`pure`** — вызов не меняет наблюдаемого состояния. Решает, **где можно
  звать**: `pure == false` в дереве, скомпилированном как выражение, — ошибка
  компиляции.
- **`deterministic`** — при тех же аргументах и тех же данных даёт тот же
  результат в пределах кадра. Решает, **можно ли кэшировать результат**.

| `pure` | `deterministic` | пример | смысл |
|---|---|---|---|
| да | да | `formatCurrency(x)` | в props можно, результат кэшируем |
| да | нет | `now()`, `screenWidth()` | в props можно, пересчитывать каждый кадр |
| нет | — | `track('tap')` | в выражении нельзя вовсе |
| нет | да | — | противоречие, регистрация отвергается |

**`deterministic` сегодня никем не читается.** Движок его хранит и проверяет на
противоречие; использовать начнёт кэш props (B29), которого нет. Поле заведено
сейчас, а не потом, по одной причине: добавление поля позже ломает ABI, а
добавление в существующий паддинг `ChupaFunction` бесплатно — размер структуры
не меняется.

### 6.1 Билтины объявляют то же самое

`BuiltinInfo` (`core/src/builtin.hpp`) получает два столбца:

```cpp
struct BuiltinInfo {
    std::string_view name;
    std::uint8_t minArgs;
    std::uint8_t maxArgs;
    bool returnsValue;
    bool pure;           ///< false — меняет данные (docs/grammar.md §6.3)
    bool deterministic;  ///< задел под кэш props (docs/backlog.md B29)
};
```

У сегодняшних двенадцати билтинов `pure` совпадает с `returnsValue`: `pop` и
`push` — единственные, кто и возвращает `Void`, и меняет данные. Это не
совпадение, а буквально доказательство `docs/grammar.md` §6.3.

Выводить одно из другого в коде тем не менее нельзя: вывод верен, только пока
верна посылка, и сломает её первый билтин, который и меняет данные, и возвращает
значение. Тогда `pure` молча стал бы `true` для мутирующей функции, а ошибка
вылезла бы в кэше props. Явные столбцы делают расхождение осознанным решением, а
не побочным эффектом.

### 6.2 Чего проверить нельзя

Детерминированность и чистота, объявленные хостом, движком не проверяются и
проверены быть не могут: `now()` и `random()` выражаются в коде и от честного
форматирования неотличимы.

`docs/grammar.md` §6.3 получает оговорку: право хоста кэшировать значения props
держится на билтинах **по устройству**, а на хост-функциях — **по объявлению**
`pure` и `deterministic`.

## 7. Что хост-функция вправе делать

Коллбэк получает `ChupaContext *`, поэтому весь публичный заголовок изнутри него
выразим. Разделение обеспечивается счётчиком `hostCallDepth_` в `Context`,
который вычислитель поднимает перед вызовом:

- **разрешено:** `chupa_fail`, `chupa_context_error*` (чтение);
- **отвергается:** `chupa_context_set*`, `chupa_run`, `chupa_eval_*`,
  `chupa_compile_*`, `chupa_register`.

Почему именно эти. `chupa_context_set*` растит пулы, а хост в этот момент держит
срез `text_` в `args[i].s` — переезд отправит его в никуда (§8). `chupa_run` и
`chupa_eval_*` перезаписывают единственный `Diagnostic` контекста и открывают
неограниченную рекурсию через C-границу, если вложенный скрипт зовёт ту же
функцию.

**Как отказ становится виден.** Сеттеры возвращают `void`, вернуть ошибку им
некуда. Страж вместо этого травит контекст: ставит `CHUPA_ERR_USAGE` и флаг.
Коллбэк доработает до конца, но по возврату движок увидит флаг и завалит
вычисление целиком — `chupa_run` вернёт `false`, код прочитается обычным
`chupa_context_error_code`.

Страж работает в релизе, а не только под `assert`. Цена — сравнение целого на
входе публичной функции; без стража ошибка хоста проявляется переездом пула,
то есть тихо испорченными данными на чужом устройстве.

**Остаётся контрактом,** непроверяемым движком: коллбэк не бросает исключение
через C-границу; хост не хранит `args[i].s` дольше вызова.

## 8. Дисциплина пулов

Пулы контекста переезжают при росте, поэтому сырой срез внутрь пула живёт лишь
до ближайшей мутации того же контекста (`core/src/context.hpp`). Хост-функция —
первый случай, когда посреди обхода дерева зовётся чужой код; общий разбор
проблемы записан в `docs/backlog.md` B34.

Сегодняшний `eval` это переживает: сырых срезов поперёк вычисления вложенного
узла он нигде не держит. `evalFormat` берёт шаблон свежим срезом на каждой
итерации (`nextFormatPiece(ctx.string(tmpl), …)`, обоснование в
`core/src/builtin.hpp`), а `text` и `key` из `coerceToString` потребляются сразу.
Реализация обязана это свойство сохранить.

Из него следуют два конкретных требования:

1. **`chupa_fail` копирует сообщение не в `text_`.** Контекст заводит под это
   отдельный буфер — тем же приёмом, каким `build_` отделён от `text_` ради
   `format`. Иначе рост `text_` внутри `chupa_fail` протухает `args[i].s`,
   которые хост уже держит.
2. **Результат безопасен.** `makeString` по `out->s` зовётся после возврата из
   коллбэка, когда аргументы больше никому не нужны.

## 9. Устройство в ядре

### 9.1 Новый модуль

`core/src/host.hpp` / `host.cpp` — по образцу `builtin.hpp`: таблица, поиск,
применение.

`host.hpp` включает публичный заголовок: `ChupaScalar` и `ChupaHostFn` — типы
границы по определению, и заводить в ядре их параллельные копии значило бы
держать две правды об одном.

### 9.2 Таблица

Живёт в `Context`, рядом с корнями, той же длительности жизни:

```cpp
struct HostFunction {
    std::string  name;
    std::uint8_t argCount;
    bool         returnsValue;
    bool         pure;
    bool         deterministic;
    ChupaHostFn  call;
    void        *userData;
};
std::vector<HostFunction> hosts_;
```

`std::string`, а не срез пула `text_`, намеренно: срез в `text_` протухает на
первом же росте пула. Регистрация случается единицы раз за жизнь контекста,
поэтому отдельная аллокация на имя ничего не стоит.

### 9.3 Резолв — одна функция на двух потребителей

```cpp
enum class CalleeKind : std::uint8_t { Unknown, Builtin, Host };

struct Callee {
    CalleeKind   kind;
    Builtin      builtin;       // при kind == Builtin
    ChupaHostFn  call;          // при kind == Host
    void        *userData;      // при kind == Host
    std::uint8_t minArgs, maxArgs;
    bool         returnsValue;
    bool         pure;
    bool         deterministic;
};

Callee resolveCallee(const Context &ctx, std::string_view name) noexcept;
```

Иначе `check.cpp` и `eval.cpp` обрастут каждый своей парой веток «билтин или
хост», и правило «что считается вызовом» размажется по двум файлам.

Коллбэк лежит в `Callee` целиком, а не индексом в `hosts_`: тогда структура
самодостаточна, второго обращения к таблице нет и вопрос «не устарел ли индекс»
не возникает. `check` эти два поля не читает.

Билтины ищутся первыми; коллизия имён невозможна, её отсекает `chupa_register`.

### 9.4 Статический проход

`checkCall` перестаёт звать `findBuiltin`/`builtinInfo` и зовёт `resolveCallee`.
`Unknown` даёт прежнее `unknown function`, сверка арности идёт по тем же полям,
`requireValue`/`requireVoid` не меняются.

Добавляется одна новая диагностика: вызов функции с `pure == false` в дереве,
скомпилированном как выражение. Значит `check` должен знать режим — сегодня он
его не знает, и в сигнатуру добавляется признак: `compileExpression` передаёт
«выражение», `compileScript` — «скрипт».

### 9.5 Вычисление

В `NodeKind::Call` появляется ветка `CalleeKind::Host`. Аргументы вычисляются в
тот же `Value args[]`, затем переводятся в `ChupaScalar hostArgs[kMaxHostArgs]`.
Агрегат в аргументе — отказ `Type` со смещением узла вызова, до вызова коллбэка.

Потолок `kMaxHostArgs` сторожится тем же приёмом, что и `kMaxFixedArgs`:
`static_assert`, не дающий буферу молча разойтись с константой.

Проверки чистоты в `eval` нет: дереву доверяем (`docs/backlog.md` B31).

## 10. Обёртка Swift

```swift
public enum ChupaScalar {
    case null
    case bool(Bool)
    case number(Double)
    case string(String)
}

extension Context {
    /// Register a host function. Must be called before any compile.
    public func register(
        _ name: String,
        arity: Int,
        returnsValue: Bool = false,
        pure: Bool = false,
        deterministic: Bool = false,
        _ body: @escaping ([ChupaScalar]) throws -> ChupaScalar?
    ) throws
}
```

Три места, где реализация неочевидна.

**Box и `user_data`.** Замыкание в `@convention(c)`-указатель не превращается.
Обёртка кладёт `body` в `final class Box`, держит массив боксов полем
`Context` — то есть ровно столько же, сколько живёт контекст, — и передаёт
`Unmanaged.passUnretained(box).toOpaque()` в `user_data`. Владеет массив,
поэтому `passUnretained` здесь корректен по устройству, а не по удаче.

**Байты возвращаемой строки.** Движок копирует `out->s` после возврата из
коллбэка, поэтому `withCString` не годится — его указатель умирает на выходе из
замыкания. Бокс держит буфер под возврат:

```swift
box.returnBytes = Array(text.utf8)
box.returnBytes.withUnsafeBufferPointer {
    out.pointee.kind = CHUPA_KIND_STRING
    out.pointee.s = $0.baseAddress
    out.pointee.s_len = $0.count
}
```

Буфер живёт до следующего вызова той же функции; движку хватает с запасом.

**Тень имени.** `ChupaScalar` — одновременно имя C-структуры, импортируемой из
`ChupaScriptC`. Разрешение имён выигрывает свой модуль, поэтому внутри thunk'а
C-тип пишется полностью: `ChupaScriptC.ChupaScalar`. Это единственное такое
место, и там квалификация даже полезна — видно, где кончается C.

> **Открытый вопрос после Р8.** Абзац выше описывает ровно то затенение, которое
> Р8 спеки `2026-08-15-chupascript-core-entities-design.md` из Swift-обвязки
> убрал: Swift-класс `ChupaContext` носил имя C-структуры `ChupaContext`, и это
> названо там дефектом, а не удобством. Предложенный здесь `ChupaScalar`
> заводит его заново, да ещё и с префиксом, который Р8 снял со всех остальных
> типов. Напрашивается `Scalar`, но это уже решение по имени публичного типа, и
> задача 7 его не принимала — оставлено тому, кто будет делать B34. Остальные
> Swift-имена в этой главе к состоянию после Р8 приведены: `Context`, `Error`.

**Ошибка.** `body` бросает — thunk ловит, зовёт `chupa_fail` и возвращает
`false`. `Error` (`swift/Error.swift`) уже несёт `code` и `message`,
новых типов не появляется; для ошибок, не являющихся `ChupaScript.Error`,
берётся `CHUPA_ERR_USAGE` и `localizedDescription`. Одна правка в нём всё же
нужна: почленный инициализатор структуры сегодня внутренний, а хосту требуется
свой `Error` создавать — значит объявляется публичный `init`.

Ловить в thunk'е надо `Swift.Error`, а не `Error`: после Р8 второе — это наш
собственный тип, затеняющий протокол внутри модуля. То есть `catch let e as
ChupaScript.Error` для своей ошибки и `catch let e` для всех прочих.

Пример:

```swift
try ctx.register("track", arity: 1) { args in
    guard case .string(let event) = args[0] else {
        throw Error(code: CHUPA_ERR_TYPE,
                    message: "track expects a string", offset: 0)
    }
    analytics.send(event)
    return nil
}
```

**Известная цена.** `case string(String)` копирует байты аргумента в Swift-строку
на каждом вызове — для `pure`-функции в props это на каждый кадр. Нулевое
копирование выразимо, но делает API неудобным; решение принято начать с копии и
вернуться к вопросу по замерам (`docs/backlog.md`).

Макрос, выводящий `arity` и `returnsValue` из сигнатуры Swift-функции, отложен:
он требует отдельного SwiftSyntax-таргета, заметно удлиняет сборку и ничего не
даёт Kotlin/JNI.

## 11. Тесты

- `core/tests/host_test.cpp` (новый): все отказы регистрации из §4.3; резолв

  возвращается; `return false` с `chupa_fail` и без; строка-результат переживает

выражается.
