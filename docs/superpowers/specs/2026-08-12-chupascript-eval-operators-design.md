## 3. Разделение на две единицы

Глава 5 делится надвое сама, и деление проходит по существу, а не по объёму.

**§5.2, §5.3 и §5.4 — чистые функции двух значений.** Дай операцию и два
значения, получи третье или ошибку. Ни дерева, ни узлов, ни рекурсии.

**§5.5, §5.6 и §5.7 — управление.** Их суть в том, чтобы правый операнд или
невыбранную ветвь **не вычислять**. Вынести их из обхода нельзя: вычислять или
нет — решение о самом обходе.

Отсюда две единицы:

```cpp
// core/src/operator.hpp — семантика операций над значениями
namespace CS {

/// Применяет бинарную операцию без короткого замыкания.
///
/// Принимает op из числа: Plus, Minus, Star, Slash, Percent, Less, Greater,
/// LessEqual, GreaterEqual, Equal, NotEqual. Логические, ?? и тернарный сюда не
/// попадают — они решают, вычислять ли операнд, а здесь оба уже вычислены.
///
/// ctx нужен единственной операции — сравнению строк на равенство.
/// offset попадает в diag при отказе: это данные, а не зависимость от дерева.
bool applyBinary(TokenKind op, Value lhs, Value rhs, const Context &ctx,
                 std::uint32_t offset, Value *out, Diagnostic &diag);

/// Применяет унарную операцию: Bang над Boolean, Minus над Number.
///
/// Контекст здесь не нужен: ни одна из двух операций не заглядывает в
/// хранилище.
bool applyUnary(TokenKind op, Value operand, std::uint32_t offset, Value *out,
                Diagnostic &diag);

}  // namespace CS
```

`core/src/eval.cpp` получает три ветки: `Unary` и `Binary` зовут `operator.*`,
`Conditional` решает сама. `Binary` при этом перехватывает `&&`, `||` и `??`
**до** вычисления правого операнда, и в `applyBinary` они не попадают.

Разделение окупается в части 3: составное присваивание определено там буквально
как `x = x + e` (`docs/semantics.md` §7.3), то есть ему нужна ровно функция
«применить бинарную операцию к двум значениям». Лежи она внутри обхода,
переплетённая с узлами, часть 3 либо дублировала бы её, либо тянулась внутрь.

## 4. Арифметика

`+` `-` `*` `/` `%` принимают **только `Number`**, оба операнда; любой другой тип
— ошибка `Type`.

**Конкатенации строк через `+` нет.** `1 + '1'` — ошибка, и `'a' + 'b'` тоже.
Это место, где привычка из JavaScript обманывает чаще всего. Строки собирает
`format` (§8.9), который приходит с частью 3.

Вычисление по IEEE 754 без дополнительных проверок: `1 / 0` даёт `+Infinity`,
`-1 / 0` даёт `-Infinity`, `0 / 0` даёт `NaN`. Проверки деления на ноль нет и не
будет: результат определён стандартом, а исключение здесь означало бы, что
неполные данные с сервера роняют экран.

`%` берёт **знак делимого** — это `std::fmod`, а не остаток от целочисленного
деления: `-5 % 3` даёт `-2`, `5 % -3` даёт `2`, `5.5 % 2` даёт `1.5`, `5 % 0`
даёт `NaN`.

## 5. Сравнения порядка

`<` `>` `<=` `>=` принимают **только `Number`**. Строки, логические значения и
агрегаты сравнивать нельзя — ошибка `Type`.

Если хотя бы один операнд `NaN`, **все четыре дают `false`**.

**Отсюда следует запрет, который легко нарушить по невнимательности: ни один из
четырёх операторов нельзя выводить отрицанием соседа.** `!(1 < NaN)` истинно,
тогда как `1 >= NaN` ложно. Каждый оператор вычисляется напрямую, встроенным
сравнением C++, которое ведёт себя с `NaN` ровно так, как требует §5.3.

> **Почему строки не сравниваются** (§5.3): побайтовый порядок не соответствует
> алфавитному, и `'Я' < 'а'` было бы истинно. Порядок, зависящий от языка, — это
> коллация, которой в рантайме нет.

## 6. Равенство

`==` и `!=`. Правила применяются **в порядке перечисления**, и порядок
существенен:

1. Если один из операндов `null` — результат истинен тогда и только тогда, когда
   второй операнд тоже `null`.
2. Если типы операндов различаются — **ошибка** `Type`.
3. `Number` сравниваются по IEEE 754. `NaN` не равен ничему, включая себя.
4. `String` сравниваются побайтово. Нормализация юникода не выполняется.
5. `Boolean` сравниваются по значению.
6. `Object` и `Array` сравниваются **по идентичности** — это `Value::sameAggregate`.

Первое правило стоит раньше второго, поэтому `null == 5` даёт `false`, а
`1 == '1'` — ошибку. Литерал создаёт новый агрегат при каждом вычислении (§2.3),
поэтому `state.items == [1, 2]` ложно всегда, даже когда содержимое совпадает.

`!=` **во всём** эквивалентен отрицанию `==`, включая случай ошибки: `1 != '1'`
тоже ошибка. Реализуется отрицанием, а не отдельной таблицей, — тогда
расхождение между ними невозможно по построению.

> **Почему по идентичности** (§5.4): структурное сравнение имеет неограниченную
> стоимость в горячем пути и требует защиты от циклов — `obj['self'] = obj`
> уронил бы наивную рекурсию.

Этим закрывается `docs/backlog.md` B15: вместо `strictEqual` и `looseEqual`,
объявленных когда-то в черновике значений, остаётся одно равенство, потому что в
языке оно одно.

## 7. Унарные операторы

| Оператор | Операнд | Результат |
|---|---|---|
| `!` | `Boolean` | отрицание |
| `-` | `Number` | смена знака |

Любой другой тип операнда — ошибка `Type`. `-` над `NaN` даёт `NaN`, над нулём —
отрицательный ноль.

Отрицательный ноль уже наблюдаем: часть 1 различает ключи `obj[-0]` и `obj[0]`,
потому что представление числа сохраняет знак. С приходом унарного минуса в
выражения это различие становится достижимым и оттуда.

## 8. Короткое замыкание и выбор ветви

Остаются в обходе: их суть — не вычислять.

**`&&` и `||`** принимают только `Boolean` и возвращают `Boolean`. Левый операнд
вычисляется и проверяется всегда. Если он определил результат, правый **не
вычисляется**, а значит и не проверяется: проверять нечего.

Отсюда следствие, которое стоит записать, потому что читается двояко: `false && 5`
даёт `false`, а не ошибку. Это не послабление правила «только `Boolean`», а
прямое следствие того, что правый операнд не вычислен.

Ошибка в левом операнде прерывает вычисление и правым не поглощается:
`ошибка && false` — ошибка.

**`??`** даёт левый операнд, если он не `null`, иначе правый. Типы произвольны и
совпадать не обязаны. Правоассоциативен — это дело грамматики, не вычисления.

`??` перехватывает **только `null`** и ошибку не гасит: `(user.age + 1) ?? 0` —
ошибка, если `age` не число. Это тот случай, где `??` соблазнительно принять за
«если что-то пойдёт не так, подставь запасное»; он делает не это.

**Тернарный** требует `Boolean` в условии, иначе ошибка `Type`. Ветви могут иметь
любые типы, совпадать не обязаны. Вычисляется **только выбранная** ветвь.

## 9. Ошибки

Новых классов не появляется: всё, что может пойти не так в главе 5, — это
неподходящий тип операнда, то есть `Type`.

| Когда | Пример |
|---|---|
| Арифметика не над числами | `1 + '1'`, `'a' + 'b'` |
| Сравнение порядка не над числами | `'a' < 'b'`, `true < false` |
| Равенство разных типов | `1 == '1'` |
| Логическая операция не над `Boolean` | `'a' && true` |
| Небулево условие тернарного | `1 ? a : b` |
| Унарный оператор не над своим типом | `!1`, `-'a'` |

Смещение — от узла операции. Первая ошибка выигрывает. При отказе `*out` не
трогается — то же соглашение, что в части 1.

## 11. Тесты

**Таблицы проверяются через `applyBinary` и `applyUnary` напрямую**, без
построения выражений. Приложение A семантики перечисляет допустимые типы для
каждой позиции — это таблица, и проверять её через разбор текста значит вставлять
лишний слой между требованием и проверкой. Ради этого разделение и сделано.

Обязательное сверх очевидного:

- **`NaN` во всех четырёх сравнениях даёт `false`,** и отдельно — что `<` и `>=`
  на `NaN` **оба** ложны, то есть один не выведен отрицанием другого. Без этого
  теста запрет из §5 держится на честном слове.
- **`NaN == NaN` ложно, `NaN != NaN` истинно.**
- **`null == 5` даёт `false`, а `1 == '1'` — ошибку.** Обе половины
  обязательны: они различают первое правило равенства и второе.
- **`state.items == [1, 2]` ложно** при совпадающем содержимом — идентичность, а
  не структура.
- **`%` со всеми знаками** и `5 % 0`, дающий `NaN`.
- **`1 / 0`, `-1 / 0`, `0 / 0`** — бесконечности и `NaN`, а не ошибки.

Через обход проверяется то, что иначе не проверить:

- **`false && ошибка` даёт `false`,** а `true && ошибка` — ошибку. Первая
  половина доказывает, что правый операнд не вычислен: побочных эффектов в
  выражениях нет, и наблюдать невычисление можно только через ошибку, которая не
  всплыла.
- **`ошибка && false` — ошибка:** левый не поглощается.
- **`false && 5` даёт `false`, а `true && 5` — ошибку.** Эта пара и есть самая
  точная проверка правила: тип правого операнда проверяется тогда и только
  тогда, когда его пришлось вычислить.
- **`null ?? ошибка` — ошибка, `1 ?? ошибка` — единица.**
- **`(ошибка) ?? 0` — ошибка:** `??` не гасит.
- **Тернарный не трогает невыбранную ветвь:** `true ? 1 : ошибка` даёт единицу.

## 12. Бенчмарки

- арифметическое выражение из нескольких операций;
- цепочка сравнений, соединённая `&&`;
- `??` по короткому пути — слева не `null`;
- `??` по длинному — слева `null`, правый вычисляется.

Последняя пара важнее прочих: `??` — самый частый оператор в props, и разница
между двумя его путями видна на экране.
