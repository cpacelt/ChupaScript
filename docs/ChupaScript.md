# 1. Введение

## 1.1. Зачем движку нужен язык

Представьте, что бэкенд присылает вам описание экрана:

```json
{
  "type": "Button",
  "props": { "title": "Купить" }
}
```

Клиент читает это описание и рисует кнопку с надписью «Купить». Пока всё просто.

Теперь предположим, что надпись должна зависеть от содержимого корзины: если корзина пуста, на кнопке написано «Корзина пуста» и она неактивна; если в ней три товара — «Оформить (3)». Бэкенд не может прислать готовую строку, потому что не знает, что пользователь положит в корзину через минуту после загрузки экрана.

Есть два выхода. Первый — ходить на сервер за новым описанием после каждого нажатия. Это работает, но означает сетевой запрос на каждое движение пальца. Второй — научить клиент **вычислять** значения на месте:

```json
{
  "type": "Button",
  "props": {
    "title":   "$$ cart.items.length > 0 ? `Оформить (${cart.items.length})` : 'Корзина пуста'",
    "enabled": "$$ cart.items.length > 0"
  }
}
```

Строки, начинающиеся с `$$`, — это код на ChupaLang. Он выполняется на устройстве и превращается в конкретные значения. Именно этот код вы и будете писать.

Второе, что нужно уметь, — менять состояние. Пользователь нажал «плюс» рядом с товаром: количество должно вырасти, сумма пересчитаться, кнопка обновить надпись. Для этого в описании экрана есть блоки `action`:

```json
{
  "type": "Button",
  "props": { "title": "+" },
  "onTap": "cart.items[itemId].qty = cart.items[itemId].qty + 1;"
}
```

Когда пользователь нажимает кнопку, движок исполняет этот код. Состояние меняется, и все значения, которые от него зависели, вычисляются заново. Экран перерисовывается сам — вам не нужно ничего обновлять вручную.

Мы называем это **реактивностью**: вы описываете, чему равно значение, а не когда его пересчитать.

## 1.2. Что вы будете писать

В отличие от обычного языка программирования, здесь нет файлов с исходным кодом. Ваш код живёт внутри JSON и попадает в движок кусочками — по одной строке за раз. Всего таких мест четыре:

- **init экрана** — код, который выполняется один раз при загрузке. Здесь объявляют переменные состояния и вспомогательные функции.
- **props** — одно выражение, вычисляющее значение поля компонента.
- **actions** — код, который выполняется в ответ на действие пользователя.
- **REPL** — интерактивная консоль для отладки, где вы вводите код построчно и сразу видите результат.

Эти четыре места ведут себя по-разному, и различия существенны: в props нельзя менять состояние, в actions нельзя объявлять функции. Мы разберём это подробно в главе 4. Пока достаточно запомнить, что **правила зависят от того, куда вы пишете код**.

Типичный размер того, что вы напишете, — от одного выражения до десятка строк. ChupaLang рассчитан именно на такой масштаб. Если логика не помещается в этот объём, скорее всего, её следует вычислить на бэкенде и прислать готовой.

## 1.3. Чем ChupaLang отличается от JavaScript

Синтаксис — JavaScript. Если вы писали на JS, вы уже умеете читать и писать этот код: те же литералы, те же операторы, те же `if` и `for`, те же шаблонные строки.

Отличие в том, что поддерживается **подмножество**. Мы убрали значительную часть языка, и убрали намеренно. Три причины:

**Код приходит от бэкенда.** Он не проходит через ваш код-ревью, не собирается вашим сборщиком и не тестируется вашими тестами. Он приезжает по сети и сразу исполняется на устройстве пользователя. Поэтому мы хотим проверять его как можно раньше и как можно строже — в идеале в момент получения ответа, до первой отрисовки.

**Код исполняется в UI-потоке.** Выражение props вычисляется на каждый кадр, для каждого узла дерева. Бесконечный цикл здесь — это не зависший скрипт в фоне, а замерший интерфейс.

**Отлаживать это тяжело.** У автора JSON нет брейкпоинтов и стека вызовов. Значит, конструкции, которые в JS ведут себя неочевидно, дают здесь несоразмерную цену.

Вот главные различия, которые вы заметите сразу:

**Нет `while` и обычного `for`.** Есть только `for...of` — обход конкретной коллекции. Это значит, что любой ваш цикл заведомо завершается: число итераций известно до его начала.

**Нет рекурсии.** Функция не может вызвать саму себя, ни напрямую, ни через другую функцию.

**Нет `try`/`catch`.** Ошибка в props не роняет экран: значение становится `undefined`, а факт ошибки попадает в лог. Перехватывать нечего.

**Нет `async`/`await`.** Всё асинхронное делает клиент. Ваш код всегда исполняется целиком и мгновенно.

**Нет классов, `this` и прототипов.** Объект — это просто набор пар «ключ — значение», ровно как в JSON.

**Нет своей стандартной библиотеки.** ChupaLang пользуется встроенными средствами JavaScript: `items.filter(...)`, `Object.keys(...)`, `Math.round(...)`, `arr.length`. Никаких собственных функций вместо них язык не вводит.

Из этого следует главное свойство языка: **любой код на ChupaLang является корректным кодом на JavaScript.** Мы только убираем конструкции, никогда ничего не добавляем. Программа без `while` и без рекурсии остаётся обычным JavaScript — просто более скромным.

**Стрелочные функции можно писать только как аргумент вызова.** `items.filter(x => x.enabled)` — можно. `let f = x => x + 1;` — нельзя.

Каждое из этих ограничений мы объясним в соответствующей главе. Общий принцип такой: **всё, что осталось, ведёт себя ровно как в JavaScript.** Мы не меняли семантику — мы её сокращали. Если конструкция есть в языке, ваши знания о JS применимы к ней без оговорок.

Исключение ровно одно, и оно описано в разделе 6.3: цикл `for...of` запоминает длину массива перед началом обхода. Без этого правила цикл можно было бы продлевать бесконечно, добавляя в массив элементы прямо во время обхода.

# 2. Значения и типы

В ChupaLang семь типов значений: число, строка, булево значение, `null`, `undefined`, объект и массив. Восьмой — функция — существует, но обращаться с ним как с обычным значением нельзя; об этом глава 7.

Типы не объявляются. Переменная хранит значение любого типа, и тип может смениться при следующем присваивании.

## 2.1. Числа

Число одно на все случаи — как в JavaScript, это число с плавающей точкой двойной точности. Отдельного целочисленного типа нет.

```js
let count = 42;
let price = 199.99;
let negative = -5;
```

Из этого следует известное свойство: дробные значения хранятся приблизительно.

```js
0.1 + 0.2      // 0.30000000000000004
```

Практический вывод: **не считайте деньги в ChupaLang.** Складывать цены товаров в корзине можно, но итоговую сумму лучше получать с бэкенда — там она посчитана точно. Если сумму всё же приходится вычислять на клиенте, округляйте перед показом:

```js
subtotal.toFixed(2)
```

> **TODO.** Нужно ли отдельное соглашение по денежным значениям — приходят ли они с бэкенда готовой строкой или числом. Решение влияет на этот раздел.

Деление на ноль не является ошибкой и даёт `Infinity`, а `0 / 0` даёт `NaN`. `NaN` не равен ничему, включая самого себя. Проверить его можно так:

```js
Number.isNaN(x)
```

## 2.2. Строки

Строку можно записать в одинарных или двойных кавычках:

```js
let a = "Привет";
let b = 'Привет';
```

Внутри JSON вам почти всегда удобнее одинарные — двойные пришлось бы экранировать.

Строки складываются оператором `+`:

```js
"Итого: " + total + " ₽"
```

Но для этого есть более удобная форма — шаблонные строки, см. раздел 5.5.

Длина строки доступна как `.length`:

```js
"Привет".length    // 6
```

Считается она не в символах, а в единицах UTF-16 — ровно как в JavaScript. Для латиницы и кириллицы разницы нет, но эмодзи и редкие иероглифы занимают по две единицы:

```js
"🎉".length        // 2
```

То же касается `slice`, `substring` и `charAt`: они режут строку по тем же единицам, и разрезать эмодзи пополам технически возможно. Если строка приходит от пользователя, обрезайте её с запасом или поручите это хост-функции.

## 2.3. Булевы значения

`true` и `false`. Ничего неожиданного.

Стоит помнить, что в условиях используются не только они: как и в JavaScript, ложными считаются `false`, `0`, `""`, `null`, `undefined` и `NaN`, а всё остальное — истинным. Отсюда типичная ловушка:

```js
if (cart.items.length) { ... }   // работает, но при 0 элементов даст false
if (discount) { ... }            // при скидке 0% условие ложно
```

Пишите сравнение явно — так понятнее и надёжнее:

```js
if (cart.items.length > 0) { ... }
if (discount != null) { ... }
```

## 2.4. `null` и `undefined`

Два разных «ничего», как в JavaScript.

`null` обычно приходит с бэкенда и означает «поле есть, значение пустое». `undefined` возникает внутри языка и означает «поля нет вообще»:

```js
let user = { name: "Аня", phone: null };

user.phone     // null      — поле есть, значение пустое
user.email     // undefined — поля нет
```

Различие редко бывает важным, поэтому проверяйте оба разом. Оператор `==` (с одним знаком равенства) делает это сам:

```js
if (user.email == null) { ... }   // true и для null, и для undefined
```

Это тот редкий случай, когда нестрогое сравнение полезно. Во всех остальных используйте `===` — см. раздел 5.2.

## 2.5. Объекты

Объект — это набор пар «ключ — значение». Ключи всегда строки.

```js
let user = { name: "Аня", age: 30 };
```

Значение читается через точку или через квадратные скобки:

```js
user.name        // "Аня"
user["name"]     // то же самое
```

Точка удобнее, но скобки нужны, когда ключ вычисляется:

```js
let field = "name";
user[field]      // "Аня"
```

Если такого ключа нет, вы получите `undefined`, а не ошибку:

```js
user.email       // undefined
```

**В ChupaLang объект — это то же, что словарь или мапа в других языках.** Отдельного типа `Map` нет и не нужно: объект и есть мапа. Единственное отличие от, скажем, `HashMap` в Kotlin — ключи могут быть только строками. Число, использованное как ключ, превращается в строку:

```js
let likes = {};
likes[42] = 10;
Object.keys(likes)      // ["42"] — строка, а не число
```

Из-за этого стоит договориться с бэкендом, что идентификаторы в словарях всегда приходят строками. Иначе вы рискуете отправить обратно `"42"` там, где ожидалось `42`.

Объект можно создать с вычисляемыми ключами и с сокращённой записью:

```js
let key = "total";
let obj1 = { [key]: 100 };        // { total: 100 }

let name = "Аня";
let obj2 = { name };              // { name: "Аня" }
```

## 2.6. Массивы

Массив — упорядоченный список значений любых типов:

```js
let items = [1, 2, 3];
let mixed = ["a", 2, null, { x: 1 }];
```

Доступ по индексу, нумерация с нуля:

```js
items[0]         // 1
items[10]        // undefined — выхода за границы не бывает, есть undefined
```

Длина:

```js
items.length     // 3
```

Всё остальное — функциями стандартной библиотеки, см. главу 8.

## 2.7. Проверка типа во время исполнения

Данные с бэкенда не всегда приходят такими, как ожидалось. Поле, объявленное числом, может оказаться `null`; список может прийти объектом. Поскольку в ChupaLang нет `try`/`catch`, единственный способ защититься — проверить заранее.

Проверки делаются средствами JavaScript:

```js
typeof x === "string"
typeof x === "number"
typeof x === "boolean"
typeof x === "object"
Array.isArray(x)
x == null                  // true для null и undefined
Number.isNaN(x)
```

```js
let name = typeof user.name === "string" ? user.name : "Без имени";
```

У `typeof` есть известные особенности, которые стоит помнить: `typeof null` возвращает `"object"`, и `typeof []` тоже `"object"`. Поэтому для массива используйте `Array.isArray`, а для пустоты — сравнение `== null`.

Если такие проверки повторяются, заведите в init собственные функции:

```js
function isText(x) { return typeof x === "string"; }
function isEmpty(x) { return x == null || x === ""; }
```

# 3. Переменные и состояние

## 3.1. `let` и `const`

Переменная объявляется через `let`:

```js
let total = 0;
total = 150;
```

Если значение не должно меняться, используйте `const`:

```js
const TAX_RATE = 0.2;
TAX_RATE = 0.25;
```

Последняя строка не пройдёт проверку:

```
ошибка: переприсваивание константы
 --> action: Button.onTap
  |
  | TAX_RATE = 0.25;
  | ^^^^^^^^ объявлена как const выше
  |
  = справка: используйте let, если значение должно меняться
```

Есть тонкость, которая часто удивляет. `const` запрещает **переприсваивать имя**, но не запрещает менять содержимое:

```js
const cfg = { retries: 3 };
cfg = { retries: 5 };   // ошибка: переприсваивание
cfg.retries = 5;        // разрешено
```

Во второй строке вы пытаетесь связать имя `cfg` с другим объектом — это запрещено. В третьей объект остаётся тем же самым, меняется только его содержимое. Так же ведёт себя `const` в JavaScript. Если вам нужна настоящая неизменяемость, языка для этого недостаточно — договаривайтесь об этом на уровне соглашений.

Обращаться к переменной до объявления нельзя:

```js
console.log(count);
let count = 0;
```

```
ошибка: обращение к переменной до объявления
 --> action: Button.onTap
  |
  | console.log(count);
  |     ^^^^^ объявлена ниже, на следующей строке
```

В JavaScript такое поведение зависит от того, использовали вы `var` или `let`. В ChupaLang `var` нет вовсе — именно потому, что его правила запутанны и служат источником ошибок, которые трудно заметить.

Объявить несколько переменных сразу можно деструктуризацией:

```js
let { name, age } = user;
let [first, second] = items;
```

Вложенные образцы и значения по умолчанию не поддерживаются: `let { a: { b } } = obj;` не сработает.

## 3.2. Состояние экрана

Переменные, объявленные в init экрана, — особенные. Мы называем их **состоянием экрана**, и они отличаются от обычных переменных двумя свойствами.

Во-первых, они живут всё время, пока экран открыт. Обычная переменная внутри action исчезает, как только action завершился. Состояние экрана переживает и нажатия кнопок, и перерисовки.

Во-вторых, **они реактивны**. Движок знает, какие props читают какую переменную. Когда переменная меняется, он пересчитывает ровно те значения, которые от неё зависели, и перерисовывает соответствующие части экрана.

Рассмотрим счётчик целиком.

```js
// init экрана
let count = 0;
```

```json
{
  "type": "Column",
  "children": [
    { "type": "Text",   "props": { "text": "$$ `Нажато: ${count}`" } },
    { "type": "Button", "props": { "title": "+" }, "onTap": "count = count + 1;" }
  ]
}
```

*Листинг 3-1: счётчик, состоящий из состояния, выражения и действия*

Три части работают вместе. Init объявляет `count` и задаёт начальное значение. Prop у `Text` читает `count` — и тем самым объявляет свою зависимость от него. Action у `Button` изменяет `count`.

Когда пользователь нажимает кнопку, движок исполняет action, обнаруживает, что `count` изменился, находит все выражения, которые его читали, вычисляет их заново и обновляет экран. Вам не нужно ни подписываться на изменения, ни вызывать что-то вроде `refresh()`.

Состояние может прийти и не из init: клиент вправе зарегистрировать переменную сам, до загрузки экрана. Так в язык попадают данные, которые знает нативная часть, — например, профиль пользователя или размеры экрана. Для вашего кода разницы нет: такие переменные читаются и меняются точно так же.

## 3.3. Изменение состояния

Состояние меняется присваиванием. Работают все привычные формы:

```js
count = count + 1;
count += 1;
count++;

isExpanded = !isExpanded;
```

Менять можно и содержимое структур:

```js
user.name = "Аня";
likes[itemId] = likes[itemId] + 1;
cart.items[0].qty = 3;
```

Ключ в квадратных скобках может быть любым выражением — это удобно, когда вы храните данные в словаре по идентификатору.

Объекты и массивы — ссылочные значения, ровно как в JavaScript. Промежуточная переменная указывает на тот же объект, поэтому изменение через неё видно и в состоянии:

```js
let u = user;
u.name = "Аня";      // user.name теперь тоже "Аня"
```

Никаких особых правил здесь нет: если вы знаете, как это работает в JavaScript, вы знаете, как это работает в ChupaLang. Движку не нужно отслеживать, через какую именно переменную произошло изменение, — почему, объясняет раздел 9.5.

Важное ограничение: **props не могут менять состояние.** Выражение вида

```js
count = count + 1
```

в поле props будет отвергнуто:

```
ошибка: изменение состояния в выражении props
 --> screen.json: Text.props.text
  |
  | count = count + 1
  | ^^^^^^^^^^^^^^^^^ props только читают состояние
  |
  = причина: выражение props вычисляется многократно и в непредсказуемом порядке
  = справка: перенесите изменение в action
```

Причина указана в тексте ошибки, и её стоит запомнить. Движок вправе вычислить выражение props один раз, десять раз или ни разу — в зависимости от того, что изменилось и что нужно перерисовать. Если бы такое выражение меняло состояние, результат зависел бы от деталей отрисовки. Отладить это было бы практически невозможно.

## 3.4. Область видимости

Переменная, объявленная внутри блока, видна только в этом блоке:

```js
if (isPremium) {
  let discount = 0.2;
  price = price * (1 - discount);
}

console.log(discount);   // ошибка: переменная не объявлена
```

Это обычная блочная область видимости, как в JavaScript.

Целиком код action тоже считается блоком. Поэтому переменные, объявленные в action, не попадают в состояние экрана и исчезают после его завершения:

```js
// action
let subtotal = 0;
for (let item of cart.items) {
  subtotal = subtotal + item.price * item.qty;
}
total = subtotal;   // total — состояние экрана, subtotal — временная переменная
```

*Листинг 3-2: временные переменные внутри action*

Здесь `subtotal` живёт ровно столько, сколько исполняется action, а `total` сохраняется и вызывает перерисовку.

Обратное направление не работает: код в init не видит переменных, объявленных в actions, — их в этот момент попросту не существует. Схема видимости получается такой:

```
состояние экрана (init)
        ↑ читают и меняют
        |
   ┌────┴─────┬──────────┐
   │          │          │
 props     action A   action B
   │          │          │
 (свои)    (свои)     (свои)      ← локальные переменные не видны друг другу
```

Отсюда простое правило: **если значение нужно нескольким местам или должно пережить нажатие кнопки — это состояние экрана. Если оно нужно только внутри одного действия — это локальная переменная.**

# 4. Контексты исполнения

## 4.1. Четыре профиля

Мы уже несколько раз сталкивались с тем, что одна и та же строка допустима в одном месте и запрещена в другом. Пора описать это правило целиком.

Движок исполняет ваш код в одном из четырёх **профилей**. Профиль определяет вызывающая сторона, а не содержимое строки: движок знает, что читает поле props, и запускает интерпретатор в профиле Prop; знает, что сработал обработчик нажатия, — и запускает профиль Action.

| | Init | Prop | Action | REPL |
|---|---|---|---|---|
| Что можно написать | инструкции | **одно выражение** | инструкции | инструкции |
| Читать состояние | да | да | да | да |
| Менять состояние | да | **нет** | да | да |
| Объявлять состояние | да | нет | нет | да |
| Объявлять функции | да | нет | нет | да |
| Локальные переменные | да | нет | да | да |
| Вызывать хост-функции | только чистые | **только чистые и детерминированные** | по списку | все |
| Когда исполняется | раз при загрузке | при каждом пересчёте | по событию | по вводу |

Строка про хост-функции стоит особняком от остальных: это правило не языка, а движка. Синтаксис вызова везде один и тот же, а что именно разрешено вызывать из каждого профиля — решает клиент, и список зависит от приложения, версии и разрешений конкретного экрана. Подробности в главе 10.

Дальше — о каждом профиле подробно.

## 4.2. Init: подготовка экрана

Init исполняется один раз, когда экран загружается, до первой отрисовки. Это единственное место, где можно объявить состояние экрана и вспомогательные функции.

```js
let count = 0;
let selectedTab = "all";
let expandedSections = {};

function formatPrice(value) {
  return `${value.toFixed(2)} ₽`;
}

function isAvailable(item) {
  return item.stock > 0 && !item.hidden;
}
```

*Листинг 4-1: типичный init экрана*

Функции, объявленные здесь, доступны из props и actions. Это важное свойство: **множество функций фиксируется в момент загрузки экрана**. Позже добавить новую функцию нельзя, и это позволяет движку проверить весь код экрана заранее — мы вернёмся к этому в главе 9.

Из init нельзя ничего делать «во внешнем мире»: навигация, аналитика, сетевые запросы отсюда недоступны. Экран, который перебрасывает пользователя на другой экран прямо при загрузке, почти всегда описан неправильно; такое поведение задаётся на уровне сценария, а не кода инициализации.

Если init завершается с ошибкой, экран не загружается вовсе. Это единственный профиль, где ошибка приводит к отказу целиком, — и это осознанно: экран с наполовину проинициализированным состоянием хуже, чем честное сообщение о сбое.

## 4.3. Props: вычисление значений

В props пишется **ровно одно выражение**. Не последовательность инструкций, не блок с `return` — одно выражение, значение которого станет значением поля.

```json
"title":   "$$ user.name",
"visible": "$$ cart.items.length > 0",
"text":    "$$ isLoading ? 'Загрузка…' : formatPrice(total)"
```

Всё, что требует нескольких шагов, выносится в функцию, объявленную в init:

```js
// init
function statusLabel(order) {
  if (order.cancelled) { return "Отменён"; }
  if (order.deliveredAt != null) { return "Доставлен"; }
  return `В пути, ${order.daysLeft} дн.`;
}
```

```json
"text": "$$ statusLabel(order)"
```

*Листинг 4-2: сложная логика выносится в функцию, prop остаётся выражением*

К props предъявляются два требования, которых нет больше нигде: выражение не меняет состояние и даёт один и тот же результат при одних и тех же данных. Первое мы обсудили в разделе 3.3, второе разберём в главе 9 — оно означает, что вызывать `now()` или `random()` внутри props нельзя.

Ошибка при вычислении props не роняет экран. Значение поля становится `undefined`, компонент получает значение по умолчанию из своей схемы, а факт ошибки попадает в лог диагностики. Экран продолжает работать — с одним неверным полем вместо белого прямоугольника.

## 4.4. Actions: изменение состояния

Action исполняется в ответ на действие пользователя: нажатие, свайп, ввод текста, появление элемента на экране. Здесь доступно всё, чего нет в props: последовательности инструкций, изменение состояния, вызовы наружу.

```js
cart.items[itemId].qty = cart.items[itemId].qty + 1;
track("cart_item_increment", { itemId: itemId });
```

Локальные переменные помогают, когда одно значение нужно несколько раз:

```js
let item = cart.items[itemId];
let newQty = item.qty + 1;

if (newQty > item.stock) {
  showToast("Больше нет в наличии");
} else {
  cart.items[itemId].qty = newQty;
  cartTotal = cartTotal + item.price;
}
```

*Листинг 4-3: action с ветвлением и локальными переменными*

Три правила, которые стоит знать заранее.

**Action исполняется целиком и мгновенно.** Внутри него не бывает ожидания. Если нужно сходить в сеть, вы вызываете хост-функцию, которая запускает запрос и завершается немедленно; результат придёт позже и попадёт в состояние. Ваш action к тому времени давно закончится.

**Изменения применяются одним куском.** Пока action работает, экран не перерисовывается — даже если состояние уже изменилось три раза. Перерисовка происходит один раз, после завершения. Это защищает от промежуточных состояний: пользователь не увидит момент, когда количество уже увеличено, а сумма ещё нет.

**Если action прерывается ошибкой, изменения откатываются.** Состояние возвращается к тому, каким было до начала. Экран остаётся согласованным.

Из action нельзя вызвать другой action. Если два события пришли одновременно, они выполнятся по очереди, а не вложенно.

## 4.5. REPL: интерактивная работа

REPL — консоль, в которой вы вводите код построчно и сразу видите результат:

```
> let items = [3, 1, 2];
> items.slice().sort((a, b) => a - b)
[1, 2, 3]
> Object.keys({ a: 1, b: 2 })
["a", "b"]
```

Здесь доступно всё: объявления, изменение состояния, любые хост-функции. Ограничения профилей сняты, потому что вы работаете руками, а не исполняете код, приехавший по сети.

REPL полезен в двух ситуациях. Первая — проверить выражение до того, как класть его в JSON: гораздо быстрее убедиться, что `order.delivery?.address?.city` возвращает то, что вы ждёте, чем перезагружать экран. Вторая — посмотреть на состояние работающего экрана: подключившись к запущенному приложению, вы можете прочитать любую переменную и понять, почему интерфейс выглядит не так, как задумано.

Помните, что код, отлаженный в REPL, не обязательно пройдёт проверку в props: REPL разрешает больше. Если выражение работает в консоли, но отвергается при загрузке экрана, посмотрите на таблицу в разделе 4.1 — почти наверняка дело в изменении состояния или в недетерминированном вызове.

# 5. Выражения

## 5.1. Арифметика

Операторы обычные: `+`, `-`, `*`, `/`, `%` (остаток), `**` (возведение в степень), а также унарные `+` и `-`.

```js
total * 1.2
(a + b) / 2
count % 2 === 0        // чётное ли
```

Приоритеты — как в математике и как в JavaScript: сначала `**`, потом `*`, `/`, `%`, потом `+` и `-`. Скобки работают как ожидается.

Оператор `+` перегружен: с числами он складывает, со строками склеивает. Если типы разные, происходит приведение по правилам JavaScript, и результат бывает неожиданным:

```js
1 + "2"        // "12" — строка, а не 3
```

Именно поэтому для сборки текста лучше использовать шаблонные строки (раздел 5.5): в них намерение видно явно.

## 5.2. Сравнения

Доступны `<`, `<=`, `>`, `>=`, а также четыре оператора равенства: `===`, `!==`, `==`, `!=`.

**Используйте `===` и `!==` по умолчанию.** Они сравнивают без приведения типов:

```js
1 === 1        // true
1 === "1"      // false
```

`==` приводит типы перед сравнением, и его правила содержат неприятные сюрпризы:

```js
0 == ""        // true
0 == "0"       // true
"" == "0"      // false
```

Есть ровно одно место, где `==` полезен, — проверка на «пусто», охватывающая и `null`, и `undefined`:

```js
if (user.email == null) { ... }
```

Во всех остальных случаях `==` стоит считать опечаткой.

Объекты и массивы сравниваются по идентичности, а не по содержимому:

```js
{ a: 1 } === { a: 1 }      // false — это два разных объекта
```

Если нужно сравнить содержимое, сравнивайте поля явно или воспользуйтесь функцией из стандартной библиотеки, если она предоставлена клиентом.

## 5.3. Логические операторы

`&&`, `||` и `!` ведут себя как в JavaScript, включая два свойства, которые стоит понимать.

**Вычисление сокращённое.** В `a && b` выражение `b` не вычисляется, если `a` ложно. Это позволяет писать безопасные проверки:

```js
user != null && user.age > 18
```

**Результат — не обязательно булево значение.** `a || b` возвращает `a`, если оно истинно, иначе `b`:

```js
user.nickname || "Аноним"
```

Выглядит удобно, но здесь прячется ловушка. Пустая строка ложна, поэтому:

```js
user.nickname || "Аноним"     // при nickname === "" даст "Аноним"
displayCount || "нет"         // при count === 0 даст "нет"
```

Если вы хотите подставить запасное значение только при `null` и `undefined`, используйте `??` — см. раздел 5.6.

## 5.4. Тернарный оператор

Единственный способ ветвиться внутри выражения, а значит — основной инструмент в props:

```js
isLoading ? "Загрузка…" : "Готово"
```

Тернарники можно вкладывать, но с этим легко переборщить:

```js
// плохо читается
status === "new" ? "Новый" : status === "paid" ? "Оплачен" : "Неизвестно"
```

Начиная с двух уровней вложенности, выносите логику в функцию с `if` (листинг 4-2). В props останется вызов, а читаться будет несравнимо лучше.

## 5.5. Шаблонные строки

Строка в обратных кавычках позволяет подставлять значения прямо в текст:

```js
`Привет, ${user.name}!`
`Осталось ${count} из ${total}`
`Итого: ${sum.toFixed(2)} ₽`
```

Внутри `${...}` допустимо любое выражение. Обратные кавычки не требуют экранирования в JSON, поэтому в описании экрана это выглядит нормально:

```json
"text": "$$ `Нажато: ${count}`"
```

Шаблонные строки — предпочтительный способ собирать текст. Они читаются лучше, чем цепочка `+`, и не подвержены сюрпризам приведения типов.

## 5.6. Работа с отсутствующими данными

Данные с бэкенда бывают неполными, и это не исключительная ситуация, а норма. Два оператора делают такой код терпимым.

**Опциональная цепочка `?.`** прерывает обращение, если слева `null` или `undefined`, и возвращает `undefined` вместо ошибки:

```js
user.profile.city        // ошибка, если profile === null
user.profile?.city       // undefined, если profile === null
```

Работает и со скобками, и с вызовом:

```js
data?.[key]
onSelect?.(item)
```

**Нулевое слияние `??`** подставляет запасное значение, но только при `null` и `undefined`:

```js
user.nickname ?? "Аноним"     // при nickname === "" даст "" — а не "Аноним"
discount ?? 0                 // при discount === 0 даст 0
```

Именно этим `??` отличается от `||`, и почти всегда нужен именно он.

Вместе они дают компактную и безопасную запись:

```js
`${user.profile?.city ?? "Город не указан"}`
```

*Листинг 5-1: типичное выражение props, устойчивое к неполным данным*

Если путь к данным приходит строкой, а не пишется в коде, напишите вспомогательную функцию — пример есть в разделе 8.6.

# 6. Управляющие конструкции

Всё, что описано в этой главе, доступно только в профилях Init, Action и REPL. В props пишется одно выражение, поэтому ни условий-инструкций, ни циклов там быть не может — ветвление в props делается тернарным оператором.

## 6.1. Условия

```js
if (cart.items.length === 0) {
  showToast("Корзина пуста");
} else if (total > balance) {
  showToast("Недостаточно средств");
} else {
  submitOrder();
}
```

Фигурные скобки обязательны даже для одной инструкции. В JavaScript их можно опустить, в ChupaLang — нет: слишком дорого обходится ошибка при последующем редактировании.

## 6.2. Цикл `for...of`

Единственный цикл в языке. Он обходит элементы массива:

```js
let subtotal = 0;
for (let item of cart.items) {
  subtotal = subtotal + item.price * item.qty;
}
```

Переменная цикла объявляется через `let` или `const` и видна только внутри тела.

Если нужен индекс, обходите результат `entries`:

```js
for (let pair of Object.entries(items)) {
  console.log(`${pair[0]}: ${pair[1]}`);
}
```

Словарь обходится по ключам:

```js
for (let key of Object.keys(likes)) {
  totalLikes = totalLikes + likes[key];
}
```

*Листинг 6-1: обход словаря*

На практике циклы нужны реже, чем кажется: большинство задач короче и понятнее решается функциями из главы 8.

## 6.3. Длина массива фиксируется на входе в цикл

Здесь находится **единственное место, где ChupaLang ведёт себя не так, как JavaScript.**

Рассмотрим цикл, который добавляет элементы в тот же массив, который обходит:

```js
let arr = [1, 2, 3, 4, 5];
for (const num of arr) {
  arr.push(1);
}
```

*Листинг 6-2: цикл, который в JavaScript не завершится*

В JavaScript этот код зациклится навсегда. Обход массива устроен так, что на каждом шаге проверяется текущая длина: добавили элемент — появился ещё один шаг, добавили снова — ещё один. Массив растёт быстрее, чем цикл его проходит.

В ChupaLang **длина массива запоминается перед первой итерацией**, и цикл выполнит ровно пять шагов. Элементы, добавленные во время обхода, не будут посещены. После цикла `arr` содержит десять элементов — пять исходных и пять добавленных, — но обошли мы только первые пять.

Обратное направление работает как в JavaScript: если массив стал **короче**, цикл завершается досрочно. Формально правило звучит так: цикл обходит индексы от нуля, пока не достигнет либо длины, зафиксированной на входе, либо текущей длины массива — что наступит раньше.

```js
let arr = [1, 2, 3, 4, 5];
for (const num of arr) {
  arr.splice(0, 2);        // цикл прервётся, когда индекс выйдет за длину
}
```

Причина расхождения та же, что у отсутствия `while` (раздел 6.5): число итераций любого цикла должно быть известно до его начала. Без этого правила `push` внутри цикла давал бы бесконечное исполнение — при том что синтаксически код выглядел бы совершенно безобидно, а проверка при загрузке экрана не смогла бы его отличить от корректного.

На практике вы вряд ли столкнётесь с этим намеренно: изменять коллекцию во время её обхода — известный источник ошибок в любом языке. Если элементы нужно добавить, собирайте их в отдельный массив:

```js
let extra = [];
for (const item of items) {
  if (needsCopy(item)) { extra.push(item); }
}
items = items.concat(extra);
```

*Листинг 6-3: безопасный способ дополнить коллекцию при обходе*

## 6.4. `break` и `continue`

Работают как обычно:

```js
for (let item of items) {
  if (item.hidden) { continue; }
  if (found != null) { break; }
  ...
}
```

Меток (`break outer`) нет. Если понадобилось прервать внешний цикл из внутреннего, вынесите внутренний цикл в функцию и воспользуйтесь `return`.

## 6.5. Почему в языке нет `while`

Это самое заметное отличие ChupaLang от JavaScript, и оно требует объяснения.

Ваш код исполняется в том же потоке, который рисует интерфейс. Бесконечный цикл здесь означает не «скрипт завис», а «приложение перестало отвечать» — пользователь видит замерший экран и убивает приложение. При этом код приезжает с бэкенда: ошибка в шаблоне экрана мгновенно доходит до всех пользователей, минуя ревью и тесты.

`for...of` устроен так, что число итераций известно до начала цикла — оно равно длине коллекции. Такой цикл всегда завершается. `while` этой гарантии не даёт, и никакая проверка не может отличить корректный `while` от ошибочного.

По той же причине нет и обычного `for (let i = 0; i < n; i++)`: условие в нём произвольное, значит это тот же `while` в другой записи.

Что делать, если алгоритм всё-таки требует цикла с условием? Три ответа, по убыванию предпочтительности:

1. **Пересмотреть задачу.** Почти всегда речь идёт об обходе коллекции, и `for...of` подходит.
2. **Перенести вычисление на бэкенд.** Если логика достаточно сложная, чтобы требовать `while`, ей место на сервере — оттуда придёт готовый результат.
3. **Попросить хост-функцию.** Клиент может реализовать нужную операцию нативно и предоставить её вызовом.

Отсутствия `while` самого по себе не хватило бы: цикл `for...of` можно было бы продлевать бесконечно, добавляя элементы в обходимый массив. Именно поэтому длина фиксируется на входе — см. раздел 6.3.

Стоит понимать, что и этого недостаточно для гарантии быстроты. `for...of` по массиву в миллион элементов повесит интерфейс не хуже бесконечного цикла, а вложенные циклы легко дают квадратичную сложность. Поэтому вдобавок действуют ограничения на число шагов, о которых глава 12.

# 7. Функции

## 7.1. Объявление функций

Функции объявляются **только в init экрана**:

```js
function formatPrice(value) {
  return `${value.toFixed(2)} ₽`;
}

function statusLabel(order) {
  if (order.cancelled) { return "Отменён"; }
  if (order.deliveredAt != null) { return "Доставлен"; }
  return "В пути";
}
```

После этого их можно вызывать откуда угодно — из props, из actions, из других функций:

```json
"text": "$$ statusLabel(order)"
```

Функция без явного `return` возвращает `undefined`.

Выносить логику в функции стоит по двум причинам, помимо переиспользования. Во-первых, в props допустимо только выражение, и функция — единственный способ применить там `if` или цикл. Во-вторых, имя функции документирует намерение: `statusLabel(order)` в описании экрана понятнее, чем развесистый тернарник.

## 7.2. Значения параметров по умолчанию

```js
function formatPrice(value, currency = "₽") {
  return `${value.toFixed(2)} ${currency}`;
}

formatPrice(100);         // "100.00 ₽"
formatPrice(100, "$");    // "100.00 $"
```

Значение по умолчанию подставляется, когда аргумент не передан или равен `undefined`. Вычисляется оно при каждом вызове.

Если аргументов передано меньше, чем параметров, и значения по умолчанию нет, параметр получает `undefined`. Лишние аргументы отбрасываются — получить их нельзя, так как `arguments` и rest-параметры в языке отсутствуют.

## 7.3. Стрелочные функции

Короткая запись, знакомая по JavaScript:

```js
x => x + 1
(a, b) => a + b
item => { return item.price * item.qty; }
```

Нужны они ровно для одного: передавать в функции работы с коллекциями.

```js
items.filter(x => x.enabled)
items.map(x => x.title)
items.slice().sort((a, b) => a.price - b.price)
```

Если тело — одно выражение, `return` не пишется: результат выражения и есть возвращаемое значение. Если тело в фигурных скобках, `return` обязателен.

## 7.4. Почему функцию нельзя положить в переменную

Стрелочную функцию разрешено писать **только непосредственно в аргументе вызова**. Всё остальное — ошибка:

```js
items.filter(x => x.enabled)              // можно
items.slice().sort((a, b) => a.price - b.price) // можно

let f = x => x + 1;                        // нельзя
let handlers = { onTap: () => close() };   // нельзя
let checks = [x => x > 0, x => x < 100];   // нельзя
```

```
ошибка: функция вне позиции аргумента
 --> init
  |
  | let f = x => x + 1;
  |         ^^^^^^^^^^ стрелочная функция допустима только как аргумент вызова
  |
  = справка: объявите обычную функцию: function f(x) { return x + 1; }
```

Причина в том, что свободно перемещающиеся функции ломают проверку, ради которой построен весь язык.

Движок проверяет описание экрана в момент загрузки: находит все выражения props и убеждается, что ни одно из них не меняет состояние. Для этого нужно знать, что именно вызывает каждое выражение. Пока функции объявлены поимённо в init, это разрешимо: список функций известен, и по нему легко пройти.

Как только функцию можно положить в переменную, массив или поле объекта, вызов перестаёт быть определённым:

```js
let fn = condition ? doSomething : doOther;
fn();     // что именно будет вызвано — неизвестно до исполнения
```

Проверить такой код заранее невозможно. Значит, ошибка вместо сообщения при загрузке экрана превратится в странное поведение у пользователя.

Из того же соображения следует второе ограничение: **функцию нельзя передать в функцию, объявленную вами.**

```js
// init
function firstMatching(list, pred) {      // ошибка
  return list.find(pred);
}
```

```
ошибка: параметр используется как функция
 --> init: функция firstMatching
  |
  | return list.find(pred);
  |                  ^^^^ параметр pred вызывается как функция
  |
  = справка: воспользуйтесь встроенным find непосредственно
```

Лямбду принимают только встроенные методы (`map`, `filter`, `find`, `sort` и подобные) и хост-функции — то есть те, чьё поведение движку известно.

Разница может показаться придирчивой, но без неё вся конструкция разваливается. Достаточно одной функции, вызывающей свой параметр, чтобы получить бесконечное исполнение из совершенно невинно выглядящего кода:

```js
function apply(f) { return f(f); }
apply(x => x(x));                    // не завершится никогда
```

Здесь нет ни рекурсии по имени, ни цикла, ни захваченных переменных — обе функции написаны строго по правилам. Разорвать это можно только одним способом: не позволять функциям попадать туда, где их применяют к самим себе.

Вместе оба ограничения дают инвариант, на который опирается вся проверка экрана:

> **Каждый вызов синтаксически называет то, что вызывается**: функцию из init, хост-функцию или встроенный метод. Ни одно выражение не вычисляется в функцию.

Стоит это недорого: в описаниях экранов таблицы обработчиков, функции-фабрики и функции высшего порядка почти не встречаются, а `map` с `filter` продолжают работать.

## 7.5. Почему в языке нет рекурсии

Функция не может вызвать себя — ни напрямую, ни через цепочку других функций:

```js
function factorial(n) {
  if (n <= 1) { return 1; }
  return n * factorial(n - 1);      // ошибка
}
```

```
ошибка: рекурсивный вызов
 --> init
  |
  |   return n * factorial(n - 1);
  |              ^^^^^^^^^ функция вызывает саму себя
  |
  = причина: рекурсия не позволяет гарантировать завершение
```

Причина та же, что у `while`: рекурсия — это цикл, число шагов которого нельзя узнать заранее. Отказавшись и от неё, и от `while`, мы получаем свойство, которое стоит того: **любой код на ChupaLang заведомо завершается**, и это проверяется до того, как экран показан пользователю.

Ограничения предыдущего раздела нужны в том числе для этого. Без них рекурсию можно выразить, не называя ни одной функции по имени, — и никакая проверка её не поймает.

Задачи, которые обычно решают рекурсией, в описании экрана встречаются в одном виде — обход дерева (например, вложенных комментариев). Здесь два пути: попросить бэкенд прислать дерево уже развёрнутым в плоский список с уровнем вложенности, либо воспользоваться компонентом, который умеет рекурсивно рендерить сам себя. Второе — забота движка, а не языка.

# 8. Работа с коллекциями

Всё в этой главе — обычные методы JavaScript. Отдельной библиотеки у ChupaLang нет, поэтому справочником служит документация по `Array`, `String` и `Object`.

Доступны и те методы, что изменяют коллекцию на месте (`push`, `sort`, `reverse`, `splice`), и те, что возвращают новое значение (`map`, `filter`, `slice`). Работают они как в JavaScript — но только в actions и init: в props любое изменение данных запрещено, см. раздел 9.2.

## 8.1. Преобразование и отбор

`map` применяет функцию к каждому элементу:

```js
items.map(x => x.title)                    // ["Кофе", "Чай"]
items.map(x => x.price * x.qty)            // [200, 150]
```

`filter` оставляет элементы, для которых функция вернула истину:

```js
items.filter(x => x.stock > 0)
orders.filter(o => o.status === "paid")
```

Вызовы соединяются в цепочку — это читается слева направо и почти всегда понятнее вложенных вызовов:

```js
let titles = items.filter(x => x.enabled).map(x => x.title);
```

*Листинг 8-1: отбор с последующим преобразованием*

Если цепочка длиннее двух-трёх звеньев, вынесите её в функцию с промежуточными переменными.

## 8.2. Поиск и проверка

```js
items.find(x => x.id === selectedId)     // первый подходящий или undefined
items.findIndex(x => x.id === selectedId)
items.some(x => x.stock === 0)           // есть ли хоть один
items.every(x => x.stock > 0)            // подходят ли все
items.includes("кофе")                   // есть ли значение
items.indexOf("кофе")                    // позиция или -1
```

`find` возвращает `undefined`, если ничего не нашлось, — проверяйте результат:

```js
let item = cart.items.find(x => x.id === itemId);
if (item != null) {
  ...
}
```

## 8.3. Свёртка

```js
items.reduce((acc, x) => acc + x.price * x.qty, 0)
```

Второй аргумент — начальное значение. Указывайте его всегда: без него `reduce` по пустому массиву — ошибка.

Читается `reduce` тяжелее, чем цикл, и в описаниях экранов редко окупается. Сравните:

```js
let sum = 0;
for (let x of items) {
  sum = sum + x.price * x.qty;
}
```

Второй вариант длиннее, но понятнее большинству читателей.

## 8.4. Сортировка

`sort` сортирует массив на месте и возвращает его же:

```js
items.sort((a, b) => a.price - b.price);        // по возрастанию цены
items.sort((a, b) => b.price - a.price);        // по убыванию
messages.reverse();
```

Функция сравнения должна вернуть отрицательное число, если первый аргумент идёт раньше, положительное — если позже, и ноль, если порядок неважен. Для чисел годится вычитание, для строк — `localeCompare`:

```js
names.sort((a, b) => a.localeCompare(b));
```

Если исходный массив нужно сохранить, отсортируйте копию — `slice()` без аргументов её делает:

```js
let byPrice = items.slice().sort((a, b) => a.price - b.price);
```

*Листинг 8-2: сортировка копии, когда исходный порядок ещё нужен*

Сортировать прямо в props нельзя: `sort` изменяет данные, а выражения props их только читают.

## 8.5. Добавление и удаление

```js
selectedIds.push(itemId);              // добавить в конец
cart.items.splice(index, 1);           // удалить один элемент
```

Второй способ — собрать новый массив и присвоить его. Он длиннее, но иногда читается лучше:

```js
selectedIds = selectedIds.concat([itemId]);
cart.items = cart.items.filter(x => x.id !== itemId);
```

Оба варианта равноправны: движок увидит изменение в любом случае.

Прочее:

```js
items.slice(0, 3)                    // первые три
a.concat(b)                          // склейка
tags.map(t => t.name).join(", ")     // сборка в строку
```

## 8.6. Работа со словарями

Объект в ChupaLang — это словарь (раздел 2.5). Работают статические методы `Object`:

```js
Object.keys(likes)                     // ["42", "43"]
Object.values(likes)                   // [10, 3]
Object.entries(likes)                  // [["42", 10], ["43", 3]]
"email" in user                        // есть ли ключ
```

Оператор `in` отличается от проверки на `undefined`: ключ может существовать и содержать `undefined`.

Копия с изменённым полем — `Object.assign`:

```js
Object.assign({}, user, { name: "Аня" })
```

Первый аргумент — пустой объект: он и станет результатом. Если передать первым `user`, метод изменит сам `user`, а не создаст копию.

Для более сложных операций — выборки полей, удаления, работы с вложенными путями — заведите функции в init:

```js
function pick(obj, fields) {
  let out = {};
  for (let f of fields) {
    if (f in obj) { out[f] = obj[f]; }
  }
  return out;
}

function getPath(obj, path, fallback) {
  let cur = obj;
  for (let part of path.split(".")) {
    if (cur == null) { return fallback; }
    cur = cur[part];
  }
  return cur == null ? fallback : cur;
}
```

*Листинг 8-3: вспомогательные функции пишутся на самом языке*

Это общий приём: всё, чего нет в JavaScript, вы дописываете сами. Язык не вводит собственных функций именно для того, чтобы код оставался обычным JavaScript.

# 9. Чистота и детерминизм

## 9.1. Что такое побочный эффект

Функция обладает **побочным эффектом**, если делает что-то помимо вычисления результата: меняет состояние экрана, показывает уведомление, отправляет событие в аналитику, инициирует переход.

```js
function total(items) {                    // без эффектов
  let sum = 0;
  for (let x of items) { sum = sum + x.price; }
  return sum;
}

function totalAndTrack(items) {            // с эффектом
  track("total_computed");                 // ← отправка события
  ...
}
```

Функции без побочных эффектов мы называем **чистыми**.

Отдельно стоит свойство **детерминизма**: функция детерминирована, если при одних и тех же аргументах и одном и том же состоянии всегда возвращает одно и то же. `now()` и `random()` ничего не меняют — они чистые, — но недетерминированы.

## 9.2. Почему props должны быть чистыми

Выражение props вычисляется движком тогда, когда ему нужно. Сколько раз — неизвестно: может один, может десять при прокрутке, может ни одного, если результат взят из кэша. Порядок вычисления соседних props тоже не определён.

Это нормально для вычисления значения и катастрофично для эффекта. Представьте prop, отправляющий событие в аналитику: число событий стало бы зависеть от того, как пользователь скроллил экран. Или prop, увеличивающий счётчик: его значение зависело бы от числа перерисовок.

Отсюда требование: **выражение props должно быть чистым и детерминированным.**

Оно не только проверяется при загрузке экрана, но и обеспечивается во время исполнения: в профиле Prop интерпретатор отказывается выполнять любое изменение данных — присваивание, `push`, `sort`, `splice`. Даже если ошибку не удалось заметить заранее, испортить состояние выражение props не сможет.

```
ошибка: попытка изменить данные при вычислении props
 --> screen.json: List.props.items
  |
  | items.sort((a, b) => a.price - b.price)
  |       ^^^^ метод изменяет массив
  |
  = справка: отсортируйте копию — items.slice().sort(...)
  = справка: или отсортируйте один раз в action и сохраните результат
```

Недетерминированность бьёт тоньше, чем эффект, и потому заслуживает примера:

```json
"text": "$$ `Обновлено ${formatTime(now())}`"
```

```
ошибка: недетерминированный вызов в выражении props
 --> screen.json: Text.props.text
  |
  | `Обновлено ${formatTime(now())}`
  |                         ^^^^^ now() возвращает разное значение при каждом вызове
  |
  = причина: props могут вычисляться повторно; значение зависело бы от момента отрисовки
  = справка: заведите переменную состояния, обновляемую клиентом
```

Правильный способ — попросить клиент положить время в состояние:

```js
// init
let currentTime = 0;   // клиент обновляет раз в секунду
```

```json
"text": "$$ `Обновлено ${formatTime(currentTime)}`"
```

Теперь значение зависит только от состояния, и движок точно знает, когда его пересчитывать. Заодно текст обновляется ровно раз в секунду, а не при каждой перерисовке.

## 9.3. Как проверка распространяется на вызовы

Запретить присваивание внутри выражения props недостаточно. Эффект может прятаться в вызове:

```js
// init
function fmt(x) {
  renderCount = renderCount + 1;     // ← эффект
  return `${x} ₽`;
}
```

```json
"title": "$$ fmt(item.price)"
```

Само выражение `fmt(item.price)` не содержит присваиваний — но при вычислении меняет состояние.

Поэтому чистота определяется рекурсивно: функция чиста, если не пишет в состояние, не вызывает нечистых хост-функций и вызывает только чистые функции. Требование к props относится ко всему, что выражение вызывает, а не только к его тексту.

В примере выше `fmt` нечиста, значит выражение props нечисто:

```
ошибка: изменение состояния при вычислении props
 --> screen.json: Button.props.title
  |
  | fmt(item.price)
  | ^^^ функция fmt изменяет состояние
  |
 --> init: функция fmt
  |
  |   renderCount = renderCount + 1;
  |   ^^^^^^^^^^^ здесь
```

## 9.4. Что проверяется до загрузки экрана

Ограничения предыдущих глав складываются в полезное свойство. Функции объявляются только в init. Их нельзя положить в переменную и нельзя передать в другую вашу функцию. Значит, у каждого вызова видно, что именно вызывается, и **набор функций вместе со всеми связями между ними известен сразу после получения описания экрана** — а циклов в этих связях нет.

Благодаря этому движок может проверить экран целиком до первой отрисовки:

- каждое выражение props действительно чисто и детерминировано, с учётом всех вызовов;
- ни одна функция не вызывает саму себя — ни напрямую, ни по цепочке;
- каждый цикл заведомо конечен;
- все вызываемые функции и хост-функции существуют и разрешены;
- код синтаксически корректен.

Экран, не прошедший проверку, не показывается — вместо этого приходит понятная ошибка. Это и есть цель, ради которой мы отказались от `while`, рекурсии и функций как значений: **ошибки в описании экрана обнаруживаются при загрузке, а не у пользователя.**

## 9.5. Что даёт чистота движку

У требования чистоты есть второе следствие, менее очевидное, но важное для понимания того, как всё работает.

Если выражение props чисто и детерминировано, то вычислить его лишний раз — операция без последствий: результат тот же, побочных эффектов нет, отличить одно вычисление от десяти невозможно. **Значит, движок волен пересчитывать props столько раз, сколько ему удобно.**

Именно поэтому в разделе 3.3 не понадобилось никаких особых правил про промежуточные переменные. Порядок работы такой:

1. Пользователь нажимает кнопку, движок исполняет action.
2. Action меняет состояние — как угодно, через сколько угодно ссылок и вложенных полей.
3. Action завершается. Движок пересчитывает выражения props.
4. Значения, отличающиеся от прежних, отправляются на отрисовку.

Движку не нужно знать, что именно изменилось. Он сравнивает **результаты** выражений, а не следит за данными. Поэтому `user.name = "Аня"`, `u.name = "Аня"` через промежуточную переменную и `items.push(x)` одинаково приводят к обновлению экрана — все три меняют то, что вернёт выражение props.

Отсюда же и запрет из раздела 9.2: если бы выражение props могло что-то менять, повторный пересчёт перестал бы быть безобидным, и вся схема развалилась бы.

# 10. Хост-функции

## 10.1. Что предоставляет клиент

Стандартная библиотека умеет считать и преобразовывать данные, но не умеет ничего показывать, никуда переходить и ни с кем общаться. Всё это делают **хост-функции** — их реализует нативная часть приложения и предоставляет вашему коду.

Типичный набор:

```js
navigate("/cart");                          // переход на другой экран
back();                                     // назад
showToast("Сохранено");                     // уведомление
track("button_tap", { screen: "cart" });    // аналитика
t("cart.empty.title");                      // строка перевода
formatMoney(1990, "RUB");                   // форматирование по локали
formatDate(order.createdAt, "d MMMM");      // дата по локали
```

Конкретный список зависит от приложения и версии клиента — уточняйте его у команды, которая ведёт движок.

Форматирование стоит отдельного упоминания. В ChupaLang нет типа даты и нет средств локализации: и то и другое требует знания часового пояса, языка и региональных настроек, которые есть у платформы, но не у языка. Поэтому даты приходят с бэкенда числом или строкой, а превращает их в читаемый текст хост-функция.

## 10.2. Разрешения

Не всякая хост-функция доступна из любого места.

**В props разрешены только чистые и детерминированные функции.** `formatMoney` и `t` — да; `navigate`, `track`, `now` — нет. Причины разобраны в главе 9.

**В init разрешены только чистые функции.** Экран, который при загрузке отправляет аналитику или перебрасывает пользователя дальше, почти всегда описан неправильно.

**В actions разрешено всё, что клиент явно разрешил этому экрану.** Даже здесь список не бесконечен: доступны только функции, включённые в разрешения экрана. Возможность делать сетевые запросы или писать в хранилище выдаётся адресно, а не по умолчанию.

Обращение к недоступной функции — ошибка проверки, а не времени исполнения:

```
ошибка: функция недоступна в этом контексте
 --> screen.json: Text.props.text
  |
  | navigate("/cart")
  | ^^^^^^^^ функция с побочными эффектами недоступна в props
  |
  = справка: перенесите вызов в action
```

## 10.3. Время, случайность и параметры устройства

Текущее время, случайные числа, размеры экрана, состояние сети — всё это меняется само по себе, поэтому читать их прямо в props нельзя.

Правильная схема: клиент кладёт значение в состояние и обновляет, когда оно меняется. Ваш код читает обычную переменную.

```js
// init
let currentTime = 0;      // клиент обновляет раз в секунду
let isOnline = true;      // клиент обновляет при смене состояния сети
let screenWidth = 0;      // клиент обновляет при повороте
```

```json
"visible": "$$ !isOnline",
"columns": "$$ screenWidth > 600 ? 2 : 1"
```

*Листинг 10-1: изменчивые величины приходят через состояние*

Плюс не только в корректности: движок точно знает, когда пересчитывать зависимые значения, и не пересчитывает их лишний раз.

В actions ограничение снято — там `now()` и `random()` доступны, потому что action исполняется один раз, в конкретный момент:

```js
lastRefreshedAt = now();
```

## 10.4. Асинхронные операции

В ChupaLang нет `async`, `await` и промисов. Ваш код всегда исполняется целиком и мгновенно.

Асинхронную работу выполняет клиент. Вы её запускаете, она завершается позже, результат попадает в состояние:

```js
// action по нажатию «Обновить»
isLoading = true;
reloadOrders();          // возвращается немедленно, запрос идёт в фоне
```

```js
// init
let isLoading = false;
let orders = [];
```

Когда запрос завершится, клиент запишет `orders` и сбросит `isLoading`. Экран перерисуется сам — вам не нужно ничего ждать и ни на что подписываться.

*Листинг 10-2: загрузка данных без асинхронности в языке*

Такая схема означает, что состояние загрузки вы моделируете явно — переменной. Это чуть многословнее, чем `await`, зато интерфейс всегда отражает реальное положение дел: пока `isLoading` истинно, показывается индикатор.

## 10.5. Почему это всё ещё JavaScript

Хост-функции — единственное, что отличает окружение ChupaLang от пустого JavaScript. Ровно так же устроен любой JS: браузерный скрипт опирается на `document` и `fetch`, код в Node — на `require` и `process`. Сам язык от этого не перестаёт быть языком.

Отсюда практическое следствие. Хост-функции реализуются на всех платформах, включая веб, — значит, на вебе ваш код исполняется настоящим движком JavaScript, без промежуточного слоя. Один и тот же фрагмент даёт один и тот же результат в мобильном приложении и в браузере.

Для команды, которая ведёт движок, это ещё и способ проверки: если интерпретатор на устройстве и V8 в браузере расходятся на одном входе, расходится интерпретатор. Расхождений быть не должно — язык устроен так, что их неоткуда взять.

Разумеется, JavaScript не станет отказываться исполнять `while` или рекурсию. Гарантии из главы 9 обеспечиваются проверкой описания экрана, а не движком, который его исполняет.

# 11. Ошибки и диагностика

## 11.1. Ошибки разбора

Обнаруживаются при получении описания экрана, до отрисовки. Сюда попадают синтаксические ошибки, обращения к несуществующим функциям, нарушения правил профиля (изменение состояния в props, рекурсия, функция вне позиции аргумента).

Экран с такой ошибкой не показывается. Это может выглядеть строго, но альтернатива хуже: экран, который выглядит правильно и ведёт себя неправильно, отлаживается неделями.

Одна из самых частых ошибок этой категории — забытая точка с запятой:

```js
count = count + 1
navigate("/cart");
```

```
ошибка: пропущен разделитель инструкций
 --> action: Button.onTap
  |
  | count = count + 1
  |                  ^ ожидается ;
```

В JavaScript этот код работает благодаря автоматической расстановке точек с запятой. В ChupaLang её нет: правила расстановки в JS сложны и в редких случаях дают не тот результат, которого ждёт автор. Разделитель обязателен.

## 11.2. Ошибки времени исполнения

Часть проблем невозможно обнаружить заранее, потому что они зависят от данных:

```js
user.profile.city        // если profile пришёл null
items[i].price           // если i вышел за границы
```

Обращение к полю `null` или `undefined` — ошибка. Обращение к несуществующему полю существующего объекта — не ошибка, а `undefined`. Разница существенна:

```js
let user = { name: "Аня" };

user.email               // undefined — поля нет, но объект есть
user.profile.city        // ошибка — profile равен undefined
user.profile?.city       // undefined — вы явно допустили отсутствие
```

Оператор `?.` из раздела 5.6 — основной инструмент защиты. Пишите его там, где данные действительно могут отсутствовать, и не пишите там, где не могут: `?.` на каждом шаге пути превращает опечатку в тихо пустой экран.

## 11.3. Что происходит, когда падает prop

Ошибка при вычислении props **не роняет экран**. Происходит следующее:

1. Значение поля становится `undefined`.
2. Компонент подставляет значение по умолчанию из своей схемы.
3. Ошибка записывается в лог диагностики: экран, путь к полю, выражение, сообщение.

Пользователь видит экран с одним неверным полем — вместо белого прямоугольника или закрытого приложения. Это осознанный выбор: интерфейс, потерявший подпись у кнопки, всё ещё полезен.

Обратная сторона в том, что ошибку легко не заметить. Поэтому лог диагностики стоит смотреть — особенно после изменений в шаблонах экранов.

## 11.4. Что происходит, когда падает action

Здесь поведение другое: **все изменения откатываются**.

Пока action исполняется, изменения состояния копятся и не применяются. Если он дошёл до конца — применяются разом. Если прервался ошибкой или лимитом — отбрасываются целиком.

```js
cart.items[itemId].qty = newQty;      // изменение записано, но не применено
cartTotal = cartTotal + item.price;   // и это тоже
recalculateDiscounts();               // ← здесь ошибка
```

Ни одно из изменений не вступит в силу. Экран останется таким, каким был до нажатия.

Это лучше, чем частично применённое изменение: количество товара увеличилось, а сумма нет — состояние, которого не должно существовать, и которое пользователь наверняка сфотографирует и пришлёт в поддержку.

## 11.5. Отладка

Основной инструмент — `console.log`:

```js
console.log(user);
console.log(`itemId = ${itemId}, qty = ${item.qty}`);
```

`console.log` печатает значение любого типа, включая объекты и массивы. Отдельной функции сериализации в языке нет — она не нужна.

Помните, что `console.log` — функция с побочным эффектом, а значит в props недоступна. Чтобы разобраться, почему выражение props даёт не то, воспользуйтесь REPL (раздел 4.5): подключитесь к работающему экрану и вычислите выражение вручную, по частям.

```
> order.delivery
{ address: null, type: "courier" }
> order.delivery.address?.city
undefined
> order.delivery?.address?.city ?? "не указан"
"не указан"
```

*Листинг 11-1: разбор выражения по частям в REPL*

# 12. Ограничения ресурсов

## 12.1. Лимит шагов

Отсутствие `while` и рекурсии гарантирует, что код завершится, но не говорит когда. `for...of` по очень длинному массиву или пара вложенных циклов способны занять UI-поток надолго.

Поэтому каждое исполнение ограничено числом шагов. Превышение прерывает исполнение с ошибкой:

```
ошибка: превышен лимит шагов
 --> action: Button.onTap
  |
  = выполнено 100000 шагов, лимит исчерпан
  = изменения состояния отменены
  = справка: вложенные циклы по большим коллекциям лучше вынести на бэкенд
```

> **TODO.** Конкретные значения лимитов для профилей Init, Prop и Action не определены. Требуется замер на реальных экранах.

## 12.2. Бюджет кадра

У props лимит жёстче, чем у actions, и на то есть причина: выражение вычисляется не один раз, а для каждого узла дерева, и не однажды, а при каждой перерисовке. Сотня узлов на экране умножает любой лимит на сто.

> **TODO.** Помимо лимита на отдельное выражение обсуждается общий бюджет на кадр — суммарная работа всех props за одну перерисовку — и поведение при его исчерпании. Это деталь устройства движка, а не языка: она не меняет смысл ни одной конструкции и на вебе не проявляется вовсе. Решение и формулировку откладываем.

На практике это означает: тяжёлые вычисления не место в props. Если список нужно отфильтровать и отсортировать, сделайте это один раз в action и положите результат в состояние:

```js
// action
visibleItems = items.filter(x => x.enabled).slice().sort((a, b) => a.price - b.price);
```

```json
"items": "$$ visibleItems"
```

*Листинг 12-1: тяжёлая работа выполняется однократно, props только читает результат*

## 12.3. Размер коллекций

Лимит шагов не ловит один класс проблем — рост потребления памяти. Классический пример:

```js
for (let x of items) {
  result = concat(result, [x]);      // каждый шаг копирует весь массив
}
```

Здесь шагов ровно столько, сколько элементов, но работы — квадратично от длины. Поэтому действует отдельный лимит на размер создаваемых коллекций.

Правильнее в таком случае воспользоваться `filter` или `map`, которые делают то же самое за один проход:

```js
result = items.filter(x => ...);
```

## 12.4. Атомарность actions

Мы упоминали это в разделах 4.4 и 11.4; здесь соберём правила вместе.

**Изменения применяются одним куском.** Пока action работает, состояние снаружи не меняется и экран не перерисовывается.

**Перерисовка происходит один раз** — после успешного завершения.

**При ошибке или превышении лимита изменения отбрасываются целиком.**

**Action не может запустить другой action.** События, пришедшие во время исполнения, встают в очередь и обрабатываются последовательно.

Последнее правило избавляет от целого класса проблем: двойное нажатие не создаст два заказа, а обновление состояния из обработчика не запустит каскад перерисовок.

# 14. Справочник встроенных средств

У ChupaLang нет собственной стандартной библиотеки. Всё перечисленное ниже — обычные встроенные средства JavaScript, и подробное описание любого из них есть в MDN. Здесь только перечень того, что разрешено.

## Массивы

Не изменяют массив: `length` · `map` · `filter` · `find` · `findIndex` · `some` · `every` · `reduce` · `join` · `slice` · `concat` · `indexOf` · `lastIndexOf` · `includes` · `flat` · `flatMap` · `at`

Изменяют массив на месте: `push` · `pop` · `shift` · `unshift` · `splice` · `sort` · `reverse` · `fill` · `copyWithin`

Вторая группа доступна в Init, Action и REPL, но не в props — там любое изменение данных отвергается (раздел 9.2). Если исходный порядок ещё нужен, сортируйте копию: `arr.slice().sort(cmp)`.

## Строки

`length` · `toUpperCase` · `toLowerCase` · `trim` · `trimStart` · `trimEnd` · `split` · `slice` · `substring` · `charAt` · `at` · `includes` · `startsWith` · `endsWith` · `replace` · `replaceAll` · `repeat` · `padStart` · `padEnd` · `localeCompare` · `concat`

`replace` и `replaceAll` — только со строковым образцом: регулярных выражений в языке нет.

## Объекты

`Object.keys` · `Object.values` · `Object.entries` · `Object.assign` · `Object.fromEntries` · оператор `in`

`Object.assign` вызывайте с пустым объектом первым аргументом: `Object.assign({}, a, b)`.

## Числа

`Math.min` · `Math.max` · `Math.abs` · `Math.round` · `Math.floor` · `Math.ceil` · `Math.trunc` · `Math.pow` · `Math.sign` · `Math.sqrt` · `Math.random`

`Number.isNaN` · `Number.isFinite` · `Number.isInteger` · `Number.parseFloat` · `Number.parseInt` · `Number.MAX_SAFE_INTEGER`

`toFixed` · `toPrecision` · `toString` — как методы числа: `price.toFixed(2)`.

`Math.random` доступна только в actions — см. раздел 10.3.

## Преобразования и проверки

`String(x)` · `Number(x)` · `Boolean(x)` · `typeof x` · `Array.isArray(x)`

## Диагностика

`console.log(x)` — недоступна в props.

## Чего нет

`Date` · `JSON.parse` / `JSON.stringify` · `RegExp` и литералы `/.../` · `Map` · `Set` · `WeakMap` · `WeakSet` · `Promise` · `Symbol` · `BigInt` · `Intl` · `parseInt` и `parseFloat` как глобальные (используйте `Number.parseInt`)

Даты и локализованное форматирование делают хост-функции — см. главу 10.

## Как дополнить

Всё, чего нет в JavaScript, пишется на самом языке и объявляется в init:

```js
function pick(obj, fields) { ... }
function getPath(obj, path, fallback) { ... }
function isEmpty(x) { return x == null || x === ""; }
```

Пример полной реализации — листинг 8-3.
