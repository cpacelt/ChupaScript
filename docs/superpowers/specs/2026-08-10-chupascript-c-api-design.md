# ChupaScript: публичный C API

Дата: 2026-08-10
Статус: состав заголовка зафиксирован

## 1. Область документа

Документ фиксирует границу между рантаймом ChupaScript и хостом: время жизни
сущностей, формат входных данных, соглашения заголовка и набор функций.

Заголовок один — `core/include/chupascript/chupascript.h`. Он рассчитан на
прямое чтение из Swift и на обёртку для Kotlin, поэтому C-совместим целиком и не
содержит ни одного типа C++.

Грамматика и семантика языка определены в `docs/grammar.md` и
`docs/semantics.md`; этот документ их не повторяет.

## 2. Как API используется

Схема, под которую он спроектирован:

1. Контроллер экрана получает JSON: макет вьюх и данные.
2. Создаёт **один контекст** на экран.
3. Загружает данные: разбирает пришедший JSON сам и по каждому корню зовёт
   отдельный вызов с именем и текстом литерала ChupaScript.
4. Разбирает макет, создаёт вьюхи. Для каждой вьюхи заводится структура `Props`,
   в полях которой лежат скомпилированные выражения.
5. Отрисовка вычисляет выражения; действия пользователя выполняют скрипты.
6. Экран закрыт — контекст уничтожен, вместе с ним всё остальное.

## 3. Владение и время жизни

**Владеющая сущность одна — `ChupaContext`.** Хост её создаёт и уничтожает;
больше в API нет ничего, что требует освобождения.

**Всё, что породил контекст, — невладеющие хендлы:** `ChupaExpression *`,
`ChupaScript *`, значения. Освобождать их нечем и не нужно.

Скомпилированные выражения и скрипты живут до смерти контекста. Значения живут
меньше: правило для них — «до следующего вычисления» — сформулировано в §7 и
строже потому, что хранилище значений переезжает при росте. Использование
хендла после отведённого ему срока — неопределённое поведение.

Следствия:

- Функция уничтожения в API ровно одна. Двойное освобождение невыразимо.
- Swift-структура `Props` остаётся структурой: поля-`OpaquePointer` копируются
  побитово, `deinit` не нужен, счётчики ссылок не появляются.
- Одинаковые исходники вправе вернуть **один и тот же** указатель. Дедупликация
  возможна именно потому, что владения нет: будь у выражения своё уничтожение,
  разделяемое дерево пришлось бы считать ссылками. API её уже допускает, и
  введение дедупликации не потребует изменений в заголовке.

Выигрыш от дедупликации не косметический: лента из 60 ячеек по 8 props — это
480 вызовов компиляции и 8 уникальных выражений.

**Память принадлежит контексту целиком.** В нём лежит всё: скопированный текст
исходников, разобранные данные, деревья разбора, значения. Поштучного
освобождения нет вовсе; вся память возвращается при уничтожении контекста.

Устроено это набором пулов, растущих дописыванием в хвост
(`2026-08-11-chupascript-values-design.md` §6). Замена их единым блоком
записана в `docs/backlog.md` B1 и на видимое из API поведение не влияет:
свойства владения от неё не зависят.

Отсюда следует, что временные значения, созданные при вычислении props,
накапливаются до закрытия экрана: расход растёт с числом пересчётов, а не с
объёмом данных. Это принято сознательно и на время — план разделения памяти
записан в §10, пункт 1.

**Потоки — без внутренней синхронизации.** Один контекст одновременно использует
не более одного потока; последовательное использование из разных потоков
допустимо. Разные контексты независимы: глобального изменяемого состояния в
библиотеке нет, поэтому два экрана могут готовиться параллельно.

## 4. Фазы контекста

```
создан  →  данные поставлены  →  компиляция и вычисление
```

Данные ставятся **не одним вызовом, а по одному на корень**: хост называет имя
и отдаёт текст его значения, `chupa_context_set(ctx, name, name_len, text,
text_len)` (детали формата — §5, нормативно —
`2026-08-11-chupascript-data-design.md`). Вызовов может быть сколько угодно, в
любом порядке между собой. Повторный вызов по уже существующему имени заменяет
его значение и состава имён не меняет — это не нарушение фазового порядка, а
штатная операция, доступная в любой момент.

Порядок, которым назван этот раздел, касается другой границы: **новое** имя
корня не должно появляться после первой компиляции макета, потому что
компилятор к тому моменту уже видел состав корневых имён и опёрся на него,
разрешая `usre.name` ошибкой компиляции, а не ошибкой первого показа экрана.
Механизм, отвергающий появление нового имени после компиляции, пока не
реализован — он ждёт самого слоя компиляции макета и зафиксирован как
`docs/backlog.md` B23.

Глубже первого сегмента проверять нечего: `user.prfoile.avatar` даёт `null` по
правилам чтения у `null` (`docs/semantics.md` §6.3) и ошибкой не является ни на
каком этапе.

## 5. Формат данных

Нормативное описание — `2026-08-11-chupascript-data-design.md`; здесь только
то, что видно на границе C API.

Хост сам разбирает пришедший с бэкенда JSON — рантайм JSON не видит и не
разбирает. Для каждого корня хост зовёт:

```c
chupa_context_set(ctx, "state", 5, "{\"count\": 0}", 12);
```

Имя — идентификатор ChupaScript (`docs/grammar.md` §4.4), а **текст — литерал
ChupaScript, а не JSON**: число, строка, `true`/`false`, `null`, массив или
объект, произвольно вложенные, — те же шесть форм из `docs/semantics.md`
§2.1. Разбирает его тем же парсером выражений, что и остальную программу;
проход, превращающий дерево в `Value`, одновременно проверяет литеральность.

Из этого следует, что отдельного профиля JSON у рантайма нет и быть не может:
профиль JSON — это то, как разбирает пришедший объект **хост**, до того как
текст каждого значения долетит досюда, и к границе C API отношения не имеет.
В частности:

- **Экспоненты в числах нет** (`1e3` — не число, а два токена, `1` и `e3`) и
  **юникодных escape нет** (`\uXXXX`) — это не решения о разборе данных, а
  свойства самого языка ChupaScript (`docs/grammar.md` §8, §4.6, §4.7),
  действующие для любого выражения. Текст значения — валидная программа
  ChupaScript ограниченного вида, поэтому подчиняется той же грамматике, что и
  остальной макет, а не отдельному, более снисходительному профилю.
- Дубликаты ключей объекта — последний выигрывает: материализация кладёт
  значения через `objectSet`, а он заменяет значение по существующему ключу.
- Глубина вложенности ограничена тем же пределом, что у парсера выражений —
  31 уровень (`docs/grammar.md` Приложение C.1); отдельного предела для данных
  нет.
- Строка без экранирования — срез текста, переданного в `chupa_context_set`;
  строка с экранированием раскодируется в пул. Набор экранирования — тот же,
  что в языке: `\\`, `\'`, `\"`, `\n`, `\t`.

`CHUPA_ERR_DATA` означает одно: текст, переданный для этого корня, не
разобрался как литерал целиком — синтаксическая ошибка, лишние байты после
значения или выражение (`count(x)`, `a + 1`) вместо записи значения.

**Ограничение, о котором нужно знать заранее.** Число в языке — `double`.
Идентификатор вида `9007199254740993` приедет искажённым. Лекарство одно:
такие поля бэкенд должен слать строками. Это свойство модели значений, а не
разбора данных, но проявляется оно здесь.

Пагинация в эту схему не входит: новая прогрузка ленты — новый контекст.

## 6. Соглашения заголовка

| Решение | Обоснование |
|---|---|
| Префикс `chupa_` у функций, `Chupa` у типов | В C нет пространств имён; `cs_` слишком ходовой, `chupascript_` длинный |
| C99; заголовок собирается и как C, и как C++ | Нужны `stdbool.h` и `stdint.h` |
| Заголовок самодостаточен | Включает `<stddef.h>`, `<stdint.h>`, `<stdbool.h>`; требующий предварительных включений заголовок ломает чужие сборки |
| Непрозрачные типы — неполные структуры | `typedef struct ChupaContext ChupaContext;` вместо `void *`: C ловит перепутанные аргументы |
| Строки на входе — `const char *` + `size_t` | Не полагаемся на NUL: Swift отдаёт `withUTF8` указателем с длиной, без копий. `size_t` Swift показывает как `Int` |
| Строки на выходе — указатель + длина, UTF-8, без NUL, во владении контекста | `count` строки в языке считает байты; строка может содержать любой байт |
| `bool` из `<stdbool.h>` | Swift видит `Bool`, а не `Int32` |
| Аннотации nullability | Swift превращает `_Nullable` в опционал, `_Nonnull` — в обычный тип; без них всё приезжает опционалом |
| Макрос `CHUPA_API` | На Android библиотека собирается с `-fvisibility=hidden` |
| Windows не закладывается | `__declspec` добавляется четырьмя строками, когда понадобится; сейчас это мёртвый код |
| Функции про сам контекст — `chupa_context_*`, операции — без этой части | Контекст принимают все функции без исключения, поэтому в именах операций эта часть несёт ноль информации |

Преамбула:

```c
#ifndef CHUPASCRIPT_H
#define CHUPASCRIPT_H

#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

#if defined(__clang__)
#  define CHUPA_NONNULL_BEGIN _Pragma("clang assume_nonnull begin")
#  define CHUPA_NONNULL_END   _Pragma("clang assume_nonnull end")
#  define CHUPA_NULLABLE      _Nullable
#else
#  define CHUPA_NONNULL_BEGIN
#  define CHUPA_NONNULL_END
#  define CHUPA_NULLABLE
#endif

#define CHUPA_API __attribute__((visibility("default")))

#if defined(__GNUC__) || defined(__clang__)
#  define CHUPA_MUST_USE __attribute__((warn_unused_result))
#else
#  define CHUPA_MUST_USE
#endif

#ifdef __cplusplus
extern "C" {
#endif

CHUPA_NONNULL_BEGIN

typedef struct ChupaContext    ChupaContext;
typedef struct ChupaExpression ChupaExpression;
typedef struct ChupaScript     ChupaScript;
typedef struct ChupaValue      ChupaValue;

typedef enum ChupaKind {
    CHUPA_KIND_NULL   = 0,
    CHUPA_KIND_BOOL   = 1,
    CHUPA_KIND_NUMBER = 2,
    CHUPA_KIND_STRING = 3,
    CHUPA_KIND_ARRAY  = 4,
    CHUPA_KIND_OBJECT = 5
} ChupaKind;

typedef enum ChupaStatus {
    CHUPA_OK    = 0,  /* значение получено          */
    CHUPA_NULL  = 1,  /* выражение дало null        */
    CHUPA_ERROR = 2   /* ошибка либо не тот тип     */
} ChupaStatus;

typedef enum ChupaErrorCode {
    CHUPA_ERR_NONE = 0,
    CHUPA_ERR_SYNTAX,   /* лексика и синтаксис                          */
    CHUPA_ERR_NAME,     /* неизвестный корень, функция, число аргументов */
    CHUPA_ERR_TYPE,     /* не тот тип операнда при выполнении           */
    CHUPA_ERR_RANGE,    /* индекс массива, запись за границу            */
    CHUPA_ERR_DATA,     /* значение корня не является литералом         */
    CHUPA_ERR_USAGE,    /* нарушён порядок вызовов                      */
    CHUPA_ERR_MEMORY
} ChupaErrorCode;
```

`CHUPA_MUST_USE` ставится на функции, чей возврат несёт признак успеха: без
него `chupa_value_number(ctx, v, &w);` без проверки компилируется молча.

**Ограничение импортёра Swift.** Все три непрозрачных типа Swift покажет одним и
тем же `OpaquePointer` — различать их он не умеет. Обёртка на Swift обязана
завернуть их в собственные типы, иначе `chupa_eval(ctx, script)` соберётся. В C
такая перепутка не собирается.

## 7. Функции

```c
/* Версия библиотеки как "major.minor.patch". Никогда не NULL. */
CHUPA_API const char *chupa_version(void);

/* ─── Контекст ─────────────────────────────────────────────────────── */

/* Создаёт пустой контекст. NULL — не хватило памяти. */
CHUPA_API ChupaContext *CHUPA_NULLABLE chupa_context_create(void);

/* Уничтожает контекст и всё, что он породил: данные, скомпилированные
 * выражения и скрипты, значения. NULL допустим и ничего не делает. */
CHUPA_API void chupa_context_destroy(ChupaContext *CHUPA_NULLABLE ctx);

/* Заводит или заменяет один корень: name — идентификатор, text — литерал
 * ChupaScript (не JSON) целиком. Вызывается по одному разу на каждый
 * корень, сколько угодно раз в любом порядке; повторный вызов по тому же
 * имени заменяет значение. При неудаче корень не заводится и не меняется. */
CHUPA_API bool chupa_context_set(ChupaContext *ctx,
                                 const char *name, size_t name_len,
                                 const char *text, size_t text_len);

/* ─── Последняя неудача на этом контексте ──────────────────────────── */

/* Класс ошибки. CHUPA_ERR_NONE — неудач не было. */
CHUPA_API ChupaErrorCode chupa_context_error_code(const ChupaContext *ctx);

/* Смещение в байтах от начала исходника, переданного в компиляцию.
 * Строку и колонку хост считает сам: текст у него есть. */
CHUPA_API size_t chupa_context_error_offset(const ChupaContext *ctx);

/* Сообщение для человека, по-английски. Действительно до следующего
 * вызова любой функции с этим контекстом. */
CHUPA_API const char *CHUPA_NULLABLE
chupa_context_error(const ChupaContext *ctx, size_t *CHUPA_NULLABLE len);

/* ─── Компиляция ───────────────────────────────────────────────────── */

/* Компилируют исходник. Текст копируется — буфер вызывающего больше не
 * нужен. Результат принадлежит контексту и живёт до его смерти;
 * уничтожать его отдельно нельзя и нечем. Одинаковые исходники могут
 * вернуть один и тот же указатель. NULL — ошибка компиляции. */
CHUPA_API ChupaExpression *CHUPA_NULLABLE
chupa_compile_expression(ChupaContext *ctx, const char *source, size_t len);

CHUPA_API ChupaScript *CHUPA_NULLABLE
chupa_compile_script(ChupaContext *ctx, const char *source, size_t len);

/* ─── Исполнение ───────────────────────────────────────────────────── */

/* Выполняет скрипт: мутирует данные контекста, значения не возвращает.
 * false — ошибка выполнения, часть изменений могла быть применена. */
CHUPA_API CHUPA_MUST_USE bool chupa_run(ChupaContext *ctx, ChupaScript *script);

/* ─── Вычисление: скаляры ──────────────────────────────────────────── */

/* Быстрый путь. Хост заявляет ожидаемый тип выбором функции, поэтому
 * вычисление и проверка типа — один вызов. CHUPA_NULL означает, что
 * выражение дало null: для вьюхи это «возьми значение по умолчанию».
 * Число и логическое возвращаются копией и живут сколько угодно;
 * строка указывает в память контекста (см. правило ниже). */
CHUPA_API CHUPA_MUST_USE ChupaStatus
chupa_eval_number(ChupaContext *ctx, ChupaExpression *e, double *out);

CHUPA_API CHUPA_MUST_USE ChupaStatus
chupa_eval_bool(ChupaContext *ctx, ChupaExpression *e, bool *out);

CHUPA_API CHUPA_MUST_USE ChupaStatus
chupa_eval_string(ChupaContext *ctx, ChupaExpression *e,
                  const char **out, size_t *len);

/* ─── Вычисление: любой тип ────────────────────────────────────────── */

/* Общий путь: агрегаты и случай, когда тип заранее неизвестен.
 * NULL — ошибка; значение null приезжает как CHUPA_KIND_NULL. */
CHUPA_API const ChupaValue *CHUPA_NULLABLE
chupa_eval(ChupaContext *ctx, ChupaExpression *e);

/* ─── Доступ к значению ────────────────────────────────────────────── */

CHUPA_API ChupaKind chupa_value_kind(const ChupaContext *ctx, const ChupaValue *v);

CHUPA_API CHUPA_MUST_USE bool chupa_value_bool  (const ChupaContext *ctx, const ChupaValue *v, bool   *out);
CHUPA_API CHUPA_MUST_USE bool chupa_value_number(const ChupaContext *ctx, const ChupaValue *v, double *out);

CHUPA_API const char *CHUPA_NULLABLE
chupa_value_string(const ChupaContext *ctx, const ChupaValue *v, size_t *len);

CHUPA_API CHUPA_MUST_USE bool chupa_array_count(const ChupaContext *ctx, const ChupaValue *v, size_t *out);
CHUPA_API const ChupaValue *CHUPA_NULLABLE
chupa_array_at(const ChupaContext *ctx, const ChupaValue *v, size_t i);

CHUPA_API CHUPA_MUST_USE bool chupa_object_count(const ChupaContext *ctx, const ChupaValue *v, size_t *out);
CHUPA_API const char *CHUPA_NULLABLE
chupa_object_key_at(const ChupaContext *ctx, const ChupaValue *v, size_t i, size_t *len);
CHUPA_API const ChupaValue *CHUPA_NULLABLE
chupa_object_value_at(const ChupaContext *ctx, const ChupaValue *v, size_t i);
CHUPA_API const ChupaValue *CHUPA_NULLABLE
chupa_object_get(const ChupaContext *ctx, const ChupaValue *v, const char *key, size_t len);
```

**Время жизни результата.**

> Указатель, отданный `chupa_eval_string` или `chupa_eval`, и всё достижимое
> из него действительны до следующего вычисления на этом контексте.

Правило описывает реальность буквально. Пулы значений переезжают при росте
(`2026-08-11-chupascript-values-design.md` §3), поэтому указатель, выданный до
ближайшей мутации, после неё повисает. Хост копирует строку в свой тип при
первом касании, и держать результат дольше ему незачем.

Числа и логические значения правилу не подчиняются: они возвращаются копией.

**Порядок перечисления ключей объекта не определён.** В языке он не определён
тоже (`docs/semantics.md` §2.1), а хранение отсортировано — обещание связало бы
руки.

**Копирование исходника закрывает вопрос о времени жизни буфера.** Требование
`docs/grammar.md` §7 — чтобы буфер пережил скомпилированную программу — снято:
контекст копирует текст в свой пул, строковые литералы становятся срезами этой
копии, хост освобождает свой буфер сразу. Цена — одна копия текста на экран.

**Ошибка в `chupa_run` оставляет данные изменёнными частично.** Скрипт —
последовательность стейтментов; ошибка прерывает её посередине, откатывать
нечего, поскольку хранилище не держит предыдущих состояний. Обработчик, упавший на
третьем присваивании из пяти, оставит первые два применёнными. Это цена принятой
модели памяти, а не недосмотр.

## 8. Ошибки

**Канал.** Провал возвращается признаком — `false`, `NULL` или `CHUPA_ERROR`, —
а подробность лежит в контексте и читается тремя аксессорами. Так устроены
sqlite и большинство C-библиотек: признак в возврате нельзя проигнорировать
незаметно, тогда как выходной параметр — можно.

**Класс.** `ChupaErrorCode` нужен, чтобы хост различал ситуации, не разбирая
текст сообщения. `SYNTAX` — сломан макет, чинить на бэкенде. `NAME` и `TYPE` —
данные разошлись с макетом. `USAGE` — ошибка обёртки. Реакция и логи у них
разные.

**Позиция.** Смещение в байтах от начала исходника, переданного в компиляцию.
Строка и колонка не хранятся: текст есть у хоста, а считать их приходится раз в
сто лет.

**Сообщение.** Для человека, по-английски, в фиксированном буфере внутри
контекста. Фиксированный, а не растущий вместе с данными, — иначе поток ошибок
съедал бы память наравне с полезными данными.

**Списка диагностик нет.** Каждое выражение компилируется отдельным вызовом,
поэтому одна ошибка на вызов и есть вся ошибка. Список имел бы смысл при
компиляции макета целиком, а так мы не делаем.

## 9. Принятые решения и обоснования

| Решение | Обоснование |
|---|---|
| Один контекст на экран, время жизни задаёт хост | Совпадает с временем жизни контроллера, вьюх и `Props` |
| Ничто из порождённого не переживает контекст | Убирает подсчёт ссылок и сборщик мусора целиком: освобождение одно, вместе с контекстом |
| Скомпилированное принадлежит контексту | Кэш между экранами в этой схеме не возникает — `Props` умирают вместе с контроллером. Взамен появляется дедупликация внутри экрана |
| Единственная функция уничтожения | Двойное освобождение невыразимо; `Props` остаётся структурой без `deinit` |
| Данные ставятся по вызову на корень, новое имя запрещено после первой компиляции | Компилятор видит состав корней на момент компиляции и ловит опечатку в корневом имени при разборе макета |
| Формат значения корня — литерал ChupaScript, не JSON | JSON снаружи разбирает хост; рантайму нужен только текст значения, а он разбирается тем же парсером, что и остальная программа |
| Ключи объекта отсортированы | Порядок в языке не определён; двоичный поиск по массиву быстрее хеш-таблицы на типичных 3–20 ключах |
| Исходник копируется в пул контекста | Снимает с хоста обязательство хранить буфер; одна копия текста на экран |
| Канал ошибок — признак в возврате, подробность в контексте | Признак нельзя проигнорировать незаметно; `warn_unused_result` ловит невзятый результат |
| Диагностика — класс, смещение, сообщение | Класс избавляет хост от разбора текста; смещение позволяет показать место в макете; строку и колонку хост считает сам |
| Без внутренней синхронизации | Один экран — один поток; контексты независимы, глобального состояния нет |
| `Value` — тег-юнион, без NaN-boxing | Решение пользователя: используем то, что уже есть в `core/src/value.hpp` |
| Наружу — непрозрачный `ChupaValue *` с функциями доступа | Раскладка не видна, через границу едут только примитивы и указатели. Обёртки Swift и Kotlin строят поверх этого свои типы |
| Функции доступа принимают контекст первым параметром | Значение адресует пулы индексами, и разрешить их может только выдавший контекст. Подпись перестаёт врать о времени жизни, а в Swift получается `ctx.string(of: v)` |
| Не сериализация агрегата в JSON | Разбор на стороне хоста дороже обхода на два порядка: `JSONDecoder` боксит каждое число и строит промежуточные объекты, тогда как обход — прямые вызовы без аллокаций |
| Скаляры возвращаются копией, а не хендлом | У числа наверху нет дома в хранилище: пришлось бы материализовать ячейку ради каждого пересчёта props |
| Трёхзначный `ChupaStatus` у скалярных вычислений | `null` в props — норма, а не исключение: данные с бэкенда неполные, чтение у `null` даёт `null`. Отличать его от ошибки обязательно |
| Функции доступа проверяют, а не полагаются на предусловие | Несовпадение типа приходит из данных, а не только из ошибки программиста: макет вправе сказать `"width": "@{ user.name }"`. UB от данных недопустимо |
| Два соглашения о провале: `NULL` у указателей, признак плюс выходной параметр у остальных | Если у типа есть невозможное значение, признак избыточен. Выходной параметр остаётся у четырёх функций вместо десяти, а в Swift указатель приезжает готовым опционалом |
