# ChupaScript: данные контекста

Дата: 2026-08-11
Статус: принято

## 1. Область документа

Документ описывает, как хост наполняет контекст данными: форму вызова, формат
значения, разбор и превращение разобранного в `Value`.

Не входит: устройство хранилища (`2026-08-11-chupascript-values-design.md`),
состав заголовка C API (`2026-08-10-chupascript-c-api-design.md`), вычисление
выражений.

## 2. Форма вызова

Хост называет корень и отдаёт текст его значения. По вызову на корень.

```c
chupa_context_set(ctx, "state", 5, "{\"count\": 0}", 12);
```

Внутренний интерфейс:

```cpp
// core/src/data.hpp
namespace CS {

/// Разбирает текст литерала и кладёт значение в контекст под именем name.
///
/// Текст обязан быть литералом целиком (§3). Выражение, лишние байты после
/// значения и синтаксическая ошибка отвергаются; diag получает класс, смещение
/// и сообщение.
bool setVariable(Context &ctx, std::string_view name, std::string_view text,
                 Diagnostic &diag);

}  // namespace CS
```

**Имя обязано быть идентификатором** по `grammar.md` §4.2 — `[A-Za-z_]`, дальше
`[A-Za-z0-9_]`, только ASCII, — и не совпадать с зарезервированным словом (§4.5:
`true`, `false`, `null` и заготовленные `if`, `while`, `for` и прочие). Имя, не
удовлетворяющее этому, отвергается.

Проверка нужна ради того же, ради чего имена вообще отданы хосту: корень, к
которому программа не может обратиться, бесполезен. Имя выбирает хост
сознательно, поэтому имя, которое язык не в состоянии написать, — ошибка хоста,
и сообщить о ней надо сразу, а не оставлять невидимую переменную.

**Имя корня даёт хост.** Это закрывает `docs/backlog.md` B3. Альтернатива —
брать корни из ключей объекта верхнего уровня — оставляла недостижимыми ключи,
не являющиеся идентификаторами: к полю `content-type` или `@meta` не подобраться
никаким написанием, и пришлось бы отдельно решать, отвергать такие данные или
молча их терять. Отвергать плохо: бэкенд добавит служебное поле, и экран
перестанет открываться из-за данных, которые никому не мешают. При именовании со
стороны хоста этой развилки нет вовсе.

**Данные приходят к хосту внутри JSON и разбираются им.** Типичная форма —
массив `variables`, где у каждого элемента есть `name` и `value`, и `value` —
строка. Хост извлекает пару и передаёт её сюда. Рантайм внешнего JSON не видит.

Из этого следует важное для §3: **экранирование внешнего уровня уже снято**.
Пока бэкенд пишет `"value": "Привет"`, разбирает
это JSON-парсер хоста, и до нас доезжают настоящие байты UTF-8.

## 3. Формат значения

Текст значения — **литерал ChupaScript**, а не JSON. Отдельного формата данных
нет: грамматика уже описывает всё нужное в `docs/grammar.md` §5.4.

| Форма | Пример |
|---|---|
| `Number` | `3`, `0.5`, `-3` |
| `String` | `'Вася'`, `"Вася"` |
| `Boolean` | `true`, `false` |
| `Null` | `null` |
| `Array` | `[3, 3, 3]`, `[]` |
| `Object` | `{"3": 3}`, `{}` |

Вложенность произвольная в пределах §4. Обе формы кавычек равноправны (`grammar.md` §A):
двойные заведены как раз потому, что текст живёт внутри JSON-строки.

**Унарный минус принимается.** Грамматика числового литерала знака не содержит —
`NumericLiteral ::= Digit+ ( '.' Digit+ )?`, — поэтому `-3` разбирается узлом
`Unary` над `Number`. Отвергать его значило бы запретить отрицательные данные, а
причина отказа была бы совершенно неочевидной. Материализация сворачивает такую
пару в отрицательное число (§5).

`!` не принимается: `!true` — вычисление, а не запись значения.

**Экспоненты нет.** `1e3` — не число, а два токена, `1` и `e3` (`grammar.md`
§11, сознательное исключение). Это единственное расхождение с JSON, которое
переживает границу, и оно ложится ограничением на автора содержимого `value` —
того же человека, который пишет выражения в соседних полях макета. `1e-7`
записывается как `0.0000001`. Нарушение видно сразу: разборщик отвергает текст с
внятным сообщением, а не принимает молча.

**Юникодных escape в языке нет, и они не нужны** (`grammar.md` §11: «символ
вписывается напрямую; явная запись доступна на уровне JSON»). Для данных
действует то же рассуждение, что и для выражений, по той же причине: и текст
программы, и текст значения приезжают внутри JSON-строки, и внешний уровень
снимается хостом до нас.

## 4. Разбор

Текст разбирается **существующим парсером выражений** — `parseExpression` из
`core/src/parser.hpp`. Отдельного разборщика данных нет.

**В парсере не меняется ни строки.** Ни нового режима, ни флага, ни ветки в
`primary()`. Ограничение «только литералы» не выражается грамматикой и не
проверяется при разборе: флаг в парсере лёг бы ветвлением в самую горячую
функцию ради пути, который выполняется один раз на переменную при сборке экрана,
а не на каждую перерисовку.

Отсюда же следует, что путь вычисления props не задет ничем: он остаётся тем
же, что измерен в `benchmarks/baseline.json`.

Предел вложенности агрегатов — тот же, что у парсера: 31 уровень
(`grammar.md` Приложение C.1). Отдельного предела для данных нет; глубже
тридцати одного уровня переменные экрана не бывают.

## 5. Материализация

`parseExpression` выдаёт дерево, контексту нужны значения. Проход, который их
превращает, — он же и есть проверка на литеральность: обход идёт по видам узлов
и на любом виде, которого в данных быть не должно, останавливается ошибкой
вместо того, чтобы строить значение.

Отдельной проверки нет: она не стоит ничего сверх прохода, который нужен в любом
случае.

```cpp
// core/src/data.cpp, внутренняя
bool materialize(const Ast &ast, NodeId node, Context &ctx, Value *out,
                 Diagnostic &diag);
```

| Вид узла | Что делает |
|---|---|
| `Number` | `Value::number` |
| `String` | `Context::makeString`; экранирование раскодируется (§5.1) |
| `Boolean` | `Value::boolean` |
| `Null` | `Value::null` |
| `Array` | `makeArray(count)`, затем `arrayPush` по элементам |
| `Object` | `makeObject(count)`, затем `objectSet` по парам |
| `Unary` с операцией `-` над `Number` | отрицательное число |
| всё прочее | ошибка §6 |

**Ёмкость известна заранее**, поэтому `makeArray` и `makeObject` получают точный
размер: `Ast::childCount` даёт его до обхода. Переездов и мусора при построении
данных не возникает — ровно тот случай, ради которого точное выделение
существует (`2026-08-11-chupascript-values-design.md` §5).

**Дубликаты ключей: последний выигрывает.** Это не отдельное правило, а
следствие: `objectSet` по существующему ключу заменяет значение. Бэкенд
отсутствия дубликатов не гарантирует, так что поведение должно быть определённым.

**Порядок ключей не сохраняется.** Хранение отсортировано, и порядок в языке не
определён (`docs/semantics.md` §2.1).

**Циклов в данных не бывает.** Литерал — дерево, а не граф; каждый агрегат
создаётся ровно один раз и вкладывается ровно в одно место. Ссылочность (§2.3)
на данные распространяется, но алиасы в них может создать только хост, положив
одно значение под двумя именами, — а это отдельные вызовы `setVariable` с
отдельными разборами, то есть отдельные агрегаты.

### 5.1 Экранирование

Парсер экранирование не раскодирует: он помечает строковый литерал флагом
`hasEscape` и хранит срез исходника (`docs/backlog.md` B9). Материализация
обязана раскодировать, потому что в `Value` едет содержимое, а не запись.

Набор — тот же, что в языке (`grammar.md` §A): `\\`, `\'`, `\"`, `\n`, `\t`.
Ничего сверх: неизвестная последовательность отвергнута ещё лексером.

Строка без экранирования копируется в пул текста как есть. С
экранированием — раскодируется во временный буфер и оттуда попадает в пул. Флаг
`hasEscape` избавляет от временного буфера в подавляющем большинстве случаев.

Тот же порядок понадобится вычислителю для строковых литералов внутри выражений,
поэтому раскодирование живёт отдельной функцией, доступной обоим. B9 этим
закрывается для данных; для выражений он закрывается вместе с вычислителем, той
же функцией.

## 6. Ошибки

`setVariable` возвращает признак и заполняет `Diagnostic` — тот же канал, что у
лексера и парсера.

| Что | Пример | Сообщение |
|---|---|---|
| Синтаксическая ошибка | `[3, 3,]` | из парсера, без переписывания |
| Выражение вместо литерала | `count(items)`, `a + 1`, `user.name` | `expression is not allowed in data` |
| Унарный оператор кроме минуса | `!true` | то же |
| Минус не над числом | `-'abc'` | то же |
| Пустой текст значения | пустая строка | из парсера |
| Имя не идентификатор | `content-type`, `2fa`, `если`, `null` | `root name must be an identifier` |

**Смещение считается от начала текста значения**, а не от начала макета: хост
получает позицию внутри своего поля `value` и может указать на неё.

Первая ошибка выигрывает: разбор дальше не идёт, и диагностика лексера доезжает
до вызывающего без переписывания — то же правило, что в парсере.

**Неудача не оставляет корня.** Если разбор или материализация провалились, имя
в контексте не появляется, а мусор, успевший попасть в пулы, остаётся до смерти
контекста — освобождения по одному нет.

## 7. Корни в контексте

Контекст обзаводится таблицей корней: имя → значение.

Отдельной структуры для неё не нужно. Таблица корней — это в точности
отображение `String` → значение, то есть **объект**, и вся машинерия уже есть:
отсортированный массив пар, двоичный поиск, вставка со сдвигом хвоста. Контекст
держит один объект и работает с ним теми же методами.

```cpp
// добавляется в core/src/context.hpp
Value root(std::string_view name) const noexcept;    // null, если имени нет
bool hasRoot(std::string_view name) const noexcept;
void setRoot(std::string_view name, Value v);
std::uint32_t rootCount() const noexcept;
std::string_view rootNameAt(std::uint32_t i) const noexcept;
```

`hasRoot` — то, на чём будет стоять проверка §7.1 семантики: всякий
идентификатор в программе есть чтение из контекста, и обращение к
несуществующему корню отвергается при компиляции макета, а не при первом показе
экрана.

**Повторный `setVariable` по существующему имени заменяет значение.** Состав
имён при этом не меняется, поэтому проверки, сделанные при компиляции, остаются
верными. Прежнее значение не освобождается: расход растёт с числом замен —
та же плата, что и везде в этом слое, и закрывается тем же B1.

**Введение нового имени после компиляции ломает проверку** и должно отвергаться.
Механизма для этого здесь не заводится: заморозка требует знания о том, что
компиляция состоялась, а компилятора на этом слое нет. Требование записано за
слоем компиляции и в `docs/backlog.md`; `hasRoot` — всё, что ему для этого
нужно.

## 8. Что это закрывает

- **B3** — форма `set_data`. Закрыт: имя корня даёт хост.
- **B9** — раскодирование экранирования. Закрыт для данных; для строковых
  литералов внутри выражений закрывается вместе с вычислителем, той же функцией.
- **B14** — глава 10 `docs/semantics.md`. Разблокирована: недоставало именно
  того, как хост наполняет контекст и какие имена в нём видны. Пишется вместе с
  C API, где закрывается последний её вопрос — время жизни значений на границе.

Новый пункт в `docs/backlog.md`: запрет на введение нового корня после первой
компиляции, с указанием, что механизм появляется вместе с компилятором.

## 10. Тесты

Помимо очевидных проверок шести форм, набор обязан закрыть то, ради чего дизайн
именно такой.

**Литеральность.** Каждый запрещённый вид узла отвергается со своим смещением:
`user.name`, `count(items)`, `a + 1`, `items[0]`, `a ? b : c`, `!true`,
`-'abc'`. Проверять надо не только признак, но и позицию: сообщение без места
бесполезно хосту.

**Минус.** `-3` даёт `-3`; `-0.5` даёт `-0.5`; `[-1, -2]` работает внутри
агрегата; `-0` сохраняет знак нуля (`semantics.md` §2.1 включает отрицательный
ноль в модель).

**Экранирование.** `'a\nb'` даёт три байта с переводом строки посередине;
`'a\\b'` — три байта с обратным слэшем; `"a\"b"` — три байта с кавычкой.

**Имена.** Идентификатор принимается; `content-type`, `2fa`, пустое имя, имя с
не-ASCII и зарезервированное слово отвергаются, каждое со своим сообщением.

**Уже снятое экранирование внешнего уровня.** Строка с настоящими байтами
кириллицы разбирается и сохраняет их побайтно — это проверка того, что мы не
пытаемся декодировать то, что декодировал хост.

**Агрегаты.** Точная ёмкость: массив на сто элементов не оставляет мусора.
Дубликат ключа: последний выигрывает. Пустые `[]` и `{}`. Вложенность.

**Корни.** Имя, которого нет, читается как отсутствующее; повторный `set`
заменяет значение и не заводит второго имени; `rootCount` считает имена, а не
вызовы; перечисление отдаёт все имена.

**Неудача не оставляет корня.** После провалившегося `setVariable` имя в
контексте не появляется, а прежнее значение того же имени, если оно было,
остаётся прежним.

## 11. Бенчмарки

- разбор и материализация плоского объекта из десяти полей — типичная переменная;
- то же для массива из ста чисел — типичный список;
- строка с экранированием против строки без него: цена временного буфера;
- поиск корня при трёх, десяти и тридцати именах.

Числа записываются в `benchmarks/baseline.json` тем же механизмом, что у
лексера, парсера и хранилища.
